데이터 확보 가능성 조사

조사일: 2026년 9월 30일. 대상: 환자·이송자용 모바일 웹, 병원용 웹, 배정 알고리즘의 캡스톤 시연.

결론

공개 API로 병원 위치·진료 분야와 일부 현재 가용 정보를 확보하고, 환자별 수용 응답과 미래 자원 일정은 병원 웹 또는 가상 데이터로 보완한다. API 연결만으로 전문의·수술실 부족을 해결하거나 도착 시점의 수용을 보장할 수는 없다.

이번 조사는 공식 서비스 설명과 공개 개발 문서 확인까지 완료했다. 인증키로 의료 API의 실제 응답을 수집하거나, 개별 필드의 결측률·갱신 지연을 측정한 것은 아니다. 아래 영문 이름은 우리 서버의 정규화 필드이며 원본 API 필드명으로 확정한 것이 아니다.

1. 확보 경로

| 필요한 데이터 | 확보 경로와 확인 수준 | 시연에서의 사용과 한계 |
|---|---|---|
| 병원 주소·연락처·좌표·진료과목 | 국립중앙의료원 서비스 설명에서 제공 확인 [1] | 후보 병원 기본정보. 진료과 존재만으로 현재 치료 가능을 확정하지 않음 |
| 응급실·수술실·중환자실 관련 가용 정보 | 국립중앙의료원 설명에 포함 [1] | 현재 상태 참고. 자원별 필드·단위·결측 의미는 활용가이드 및 실제 응답 검증 필요 |
| 중증질환 수용 가능 정보 | 국립중앙의료원 설명에서 제공 확인 [1] | 질환·시술 조건 후보 필터. 특정 환자의 수용 확답과 구분 |
| 의료기관 기본정보 | 심평원 병원정보서비스 [2] | 보조 기준정보. 신고 기반 정보이며 현재 근무 상태가 아님 |
| 시설·장비·진료과목·전문과목별 전문의 수 | 심평원 의료기관별상세정보서비스 [3] | 시설·인력 구성 확인. 근무 중·수술 중 여부와 구분 |
| 환자 위치→병원 이동시간·거리 | 카카오모빌리티 자동차 길찾기 [4] | 도로 이동시간 추정. 응급차 특례 주행이나 실제 도착시각 보장 아님 |
| 환자 진료과·우선순위·필요 자원 | 가상 환자 데이터, 입력 화면 | 초기에는 주어진 값. 자동 진단 구현 제외 |
| 환자별 수용 여부·불가 사유·응답시각 | 자체 병원 웹과 서버 | 공개 조회 API에 환자별 수용 문의·예약 쓰기 기능이 있다고 확인되지 않음. 자체 구현 |
| 현시점 당직 전문의·수술팀 실제 가용성 | 병원 입력 또는 협력기관 연계 필요 | 조사한 공개 설명에서 확보 확인 못함. 시연은 가상 운영 인력 |
| 진료·수술 종료 예상시각, 대기열 | 병원 입력/연계 또는 가상 데이터 | 공개 API로 확정 확보했다고 볼 수 없음. 모델의 주요 가정 |
| 이동 중 환자의 도착 예정 수요 | 자체 확정 이송 기록 | 시스템 이용 환자만 직접 관측 가능 |
| 앱 미사용 환자 유입 | 병원에서 발생 후 등록 | 미래 유입을 미리 알 수 없음. 시뮬레이터의 실제 사건과 알고리즘 관측을 분리 |
| 도착 시점 수용 가능성 | 위 자료로 계산한 추정 결과 | 원천 데이터가 아니라 모델 출력. 병원 재확인 필요 |

[1]은 전국 응급의료기관의 위치, 진료 정보, 일부 가용 자원과 중증질환 수용 정보를 제공하는 REST/XML 서비스다. 포털 갱신 주기는 ‘실시간’으로 표기되어 있다. 이 표기는 모든 병원이 몇 초마다 입력한다는 보장이 아니며, 원본 정보가 관측된 시각과 서버 수집 시각을 별도로 확인해야 한다.

[2]의 암호화된 요양기관 식별자를 [3]의 조회에 사용한다. 국립중앙의료원 식별자와 동일하다고 가정하지 않는다. [3]의 갱신 주기 역시 포털에는 실시간으로 표기되어 있으나, 전문의 수를 당직 가용 인원으로 해석하지 않는다.

2. 신청 및 실응답 검증

- 우선 신청: 국립중앙의료원 전국 응급의료기관 정보 조회 서비스. 공식 페이지에 개발·운영 자동승인으로 기재되어 있다. 현재 페이지의 개발 트래픽 숫자는 비어 있어 승인 계정의 한도를 확인해야 한다. [1]
- 보완 신청: 심평원 병원정보서비스와 의료기관별상세정보서비스. 개발계정 트래픽은 각 페이지에 10,000으로 표시된다. 병원정보서비스의 운영단계는 심의승인, 상세정보서비스는 자동승인으로 표시되므로 각각 확인한다. [2][3]
- 이동시간: 카카오 개발자 앱과 REST API 키 설정이 필요하다. 의료정보나 환자 증상은 지도 요청에 포함하지 않고 출발·도착 좌표만 전달한다. 비용·쿼터는 실제 계정과 사용량 기준으로 별도 확인한다. [4][5]
- 국립중앙의료원 참고문서: 공식 페이지의 ‘NIA-IFT-OpenAPI활용가이드-01.국립중앙의료원-응급의료정보조회서비스_V13.hwp’. 이번 조사에서는 공개 설명까지 확인했으며 파일 내부 필드명·코드표는 미검증이다. 원본 키 이름은 추측해 확정하지 않는다.

실응답 검증의 완료 조건:
1. 승인된 키로 지역을 한정한 첫 정상 응답과 오류 응답을 확보한다. 키는 응답 파일·로그에서 제거한다.
2. 주소/기관/가용병상/중증질환 조회별 요청 파라미터, 원본 필드명, 코드표, 단위, 페이지네이션을 기록한다.
3. 병원 10곳의 기본정보와 동적 정보를 연결하고, 같은 이름의 분원·주소 변경을 확인한다.
4. 빈 문자열, 누락, 음수·특수 코드, 0의 의미를 구분한다. 미확인을 0 또는 ‘수용 가능’으로 변환하지 않는다.
5. 원본 갱신시각 제공 여부를 확인한다. 없으면 source_observed_at=null로 두며 fetched_at으로 대신하지 않는다.
6. 허용 쿼터 내 반복 관측으로 값 변경 빈도·결측률·오류율을 측정한다. API 값의 변경 주기는 실제 병원 사건의 발생 시각과 다를 수 있다.
7. 가용병상과 실제 수용 응답 간 차이는 병원 협력 없이는 검증 완료로 표시하지 않는다.

3. 내부 데이터 계약

| 객체 | 최소 필드 | 출처 |
|---|---|---|
| Hospital | hospital_id, source_ids, name, address, phone, lat, lon, capabilities | 공개 기준정보·수동 매칭 |
| ResourceSnapshot | hospital_id, resource_type, reported_available, source_observed_at, fetched_at, source, version, quality | 공개 API 또는 병원 입력 |
| ResourceCalendar | hospital_id, resource_type, capacity, blocked_intervals, valid_from, valid_to | 가상 데이터 또는 병원 입력 |
| Patient | patient_id, origin, required_capabilities, resource_demands, priority, priority_source, requested_at, latest_start_at, duration_estimate, state | 가상 데이터·화면 입력 |
| Inquiry | request_id, patient_id, hospital_id, response, responded_at, expires_at, patient_version, resource_version | 자체 병원 웹 |
| Assignment | patient_id, hospital_id, state, eta_at, estimated_start_at, version | 자체 배정 서버 |
| TravelEstimate | origin, destination, duration_seconds, distance_meters, fetched_at, provider, scenario | 지도 API 또는 합성 행렬 |
| ExternalArrival | event_id, hospital_id, occurred_at, observed_at, resource_demands, duration_estimate | 병원 입력·실험 사건 |

시간은 서버에서 UTC로 저장하고 화면은 한국시간으로 표시한다. 솔버 입력은 최초 실험 기준시각에서 지난 정수 분으로 변환한다. 소요시간은 올림하여 도착 이전 치료가 잡히지 않게 한다.

응답 상태: PENDING / ACCEPTED / DECLINED / EXPIRED / CANCELLED. 미응답은 거절이 아니며 최종 배정에는 사용할 수 없다. ACCEPTED는 해당 환자 조건의 응답으로 저장하고 조건 변경 또는 만료 시 재확인한다.

병원 간 식별자 매칭: 이름·주소·전화·좌표로 후보를 만들고, 애매한 항목은 사람이 확인한다. 확인한 hospital_id↔각 출처 ID 관계만 저장한다. 자동 이름 매칭을 확정 연결로 사용하지 않는다.

4. 수집과 갱신 설계

브라우저 → 자체 서버 캐시 → 원천 API 구조를 사용한다. 화면의 2~3초 조회는 자체 서버 상태 조회이며 의료·지도 API를 매번 호출하는 설정이 아니다.

초기 실험 설정안: 기본정보는 최초 적재, 병원 웹 사건은 즉시 서버 반영, 외부 가용 정보는 60초 수집 간격을 후보로 둔다. 실제 적용 간격은 쿼터·페이지 수·소스 갱신 특성 확인 후 결정한다. 60초는 제공기관의 보장 주기가 아니다. 하루 호출량은 ‘하루 수집 횟수 × 지역·페이지·엔드포인트 수’로 산정한다.

응답 만료·정보 신선도 기준은 설정값으로 분리한다. 출처 관측시각이 없거나 기준을 넘긴 정보는 확인 필요로 표시하고, 동적 가용성을 확정 조건으로 사용하지 않는다. 오류 시 마지막 데이터를 그 나이와 함께 보여주되 최신 상태로 위장하지 않는다.

가용 수와 점유를 이중 차감하지 않는다. 총 용량+개별 점유일정을 관리하는 시연 캘린더를 솔버의 기준으로 사용한다. API의 잔여 병상 수에서 이미 반영된 기존 점유를 다시 빼지 않는다. 공개 스냅샷만 있는 병원은 미래 일정이 없으므로 미래 가용 시간 계산을 완성할 수 없다.

5. 바로 진행할 데이터 작업

1. 우선 한 지역 10개 병원과 20명 이하의 가상 환자로 시작한다. 지역·규모는 실험 설정이며 실제 대표성을 주장하지 않는다.
2. 병원 기본정보가 확보되기 전에도 같은 내부 스키마의 가상 병원을 사용해 화면·서버·솔버를 연결한다.
3. public / hospital_input / synthetic 출처를 모든 레코드에 표시한다. 실제 병원 이름에 가상 자원을 붙이는 시연에서는 가상 운영 상태임을 화면에 표시한다.
4. api_field_mapping.md에 원본 필드→내부 필드 매핑과 결측 처리를 채운 후 어댑터를 구현한다.
5. 미래 자원 일정은 처음에는 진료 자리와 전문팀의 가상 점유 구간으로 만든다. 수술실·ICU 연속 치료 단계는 별도 확장으로 둔다.
