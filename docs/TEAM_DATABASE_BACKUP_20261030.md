# 공통 시연 DB 백업·검사·복원

대상: `server.team_runtime`에서 만든 **합성 병원 10곳 전용 공통 DB**. 기본 시연 DB는 `data/team-common.db`다. API로 수집한 실제 병원 DB나 표식이 다른 DB를 공통 시연 DB로 변환하지 않는다.

실행 도구: `server/team_backup.py`. UI·음성 해석·기준 배정 알고리즘을 변경하지 않았다. 기존 `server/recovery_rehearsal.py`의 독립 가상 복구 리허설과 별개로, 이미 사용하는 공통 DB를 온라인 상태에서 백업하는 관리 명령이다.

## 1. 사용 방법

저장소 루트에서 공통 서버용 Python 환경을 사용한다. 아래 출력 폴더와 복원 DB 이름은 예시이며 **매번 새로운 이름**을 지정한다.

```powershell
# 실행 중인 원본 서버를 유지한 채 백업 가능
python -m server.team_backup backup --db data/team-common.db --output data/backups/team-common-20261030-01

# 파일 해시, 스키마, 행 수, 업무 기록 해시, SQLite 무결성 재검사
python -m server.team_backup verify --backup data/backups/team-common-20261030-01

# 기존 파일을 덮어쓰지 않고 별도 DB로 복원
python -m server.team_backup restore --backup data/backups/team-common-20261030-01 --db data/team-restored-20261030-01.db

# 서버 실행 기준 및 복원 DB 검사
python -m server.team_runtime check --db data/team-restored-20261030-01.db

# 복원본을 별도 포트에서 명시적으로 실행
python -m server.team_runtime serve --db data/team-restored-20261030-01.db --port 18034
```

각 백업 명령에는 `--timeout-seconds 30`을 지정할 수 있다. 성공은 종료코드 0과 `success:true`, `verified:true`로 확인한다. 실패는 종료코드 1이며, 인자 오류는 argparse 종료코드 2다. 출력에는 환자 정보·음성 원문·DB 행을 넣지 않는다.

복원은 서버 실행이나 기존 화면의 연결 주소 변경까지 자동 수행하지 않는다. 복원 서버를 사용할 때 화면도 해당 포트의 서버를 보도록 설정한다. 기존 실행 DB를 삭제하거나 교체할 필요가 없다.

## 2. 보존되는 내용과 초기화되는 내용

| 구분 | 처리 |
| --- | --- |
| 환자·문의·수용 응답·대화·음성 초안·이벤트·전달 및 확인 기록 | 백업 시점의 행·식별자·버전 보존 |
| 수용 응답 만료시각·문의 마감·다음 평가시각·자원 관측시각 | 원래 시각 보존. 새로 연장하거나 최신 정보로 표시하지 않음 |
| 자원 수량·점유·수용 조건·출처 | 보존. 합성 자원도 자동 보충하거나 갱신하지 않음 |
| 입력 `planning_state.revision` | 보존 |
| 계산 중이던 임시 lease | **복원본에서만** `lease_owner=NULL`, `lease_until=0`, `last_error=NULL` |
| 이전 계산 결과 캐시 | **복원본에서만** `planning_results` 삭제, `completed_revision=-1`로 재계산 요청 |

사라진 프로세스의 계산 lease가 남아 있으면 워커가 최대 300초 기다릴 수 있으므로 초기화한다. 이는 수용 응답·업무 잠금을 해제하거나 자원을 확보하는 조치가 아니다. 새 서버에서 실제 배정 워커가 다시 계산하고 문의 워커가 저장된 업무를 이어 간다.

복원 뒤 실제 시간이 지나 이미 만료된 수용 응답은 정상적으로 만료 처리되며, 마감이 지난 문의 업무도 원래 마감 기준으로 처리된다. 백업 시각으로 시간을 되돌리거나 약속의 유효기간을 늘리지 않는다.

## 3. 백업 형식과 실패 처리

출력 폴더에는 `snapshot.db`와 `manifest.json`이 저장된다.

- SQLite backup API로 읽기 트랜잭션의 일관된 스냅샷을 만든다. 실행 중인 원본의 **커밋된 WAL 기록**을 포함하며, 단순 `.db` 파일 복사를 사용하지 않는다.
- 백업 DB는 DELETE journal 형식의 단일 파일로 닫는다. 원본 WAL·SHM·OS 잠금파일을 복사하지 않는다.
- 명세에는 버전·생성시각·공통 DB 표식·파일 SHA-256·스키마 해시·테이블별 열/행 수/논리 해시가 들어간다. 환자별 값과 인증키는 명세나 정상 로그에 넣지 않는다.
- 복원 전에 전체 명세와 실제 DB가 일치해야 한다. 복사 직후에는 전체 논리 상태를, 계산 임시 상태 초기화 뒤에는 스키마와 모든 업무 테이블의 해시를 다시 비교한다.
- 업무 해시에서 제외하는 것은 `planning_state`, `planning_results`, `sqlite_sequence`뿐이다. 전체 테이블 해시는 별도로 명세에 포함된다.
- 기존 출력 폴더·복원 DB·WAL/SHM/journal 파일이 있으면 거절한다. `--force`나 삭제·덮어쓰기 기능은 없다. 링크·정션·하드링크 별칭 경로도 거절한다.
- 복원 대상은 공통 실행기와 같은 OS 잠금으로 보호한다. 잠금파일이 남았다는 이유만으로 삭제하지 않는다. 실제로 사용 중인 잠금은 거절하고 해제된 파일은 재사용한다.
- 중간 실패 산출물은 보존한다. 성공 결과를 받지 못한 복원본을 서버로 실행하지 말고, 원인을 확인한 뒤 새 출력/DB 경로로 다시 실행한다.

파일과 명세의 일치는 우발적인 훼손 검사용이다. 전자서명·암호화·외부 백업·자동 주기 백업은 이번 기능에 포함하지 않는다. DB 파일 자체에는 원래 업무 정보가 들어 있으므로 보관·공유 범위도 기존 DB와 같다.

## 4. 검증 범위

`test_team_backup.py`는 별도 가상 DB만 사용한다. 원본 보존, 커밋 WAL 포함 및 미커밋 제외, 온라인 실행 잠금 중 백업, 변조/명세/외래키 오류 감지, 새 경로 강제, 대상 잠금, 제한시간, 만료시각 보존 등을 검사한다.

`test_team_backup_resume.py`는 임시 localhost 서버와 **실제 두 백그라운드 워커**를 사용한다. 음성 등록·미제출 수정 초안·수용 응답·알림 전달 기록을 만든 뒤, 미래 300초 계산 lease와 대기 문의가 있는 합성 스냅샷을 복원한다. 복원 직후 모든 업무 해시가 같고, 이후 문의가 3곳에서 6곳으로 진행되며 새 `READY` 결과·미래 만료시각·solver 결과·완료 revision이 확인돼야 통과한다. due-time 조정은 원본 시연 DB가 아닌 **명시적 가상 시험 조건**이다.

```powershell
python -m unittest test_team_backup test_team_backup_resume -v
```

Windows에서 CP-SAT 자식 프로세스를 포함하는 사용자 정의 실행 스크립트에는 `if __name__ == '__main__':` 보호문을 둔다. 기존 운영/시연 DB와 실제 병원에는 요청하지 않는다. UI·마이크·다른 물리 PC·정전 후 파일 복구는 이 자동시험의 검증 범위에 포함되지 않는다.

결과 원본은 `outputs/team_database_backup_20261030/`에 보존한다. Windows 심볼릭 링크 생성 권한이 없는 시험은 생략 여부를 보고서에 표시하며, 이를 실행 통과 수에 포함하지 않는다.

다음 연결 작업은 팀원 화면에서 동일 이송 복원, 문의/수용/확정/조건 변경 알림, 재접속 후 중요 사건 확인을 실제 기기로 확인하는 것이다. 서버 복구 검사 통과와 화면 연결 완료는 구분한다.
