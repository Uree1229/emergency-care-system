## 첫날 진행 순서

1. 아래 방식으로 **현재 main을 새 폴더에 받아** 자기 브랜치를 만듭니다.
2. 자신의 작업 안내와 AI 시작 프롬프트를 읽힙니다. AI가 현재 상태·소유 범위·첫 검증을 요약하게 합니다.
3. [공통 실행 안내](COMMON_RUNTIME.md)의 외부 키 없는 개발 시연부터 실행합니다. 첫날부터 모든 솔버·연구 실험을 설치하거나 재현할 필요는 없습니다.
4. 기존 정상 흐름을 먼저 확인합니다. 같은 환자 ID로 문의 → 병원 응답 → 목적지 확정 → 출발 → 대화 → 도착이 이어져야 합니다.
5. 첫 작업의 실패 상황을 재현하고, 작은 수정과 관련 검사를 진행합니다. 정리한 증거와 함께 PR을 올립니다.

### 브랜치 준비

Git 접근 권한이 있는 계정으로 실행합니다. 아래는 개발 중인 폴더를 건드리지 않는 새 복사본 기준입니다.

```powershell
git clone --branch main https://github.com/Uree1229/emergency-care-system.git emergency-care-dev1
cd emergency-care-dev1
git switch -c codex/dev1-paramedic-20261102
git log -1 --oneline
```

dev2는 폴더를 `emergency-care-dev2`, 브랜치를 `codex/dev2-hospital-20261102`로 바꿉니다. 이후 작업별 브랜치 이름은 날짜·기능을 덧붙여 구분합니다. 기존 작업 폴더의 변경을 `reset --hard`, 강제 checkout, 파일 일괄 덮어쓰기로 지우지 않습니다.

| `server/`, DB 스키마·운영 자료, 배정·문의 정책, `simulation/`, 솔버·기준 해시·고정 의존성 | 서버 담당. 화면 문제를 해결하려고 직접 변경하지 않음 |

한 담당이 GPT와 Claude를 함께 사용한다면 같은 파일을 동시에 수정시키지 않습니다. 작업별 폴더·브랜치를 나누고 변경 파일을 확인한 뒤 합칩니다. 새 React/Next/Flutter 프로젝트를 추가하거나 기존 정적 웹 구조를 교체하는 일은 이번 첫 작업에 포함하지 않습니다.

## API가 부족하거나 다르게 동작하면

화면 담당은 서버 코드를 임의로 고치거나 SQLite에 직접 값을 넣어 우회하지 않습니다. 다음 형식으로 계약 확인을 요청합니다.

```text
담당 / 작업 ID:
Git 커밋 / 서버 주소 / 실행 모드:
재현 순서:
요청 method·path·본문(키·실제 개인정보 제외):
실제 상태코드·응답:
기대한 동작 / 현재 UI로 해결할 수 없는 이유:
임시 우회 없이 보존한 기록:
```

특히 [main에 없는 v1.4 API](CURRENT_STATE.md#main에-없는-로컬-전용-기능)는 서버 담당이 통합하기 전까지 호출 대상으로 삼지 않습니다. 서버의 기존 수용·확정·자원·버전 검사를 끄지 않습니다.

## PR과 작업 종료 기록

한 PR에는 하나의 재현 가능한 개선을 담습니다. `git add .`로 DB·키·녹음·다른 담당 변경을 함께 올리지 말고 파일 목록을 확인합니다. main에 직접 기능 코드를 밀어 넣거나 다른 담당 브랜치를 강제로 갱신하지 않습니다.

PR 설명에는 다음 다섯 가지를 적습니다.

1. 바뀐 사용자 동작과 재현 상황.
2. 수정한 파일과 담당 범위.
3. 실행한 검사 명령·결과. 실행하지 않은 검사는 미실행으로 표시.
4. 실제 브라우저·기기에서 확인한 범위와 남은 한계.
5. 서버 계약 확인 요청과 다음 작업.

완료 기준은 버튼이나 화면의 존재가 아니라 **동일 환자·담당자·병원 범위에서 기록이 맞게 남고, 유실·재시도·새로고침 후에도 잘못된 중복 처리가 없는 것**입니다.
