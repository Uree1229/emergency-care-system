## 재현한 문제

현재 환자 앱의 수동 등록은 `id` 없이 `POST /api/patients`를 보내고 서버는 요청마다 새 `P-UUID`를 발급합니다. `7749443`과 `6fbf6c6`의 이 경로는 같습니다. 실제 서버 HTTP 요청 처리기와 새 SQLite 메모리 DB를 사용해 첫 저장을 성공시킨 뒤 응답만 호출자에게 전달하지 않고 같은 본문을 다시 보냈습니다.

| 합성 요청 | 첫 저장과 재요청 | 저장 결과 |
|---|---|---|
| 현재 화면처럼 ID 없음 | 첫 `200` 응답 유실, 같은 본문 재전송 `200` | 서로 다른 환자 ID 2개, 생성 사건 2개, 대화 2개, 문의 0개 |
| 같은 고정 ID 지정 | 첫 `200` 응답 유실, 같은 본문 재전송 `409 DUPLICATE`, 해당 ID 조회 `200` | 환자·생성 사건·대화 각 1개, 문의 0개 |
| 고정 ID로 나이를 바꿔 재전송 | 같은 본문 재요청과 동일한 `409 DUPLICATE` | 첫 환자와 첫 입력값 유지 |

요청 처리기에서 응답을 버려 재현했습니다. 통합 완료 시 환자 앱에서도 연결 장애 후 복구를 확인하세요. [환자 앱 등록](../../../../patient-ui/app.js#L232) · [등록 경로](../../../../server/app.py#L524) · [서버 저장과 중복 응답](../../../../server/service.py#L355)

## 적용할 최소 계약

1. 환자 앱은 첫 제출 전에 고정 환자 ID를 한 번 만들고 서버 origin과 원래 본문을 함께 임시 보관합니다. 같은 탭에서 결과가 확인될 때까지 새 ID 발급과 본문 변경을 막습니다. 저장소에 기록하지 못하면 보내기 전에 오류를 표시합니다. 임시 보관 범위와 유효기간을 구현과 함께 기록하세요.
2. 새로고침·재접속 시 원래 서버의 같은 ID를 조회합니다. 최초 응답 유실·손상·서버 오류가 생기면 해당 등록을 미확인 상태로 남겨 두고, 사용자가 원래 요청 재시도를 선택할 때만 같은 ID와 본문으로 전송합니다. 조회 실패나 다른 서버의 응답이 오면 원래 요청을 보존합니다. 조회 시점의 범위가 바뀌면 늦은 응답을 폐기합니다.
3. 서버 담당과 기존 등록 경로에 붙일 선택적 재시도 계약을 먼저 합의합니다. 제안은 서버가 계산한 원래 등록 본문의 fingerprint를 환자 ID와 연결해 생성과 같은 트랜잭션에 저장하는 것입니다. 같은 ID와 fingerprint의 재시도는 최초 저장을 확인하고 현재 환자를 반환합니다. 같은 ID에 다른 본문이 오면 `409`로 거절합니다. 이전에 생성된 환자처럼 비교 근거가 없는 경우 화면은 확인 필요를 유지합니다. 기존 ID 생략 호출의 계약도 보존합니다.
4. 모바일 `create_episode`는 고정 `MOBILE-UUID`와 `extra.source_app`, 정렬한 JSON 본문의 SHA-256을 보냅니다. `DUPLICATE`·연결 실패·응답 손상·서버 오류 뒤 같은 ID를 조회해 두 값이 모두 일치하는지 확인합니다. 이 조회·검증 순서를 참고하세요. 모바일은 `auto_inquiry=True`로 시작하는 별도 업무이므로, 환자 웹은 저장 이후 현재의 명시적 문의 시작 동작을 유지합니다. 서버가 직접 계산하고 보존한 등록 근거를 재시도 판정에 사용하세요. [모바일 요청 생성과 복구](../../../../emergency-app/common_server.py#L127)

환자 앱 코드와 해당 테스트는 dev1 범위입니다. 등록 API·스키마·마이그레이션이 필요한 경우 서버 담당과 변경 파일과 호환성을 정한 뒤 함께 진행하세요. 병원 화면과 음성 업무는 각 담당 범위를 따릅니다.

## 완료 기준

- 정상 등록에서 환자·생성 사건·대화가 각 1개이고, 환자 앱이 저장한 ID의 진행 화면을 엽니다.
- 저장 성공 뒤 응답 유실 또는 응답 JSON 손상을 넣어도 원래 ID의 환자·생성 사건·대화가 각 1개입니다. 새로고침 때 자동 POST가 없으며, 정확한 원요청 복구 뒤에도 각 1개입니다.
- 같은 ID의 동시 요청은 동일 본문이면 최초 저장 한 건으로 귀결됩니다. 다른 본문이면 한 요청만 저장되고 다른 요청은 충돌합니다. 수정된 기존 환자를 조회해도 원래 등록의 동일성을 별도로 판단합니다.
- 같은 ID를 조회해도 원본문이 일치하지 않거나 비교 근거가 없으면 성공 처리하지 않습니다. GET 실패·저장소 오류·서버 전환·늦은 응답도 각각 확인합니다.
- 확인 완료 후 사용자가 명시적으로 새 환자 등록을 시작하면 새 ID로 별도의 한 건을 만듭니다. 모든 등록·복구 시도에서 자동 문의가 0개이고 기존 문의 시작 버튼은 동작합니다.

새 합성 DB에만 장애를 주입하고 실행 커밋, 실패 경로, 결과별 환자·생성 사건·대화·문의 개수와 명령을 보관하세요. 기록에는 합성 ID와 상태 또는 요청 해시를 쓰고 원본문·개인정보·키는 포함하지 않습니다. 단위 검사, HTTP 처리기, 실제 브라우저 검증을 각각 구분하고 미실행 항목을 표시하세요. 등록 회귀는 `test_patient_workflow_registration*`처럼 구분되는 이름을 사용합니다.
