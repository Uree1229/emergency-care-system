# 서버 조건 변경 처리의 지도 재생

2026-10-13. 격리된 가상 SQLite에서 실제 서버의 서비스·워커 함수를 실행하고, 생성된 사건과 시각별 상태를 지도에 연결했다. 기능 흐름 시연이며 알고리즘의 개선율을 입증하는 비교 실험은 아니다.

## 실행

저장소 루트에서 Python 표준 라이브러리만으로 실행한다.

```powershell
python -m server.transport_replay_experiment
python -m simulation.transport_replay_adapter
python -m simulation.viewer_server --reuse-data --no-browser --port 18005
```

지도 주소: `http://127.0.0.1:18005/?scenario=transport-server-transport-change`.

기존 지도 데이터가 없다면 마지막 명령에서 `--reuse-data`를 뺀다. 원래 지도 데이터 생성과 이번 서버 기록 생성은 별개다. 선택창의 **서버 조건 변경 처리 기록** 그룹에서 다음 4가지를 고른다.

| 사례 | 확인할 동작 | 관찰 종료 결과 |
|---|---|---|
| 환자별 영향 구분 | 같은 병원으로 이동 중인 A·B 중 전문팀이 필요한 A만 재확인 | B 도착 확인, A는 재확인 상태 유지 |
| 병원의 수용 유지 판단 | 병원이 기존 환자 수용을 유지한다고 판단 | 목적지 유지, 대체 문의 없음, 도착 확인 |
| 수용 확인 뒤 사람의 목적지 변경 | 조정 요청 → 대체 문의 → 수용 확보 → 사람의 변경 | 새 병원으로 목적지 변경 후 도착 확인 |
| 대체 수용을 확보하지 못함 | 대체 후보가 모두 수용 불가 응답 | 기존 목적지와 조정 필요 상태 유지, 도착 미기록 |

변경 사례의 대본상 시각은 전문팀 점유 증가 60초, 병원의 조정 요청 65초, 대체 문의 66초, 새 병원 수용 응답 80초, 변경 대기 83초, 사람의 목적지 변경 95초다. **80초에 수용 응답이 와도 95초 전에는 목적지가 바뀌지 않는다.** 이 시각들은 실제 병원의 응답시간 통계가 아니다.

## 실제 처리 기록과 합성 입력

- 기록기: `server/transport_replay_experiment.py`. 임시 DB를 만들고 `service`, `transport_review`, `transport_reassignment`를 실행한다. 현재 시연 DB와 외부 API는 사용하지 않는다.
- 원본: `simulation_results/server_transport_replay.json`. 사건 ID·원래 시각·처리자·payload·원본 사건을 보존한다. 동작 직후 환자별 스냅샷과 별도 위치 관측을 저장한다.
- 변환기: `simulation/transport_replay_adapter.py`. 원본 사건을 하나도 생략하지 않고 순서를 유지한다. 원본 파일 SHA256을 재생 자료에 남긴다.
- 재생 자료: `simulation/viewer/transport_replay_data.json`. 기존 문의 정책 검증 자료와 별도 파일이다.
- 화면: 현재 시각까지 저장된 상태만 사용한다. 병원 확정과 출발, 새 수용 응답과 사람의 목적지 변경을 구분한다. 변경 전 이동 구간은 원래 병원까지 늘리지 않고 변경 당시의 위치에서 끝낸다.

병원·환자·자원·병원 판단·위치·이동시간·도착 확인은 모두 합성 입력이다. 점선 차량 이동은 대본상 위치 관측 사이의 보간이며 실제 도로 경로가 아니다. ETA만으로 도착을 만들어 넣지 않는다. 치료·전원·예후는 미기록으로 표시한다.

## 확인한 범위

기록기 8개·변환기 7개를 포함한 관련 회귀 **79개**가 통과했다. 실제 DB 사건과 원본의 일치, 결정성, 환자별 영향 구분, 수용 유지, 사람의 변경 전 목적지 유지, 변경 지점의 경로 연속성, 미해결 시 도착 미생성을 확인했다.

Chrome **12개 검사**로 4개 사례, 대체 문의선, 시간별 목적지·상태, 사건 이동, 재생·정지, 기존 지도·문의 정책 재생과 390px 화면을 확인했다. 증거는 `.codex-build/transport-replay-20261013/`에 있다. API 키·실제 환자·실제 병원 전송은 사용하지 않았다.

## 다음 성능 검증

이번 기능 시연을 개선율로 제시하면 안 된다. 다음은 **문의 정책을 동일하게 고정하고 배정 규칙만 바꿔** 첫 수용·예상 도착 우선·자원 경합 조정·CP-SAT을 비교하는 것이다. 모든 방식에 같은 환자·외생 상태 변화·회신 조건·관측 가능 정보를 제공해야 한다.

CP-SAT이 현재 시점의 후보를 비교하는 방식과 미래 사건까지 아는 전체 기간 최적해를 구분한다. 전체 기간 최적해는 성능 상한 비교용이며 온라인 운영 방식의 공정한 직접 비교군이 아니다. 문의 수, 미배정, 선정시간, 예상 도착, 재확인부터 변경까지의 지연, 불필요한 목적지 변경을 함께 보고한다. 이미 결과를 본 seed는 독립 검증으로 재사용하지 않는다.
