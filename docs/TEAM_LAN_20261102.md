# 11월 2일 같은 WiFi PC·휴대전화 연결

구성은 **휴대전화/PC → HTTPS 게이트웨이 → PC의 `127.0.0.1` 공통 full 서버 → 같은 합성 DB**다. 새 `server.team_lan` 도구만 추가했으며 기존 공통 서버의 loopback 제한·DB 잠금·워커·화면은 유지한다. 이 문서는 서버 연결 준비이며 팀원 화면·브라우저 마이크 시험 완료를 뜻하지 않는다.

## 1. 준비할 것

- PC와 휴대전화를 같은 WiFi에 연결한다. 게스트망의 기기 간 통신 차단/AP isolation이 있으면 다른 시험망을 사용한다.
- Python 3.12와 `requirements-server.txt` 의존성, Git for Windows의 OpenSSL이 필요하다. 기본 탐지는 `C:/Program Files/Git/usr/bin/openssl.exe`다. 다른 설치는 `prepare --openssl "실제 경로"`로 지정한다.
- 아래 예시의 `192.168.0.10`은 **서버 PC의 WiFi IPv4**로 바꾼다. 휴대전화에서 `127.0.0.1`을 사용하면 휴대전화 자신을 가리킨다.

```powershell
python -m pip install --target .solver_deps -r requirements-server.txt
python -m server.team_lan addresses
```

`addresses`는 사설 IPv4 후보와 자체 시험용 `127.0.0.1`만 표시한다. 여러 어댑터가 있으면 Windows WiFi 설정 또는 `ipconfig`로 WiFi 주소를 직접 확인한다. 공인 IP·`0.0.0.0`·링크로컬·IPv6는 bundle 준비에 허용하지 않는다.

## 2. 한 번만 새 인증서 bundle 준비

프로젝트 루트에서 실행한다. **출력 폴더가 이미 있으면 덮어쓰지 않는다.** IP가 바뀌면 새 이름으로 다시 준비한다.

```powershell
python -m server.team_lan prepare --ip 192.168.0.10 --output data/team-lan-20261102
```

생성 파일:

| 파일 | 용도·공유 범위 |
|---|---|
| `rootCA.crt` | 이 시험의 공개 루트 인증서. 시험할 PC·휴대전화에 이 파일만 전달 |
| `rootCA.key` | 루트 개인키. 서버 PC에 보관, 기기에 전달하지 않음 |
| `server.crt`, `server.key` | HTTPS 서버 인증서·개인키. 서버 PC에 보관 |
| `access-token.txt` | 무작위 32자 접속 비밀번호. 파일 값은 로그·Git·URL·화면 캡처에 넣지 않음 |
| `manifest.json` | IP·용도·공개 CA 해시만 포함. 키·비밀번호 값은 없음 |
| `.gitignore` | `*`로 bundle 안의 파일 전부 Git에서 제외 |

인증서는 14일 동안 유효하며 선택한 IP, `127.0.0.1`, `localhost`를 SAN에 넣는다. 서버는 선택한 IP에만 바인딩한다. 일반 LAN bundle의 PC 접속도 선택 IP를 사용한다. `127.0.0.1` bundle은 같은 PC 자체 시험 전용이다.

bundle은 `data/` 같은 비공개 폴더에 둔다. `server/static`, `paramedic-ui`, `patient-ui`, `hospital-ui` 아래 경로는 비밀 파일이 웹으로 노출될 수 있어 거절한다. bundle 전체를 메신저·공유 폴더에 올리지 않는다. 준비 중 실패한 새 폴더는 자동 삭제하지 않으므로, 실패 원인을 확인하고 새 출력 경로를 사용한다.

## 3. 각 기기에서 CA 신뢰를 수동 설정

도구는 OS 신뢰 저장소를 변경하지 않는다. **공개 `rootCA.crt`만** USB·파일 전송 등으로 전달해 시험할 기기에 직접 설치한다. 설치 파일의 SHA-256은 bundle의 `manifest.json.ca_sha256`와 비교할 수 있다. 알 수 없는 다른 인증서를 설치하지 않는다.

- **Windows PC:** `rootCA.crt`를 열고 인증서 설치에서 현재 사용자 → 신뢰할 수 있는 루트 인증 기관을 선택한다. 조직 정책으로 설치가 막히면 관리자의 시험 환경 정책을 따른다.
- **Android:** 기기 설정의 보안/인증서 설치에서 CA 인증서로 설치한다. 제조사마다 메뉴가 다르다. Chrome을 완전히 다시 열고 아래 주소의 인증서가 신뢰되는지 확인한다.
- **iPhone/iPad:** 인증서 프로파일 설치 후 설정 → 일반 → 정보 → 인증서 신뢰 설정에서 해당 시험 루트의 완전 신뢰도 직접 켠다.

인증서 경고를 무시하거나 브라우저 보안 기능을 끄는 방법으로 시험하지 않는다. 종료 후 시험용 CA와 iOS 프로파일은 기기 설정에서 직접 제거할 수 있다.

## 4. 공통 full 서버와 게이트웨이 실행

**터미널 A:** 기존 DB와 구분되는 전용 합성 DB를 사용한다. 같은 파일이 있으면 초기화하지 않고 보존한다.

```powershell
python -m server.team_runtime serve --db data/team-wifi-20261102.db --port 18033
```

**터미널 B:** 위 서버와 워커가 시작된 후 게이트웨이를 켠다.

```powershell
python -m server.team_lan serve --bundle data/team-lan-20261102 --upstream-port 18033 --port 18443
```

게이트웨이는 시작 전에 OpenSSL로 서버 인증서의 CA 서명·유효기간·선택 IP의 SAN을 확인한다. bundle의 IP만 수정하거나 다른 인증서·키를 복사해 섞으면 바인딩 전에 거절한다. upstream의 `/api/team-runtime`에서는 합성 full 모드, 고정3 문의·3초 솔버, 유효 공통 DB·프로필, 두 워커의 `RUNNING` 상태를 확인한다. `voice-only`, 옛 지도 재생/시연 서버, 배정 워커가 꺼진 `team_demo`, 다른 정책·upstream은 거절한다. 아직 워커가 시작 중이면 상태를 확인한 뒤 재실행한다.

게이트웨이는 upstream을 `127.0.0.1`로 고정한다. upstream과 HTTPS 포트는 달라야 한다. 공통 서버를 LAN에 직접 공개하거나 `server.app --seed`로 바꿔 띄울 필요가 없다. 두 터미널은 시험 중 계속 실행하고, 종료는 게이트웨이부터 Ctrl+C, 그다음 공통 서버를 Ctrl+C로 종료한다.

## 5. Windows 방화벽이 막을 때만 수동 허용

도구가 방화벽을 수정하지는 않는다. PC WiFi가 신뢰하는 시험망의 **Private** 프로필인지 먼저 확인한다. 필요한 경우 관리자 PowerShell에서 아래 명령을 사람이 직접 실행한다. IP는 실제 WiFi IP로 바꾼다.

```powershell
New-NetFirewallRule -DisplayName "Capstone WiFi HTTPS 18443" -Direction Inbound -Action Allow -Protocol TCP -LocalAddress 192.168.0.10 -LocalPort 18443 -Profile Private -RemoteAddress LocalSubnet
```

공개/Public 프로필이나 모든 원격 주소로 범위를 넓히지 않는다. 18033 loopback 포트는 열지 않는다. 시험 후 만든 규칙이 더 이상 필요 없으면 해당 이름의 규칙만 제거한다.

```powershell
Remove-NetFirewallRule -DisplayName "Capstone WiFi HTTPS 18443"
```

## 6. PC·휴대전화에서 같은 HTTPS origin 사용

두 기기에서 `https://192.168.0.10:18443`를 사용한다. 브라우저가 인증을 요청하면 사용자 이름은 **`team`**, 비밀번호는 서버 PC에서 별도로 확인한 `access-token.txt`의 값이다. 주소에 `team:비밀번호@...`를 넣지 않는다.

이 Basic 인증은 시연 서버 접속 암호다. **구급대원·병원 의료 운영 계정, 병원별 권한, 의료진 인증을 구현한 것은 아니다.** `actor_id`와 병원 ID는 기존 시연용 계약을 따른다. 실제 환자 자료를 이 시험에 사용하지 않는다.

| 용도 | 같은 HTTPS origin 뒤의 경로 |
|---|---|
| 음성 입력 화면 | `/paramedic/` |
| 구급대 진행 화면 | `/patient/?pid=반환된환자ID` |
| 병원 H01 | `/hospital/?hid=H01` |
| 공통 실행 정보 | `/api/team-runtime` |
| DB·워커 상태 | `/api/system/status` |
| 음성 기능·STT 준비 여부 | `/api/voice/capabilities` |

화면에서 API 주소를 별도로 설정한다면 이 HTTPS origin으로 통일한다. HTTPS 화면에서 `http://127.0.0.1:18033`이나 PC의 HTTP 주소를 직접 호출하면 다른 기기·mixed content·CORS 문제가 생긴다. 게이트웨이는 다른 Origin의 요청을 허용하지 않는다. 화면 소스는 바꾸지 않았으므로, 하드코딩된 주소나 화면 간 환자 ID 전달은 담당자가 연결해야 한다. `/api/team-runtime`의 원본 내부 `links`는 loopback 서버 링크일 수 있으므로 휴대전화에서는 위 HTTPS 경로를 사용한다.

음성 제출 응답의 `patient.id`가 공통 이송 ID다. 다른 예제의 고정 ID를 사용하지 않는다. `actor_id`, 음성 `sid`, 환자 `pid`, 요청 ID는 재접속에도 유지하고, `expected_version`의 대상이 음성 초안인지 환자인지 구분한다. `start_inquiry:false`로 보냈다면 서버가 임의로 문의를 시작하지 않는다.

서버 전용 준비 확인은 인증서 검증을 켠 상태로 실행한다. 비밀번호 자체를 명령 인자에 넣지 않는다.

```powershell
python -m server.team_readiness check --server https://192.168.0.10:18443 --ca data/team-lan-20261102/rootCA.crt --token-file data/team-lan-20261102/access-token.txt
python -m server.team_readiness seed --server https://192.168.0.10:18443 --ca data/team-lan-20261102/rootCA.crt --token-file data/team-lan-20261102/access-token.txt --case general --run-id WIFI-20261102-A --output data/wifi-20261102-A-receipt.json
```

seed는 새 합성 시험 건을 만들고 기존 환자를 덮어쓰지 않는다. 준비 검사와 시험 결과의 범위는 해당 도구 문서를 따른다. 병원에서 수용·담당자가 목적지 확정하는 단계는 자동 통과시키지 않는다.

## 7. 마이크·알림·채팅 시험의 경계

신뢰된 HTTPS와 마이크 권한은 기기 시험의 전제이며 음성 인식 성공을 보장하지 않는다. `getUserMedia`는 secure context가 필요하고, 브라우저 `SpeechRecognition`은 지원이 제한되며 일부 인식 엔진은 인터넷에 의존한다. Android/iOS의 실제 시험 브라우저에서 권한과 지원 여부를 확인한다. [마이크 보안 조건](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [브라우저 음성 인식 지원](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition).

서버 `transcripts` API는 앱 STT 결과를 받는다. 별도 `audio` API는 Azure 설정이 있을 때 16kHz·모노·16비트 PCM WAV의 짧은 최종 인식을 지원한다. 일반 WebM 녹음을 그대로 보내거나 실시간 서버 스트리밍을 지원한다고 가정하지 않는다. 게이트웨이 추가는 STT 모델·파서 변경이 아니다.

알림은 기존 폴링·수신/확인 API이고 앱 푸시를 새로 구현한 것이 아니다. 알림 GET과 delivered/acknowledge를 구분한다. 채팅은 구급대·현재 병원의 메시지와 서버 자동 사건이며, 병원 참여는 목적지 확정 후다. 정상 흐름 외에 새로고침, 같은 요청 재시도, 문의 후 정보 수정, 이송 중 변경안 승인, 이전 병원 대화 세션 종료도 실제 두 기기로 확인한다.

## 8. 보호 범위와 검증

TLS 1.2 이상, Basic 인증, 같은 Origin/Host 검사, 최대 16MiB 요청, 고정 loopback upstream만 지원한다. 전달 시 인증·쿠키·hop 헤더를 제거하고, 경로·query·본문·인증 값을 접근 로그에 남기지 않는다. 응답은 `no-store`, `nosniff`, `no-referrer`를 사용한다. 프록시가 의료적 수용이나 목적지를 결정하지 않는다.

upstream 업무 API 전달의 소켓 timeout은 35초다. 기존 음성 인식의 15초 대기보다 게이트웨이가 먼저 정상 응답을 끊지 않도록 분리했다. 이는 전체 작업의 엄밀한 wall-clock 제한을 보장하는 값은 아니다. 최초 upstream 상태 확인은 5초, 들어오는 HTTP 요청 소켓은 10초 설정을 유지한다.

```powershell
python -m unittest test_team_lan -v
```

시험은 새 합성 DB·일회성 인증서·loopback 포트에서 실제 CA/호스트명 검증, 인증 실패, Origin·본문 제한, 정적/JSON/쓰기 전달과 인증 제거, 잘못된 upstream 거절, 실제 공통 full 서버의 두 워커 연결을 확인한다. 이것은 휴대전화 마이크·OS 신뢰 설치·WiFi 방화벽의 실제 시험 결과와 구분한다. Windows에서 심볼릭 링크 생성 권한이 없으면 해당 생성 시험 하나는 생략될 수 있다.
