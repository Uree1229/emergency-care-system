# 이미 문의 중인 환자의 후속 문의 기회를 포함한 후보 평가

상태: 기존 240개 환경·827명에서는 사용자 목표를 통과했지만, 새 개발 120개 환경·415명에서는 개선이 재현되지 않아 개발 통과 조건을 충족하지 못했다. 두 단계의 공식 저장 감사는 모두 통과했으며 개발 단계에서 종료했다. 별도 검증 368개 환경은 실행하지 않았고 이번 후보는 채택하지 않는다.

## 요청과 고정 비교 기준

사용자 요청은 이전 후보 D의 CS 대비 순성공 2건 증가를 유지하면서, 선정 대기시간 합계의 1,516초 증가를 줄이는 것이다. 환자 우선순위와 성공 수를 먼저, 대기시간을 다음으로 판단한다는 기존 선택을 따른다. 과거에 성공했던 모든 환자의 개별 성공을 동시에 보존하는 것은 현재 자원 제약에서 불가능하다는 봉인된 검토 결과를 유지한다.

기존 관측 자료 240개 환경, 827명은 모두 이번 후보 개발 자료다.

| 기준 | 선정 성공 | 선정 실패 | 총 선정 대기시간 |
|---|---:|---:|---:|
| CS | 689명 | 138명 | 111,858초 |
| 이전 D | 691명 | 136명 | 113,374초 |

대기시간은 선정까지 걸린 시간이며, 선정하지 못한 환자는 실험 관측 한도 300초를 합계에 반영한다. 병원 도착시간이나 치료 시작시간을 의미하지 않는다.

새 후보의 기존 자료 통과 목표는 성공 691명 이상, 총 선정 대기시간 113,374초 미만이며, 12개 고정 비교군의 최선보다 우선순위·실패·대기 순서의 비교값이 좋아야 한다. 1,516초 증가를 완전히 없애야 한다는 조건은 두지 않았다. 최종 보고에는 CS 대비 남은 증가분과 이전 D 대비 줄어든 초를 모두 적는다.

이 목표에 맞춰 새 후보에서는 기존 자료의 출처별 최선 비교군 조건을 전체 자료의 사용자 목표로 대체했다. 각 출처·일반·스트레스·개별 성공 교환은 계속 별도로 보고한다. 이미 봉인된 이전 D의 기존 조건 미통과 결과를 변경하는 조치는 아니다.

## 변경한 계산

후보 이름은 `eat_cohort_hedge_l15_f`다. 이전 D의 최대 3개 문의안, 첫 문의 대상자와 참조 후속 문의 계산을 그대로 보존한다. 추가로 현재 등록되어 있고 관측 시간이 남아 있는 대기 환자를 빠짐없이 읽어, 기존 첫 문의 집합과 나머지 환자로 나누어 각 환자를 한 번씩 평가한다. 문의 이력이 있거나 이전에 새 문의를 보내지 않았던 환자도 포함한다.

이미 보낸 문의의 응답 분포는 원래 공개 기록으로 한 번 계산하여 모든 문의안에 공통으로 사용한다. 나중에 가상으로 추가한 문의가 이미 보낸 문의의 앞쪽 대기열에 들어간 것으로 계산하지 않는다.

나머지 환자는 다음 검토 시점 이후의 후속 문의 계획을 평가한다. 원래 시점의 관측과 대기열 잔여시간을 고정하고, 각 문의안의 현재 추가 문의를 반영한다. 각 계획 시점에서 기존 미응답 문의와 앞서 계획한 문의의 신선한 건수를 합쳐 최대 4건을 지킨다. 180초까지는 동시 문의에 포함하고, 신규 문의는 자동 문의 마감 A와 실험 관측 종료 H 이전에만 허용한다. 마감 이후에도 기존 문의의 늦은 회신 가능성은 H까지 남긴다.

기존 회신과 새 후속 문의의 생존확률을 한 번만 결합하고, 문의를 보낼 시점까지 수용 회신이 없을 확률로 문의 비용을 계산한다. 검토 시점이 격자에 맞지 않거나 마지막 구간이 짧아도 실제 시각을 사용한다.

이는 현재 정보로 계산하는 환자별 가상 후속 계획이다. 미래의 실제 회신을 알고 다시 계획하거나, 여러 환자의 미래 문의를 공통 예약하는 모델은 아니다. 미래 환자, 비공개 응답 정보, 정답용 오라클을 정책 입력에 사용하지 않는다. 실제 실행은 현재 두 환자의 문의만 적용하고, 이후에는 기존 H 실행 경로를 따른다.

수용 가능 응답이 현재 유효하면 성공확률 1·추가 대기 0으로 계산한다. 작업이 없거나 중지되었거나 새 문의 기한·예산이 끝났으면 기존 회신 가능성만 남긴다.

## 무결성과 검증 절차

정책과 별도로 작성한 감사 코드가 공개 입력에서 기존 D의 점수, 기존 문의의 응답 분포, 각 후속 계획, 성공확률과 대기 점수 및 최종 선택을 재계산한다. 전체 환자 목록과 각 환자의 우선순위·작업·문의·이벤트 원본은 같은 시점에서 읽고, 실제 두 문의를 쓰기 전에 다시 확인한다. 계산 도중 자료가 달라지거나 두 번째 적용이 실패하면 묶음 전체를 적용하지 않는다.

소스·조건을 고정한 뒤 기존 240개 환경을 한 번 실행하고 모든 결과를 저장한다. 기존 자료 목표를 통과해야 새 개발 120개 환경을 실행하고, 그 조건도 통과해야 별도의 검증 368개 환경을 실행한다. 새 자료에서는 최선 비교군보다 좋아야 하며, D 대비 실패 수 비증가와 총 대기 감소를 함께 요구한다. 검증에서는 10,000회 시나리오 단위 짝 부트스트랩의 주변 95% 구간 조건도 적용한다. 여러 지표·비교군을 동시에 보장하는 신뢰구간이라고 해석하지 않는다.

성능 실험의 환자 우선순위는 모두 기존 입력의 미확인·기본값 4다. 우선순위가 다양한 실제 임상 상황의 효과를 검증했다는 주장은 하지 않는다. 운영 기본 정책 변경이나 배포는 이 실험에 포함하지 않는다.

## 결과

동일한 240개 환경·827명의 저장 원문에서 집계한 값이다. 압축·원문 SHA를 확인하고 정책·모델·정답용 오라클을 실행하지 않은 별도 집계에서도 일치했다. 기존 자료의 공식 저장 감사와 보완 감사는 통과했다. 아래 개선이 새 자료에서도 재현되었다는 뜻은 아니다.

| 비교 | CS | 이전 D | 새 후보 |
|---|---:|---:|---:|
| 선정 성공 | 689명 | 691명 | 692명 |
| 선정 실패 | 138명 | 136명 | 135명 |
| 총 선정 대기시간 | 111,858초 | 113,374초 | 113,296초 |
| CS 대비 성공 순증 | — | +2명 | +3명 |
| CS 대비 총 대기 증가 | — | +1,516초 | +1,438초 |

이전 증가분에서 **78초(약 5.1%)**를 줄였다. D 대비 기존 성공 손실은 없고 새 성공 1명이 추가되었다. 대기시간이 줄어든 환자는 2명, 늘어난 환자는 0명이다. 기존 6명의 복구 사례와 D에서 새로 성공했던 3명은 모두 유지했다. CS에서 성공했으나 D에서 실패했던 1명은 이번에도 실패하여, CS의 개별 성공을 모두 보존한 결과는 아니다.

78초의 구성은 원 repair 065/P06의 선정 93→86초(7초)와 원 development 083/P01의 선정 실패→229초 선정(실패의 300초 반영값 대비 71초)이다. 두 경우 외 825명의 대기값은 D와 같다. 전체 113개 실제 묶음 중 D에서 다른 문의안을 선택한 것은 2개다.

선정 대기에서의 비악화가 도착시간의 비악화를 뜻하지는 않는다. D 대비 실패를 1,800초로 반영한 도착 비용 J의 평균은 약 1.016초 줄었지만, 개인별 최대 도착 비용 증가 95초가 있다. 또한 CS 대비 선정 대기가 늘어난 환자는 35명이고 개인별 최대 증가는 117초다. 위의 악화 0명은 D 대비 선정 대기만을 뜻한다.

일반 상황 695명은 D 대비 실패 130→129명, 총 대기 101,032→100,954초다. 스트레스 상황 132명은 실패 6명·총 대기 12,342초로 D와 같으며, CS 대비 스트레스 대기 증가 1,721초는 그대로 남는다. 원래 복구 후보 7명은 4→5명 성공했고, 과거 새 성공 후보 4명 중 2명만 성공하는 상태는 유지됐다. 이는 개별 성공 대상의 전원 보존을 주장한 결과가 아니다.

## 새 개발 자료 결과

기존 827명과 분리한 새 자료 120개 환경·415명이다. 일반 96개 환경·349명과 스트레스 24개 환경·66명으로 구성한다. 13개 비교 정책을 모두 한 번씩 실행한 1,560개 분기를 저장했고, 결과를 제외하거나 다시 실행하지 않았다. 저장 원문의 해시·입력 명세·비교 정책별 환자 집합을 확인한 독립 집계 값이며, 120개 환경 전체의 공식 저장 감사도 통과했다.

| 새 자료 비교 | CS | 이전 D | 새 후보 | 최선 비교군 B |
|---|---:|---:|---:|---:|
| 선정 성공 | 364명 | 363명 | 363명 | 367명 |

새 후보는 D와 415명 모두의 선정 성공·실패 및 대기시간이 같았다. D 대비 성공 손실·추가 성공·대기 증감은 모두 0이다. 이 비교가 모든 실제 문의안이나 전체 원문까지 같다는 뜻은 아니다. CS와 비교하면 성공 1명 감소·총 대기 1,261초 증가이며, 최선 비교군 B와 비교하면 성공 4명 감소·총 대기 874초 증가다.

새 후보 분기의 저장 감사에서 공동 판단 묶음 67개, 추가 평가 대상 문의안 집합 12개를 확인했으나, 이번 추가 후속 계산이 D의 선택을 바꾼 개입은 0건이었다. 후속 계산이 실제로 실행됐다는 사실과 선택·성과 개선이 나타났다는 주장은 구분한다.

|---|---:|---:|---:|---:|
| 일반 | 349명 | 300명 | 49명 | 48,629초 |

사전에 고정한 개발 조건 중 D 대비 실패 비증가는 통과했지만, D 대비 총 대기 감소와 최선 비교군 대비 우선순위·실패·대기 개선은 실패했다. 따라서 새 자료에서도 CS 대비 성공 증가가 유지되었다고 주장할 수 없다. 기존 자료 827명의 성공 +3명·78초 단축과 이번 415명의 미재현을 합산해 성과를 포장하지 않는다.

후속 검증 368개 환경으로 진행하지 않고 개발 단계에서 종료한다. 정책·가중치·통과 조건·난수 네임스페이스는 결과를 보고 다시 조정하지 않았다. 운영 기본 정책 `fixed_3`와 실행 서버는 변경하지 않았다.

## 저장 감사 전용 보완과 보존 경계

첫 정식 실행은 240개 결과를 모두 저장했으나, 원 감사 코드가 공개 이력으로 실제 등록된 환자를 `scenario.patients`에 없다는 이유로 거부했다. 첫 사례는 원문 026의 `HIST_H08_3`이다. 이 환자는 동결된 데이터베이스 생성 코드에 따라 공개 history에서 생성되었고, 현재 WAITING·작업 없음·관측 시간 잔여 상태이므로 전체 대기 환자 목록에 포함되는 것이 맞다.

알고리즘·원래 434개 소스·240개 결과·조건·네임스페이스를 그대로 보존한다. 먼저 별도 소스 4개로 공개 history·생성 사건·전체 현재 snapshot·기존 데이터 생성 규칙을 확인하는 감사를 추가했다. 이어 기존 감사의 `math.prod([])`가 만드는 정수 P=0/F=1과 계산 코드의 실수 0.0/1.0을 다르게 취급하는 형식 오류를 발견해, 값과 허용오차를 바꾸지 않는 별도 보완 소스 4개를 추가했다. 원래 438개 파일도 변경하지 않고 총 442개 소스를 결속했다.

두 번째 보완은 기존 240개 후보 기록 전체의 독립 감사를 통과한 뒤, 새 자료의 성능 실행 전에 고정했다. 알려진 결과를 본 뒤 감사의 잘못된 전제를 수정한 절차이며, 처음 434개 감사가 완전히 사전 등록된 상태로 통과했다고 주장하지 않는다. 일반적인 외부·중첩 반복 history 입력 전체가 아닌 현재 고정된 생성기와 실험 입력 범위의 검증이다.

보완 절차는 저장 결과를 다시 검사하며 시뮬레이션을 재실행하지 않는다. 원 감사의 434개 소스 표시는 기본 소스 범위로 보존하고, 필수 보완 단계 기록과 최종 합성 기록에서 전체 442개 소스를 결속한다. 기존 검사 637개와 보완 검사 23개가 통과했다. 복구 처리시간은 원래 성능 실행시간과 구분한다.

## 종료 기록

기존 240개·새 개발 120개 환경의 실행 및 저장 감사 보완 기록을 각각 보존했다. 실제 새 성능 실행은 기존 후보 240개 분기와 새 개발 1,560개 분기의 합계 1,800개다. 새 원문은 360개이며, 기존 비교를 위해 읽은 원문 1,320개·2,880개 분기는 별도 캐시 범위다. 감사 보완용 성능 재실행과 결과 제외는 모두 0이다.

고정된 복구 드라이버에 `validation`을 요청했을 때, 실제 개발 통과 조건에서 멈추는지 별도 진단으로 확인했다. 실행 함수·프로세스 풀·시뮬레이션 작업은 모두 호출 0회이고, 검증 결과 폴더와 파일은 생성되지 않았다. 근거는 `diagnosis/validation-gate-blocked.json`이다. 이는 후속 단계의 사전 차단을 확인한 것이며 별도 검증 성능을 측정했다는 뜻은 아니다.

최종 수치 회계·해시 결속은 `.codex-build/eat-cohort-hedge-20261021/verification.json`의 기본 434개 소스 기록과 `verification-with-audit-addendum-v2.json`의 보완 포함 442개 소스 기록으로 구분한다. 이 기록의 무결성 통과와 후보의 성능 통과는 다른 판단이다. 이번 후보의 성능 판단은 새 개발 조건 미달·미채택이다.
