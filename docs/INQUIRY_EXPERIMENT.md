# 서버 문의 정책 비교 — 2026-10-12

후속 개선은 [V3 개발 선택과 별도 seed 검증](INQUIRY_V3_EXPERIMENT.md)에 정리했다. 아래는 V2까지의 당시 결과이며, 여기서 사용한 seed 6101~6108은 후속 실험의 개발 자료로 분류했다. 기존 보고서와 원시 기록은 보존했다.

고정 1·3·5곳 문의와 관측 기반 V2를 실제 `server/inquiry_workflow.py`로 비교했다. **정책마다 유리한 조건이 다르며, 현재 V2를 범용 우수 정책으로 결론 내릴 수 없다.**

[전체 결과 표](../simulation_results/server_inquiry_comparison_20261012.md), [환자별 결과·환경·사건 JSON](../simulation_results/server_inquiry_comparison_20261012.json), [독립 감사](../simulation_results/server_inquiry_comparison_20261012_audit.json).

## 이번 결과

8개 유형 × 미사용 seed 6101~6108 = 64개 시나리오, 정책 4종 = 256개 분기다. 각 정책에서 같은 가상 환자 176명을 평가했다. 정책 설정은 결과를 보고 변경하지 않았다.

| 정책 | 300초 내 선정 | 선정 성공자의 평균(초) | 실패를 300초로 포함한 대기 평균(초) | 문의/환자 |
|---|---:|---:|---:|---:|
| 고정 1곳 | 149/176 | 135.77 | 160.97 | 3.26 |
| 고정 3곳 | 152/176 | 110.78 | 136.58 | 6.17 |
| 고정 5곳 | 153/176 | 102.90 | 128.66 | 6.96 |
| 관측 V2 | 159/176 | 83.79 | 104.68 | 1.62 |

평균 성공자의 구성이 다르므로 위 두 선정시간 평균을 그대로 개선율로 만들지 않는다. 고정3과 V2가 **함께 선정한 143명**에서 V2는 선정이 평균 33.26초 빨랐고, 선정 경과시간+합성 이동시간은 51.85초 짧았다. V2만 선정한 환자는 16명, 고정3만 선정한 환자는 9명, 둘 다 선정하지 못한 환자는 8명이다.

그러나 전체 환자 중 128명(72.7%)은 동시·순차 다수 환자 조건이다. 8개 유형을 같은 비중으로 평가하면 다음과 같다.

| 정책 | 유형별 성공률 평균 | 유형별 300초 제한 대기 평균(초) | 유형별 문의/환자 평균 |
|---|---:|---:|---:|
| 고정 1곳 | 83.79% | 132.13 | 3.09 |
| 고정 3곳 | 84.38% | 95.83 | 4.96 |
| 고정 5곳 | 84.57% | 85.80 | 6.00 |
| 관측 V2 | 74.80% | 137.06 | 2.28 |

**문의 감소는 확인했지만, 조건 전반의 선정시간과 실패 방어는 부족하다.** 전체 환자 가중 평균과 유형 균등 평균 모두 실제 지역의 발생 분포를 반영한 수치는 아니다.

## 효과가 있거나 부족했던 조건

- 동시 환자 8명·병원별 처리자 1명: 고정3은 48/64명, V2는 64/64명을 선정했다. 공통 선정 환자의 선정시간은 V2가 87.73초 짧고 문의는 7.09→1.14건/환자였다. 문의가 큐에 몰리는 합성 조건에서 분산의 효과가 나타났다.
- 가까운 두 병원이 계속 무응답: 고정3은 8/8명, V2는 0/8명을 선정했다. V2가 두 번째 병원에 180~195초에 문의하면서 300초 안에 세 번째 후보까지 도달하지 못했다. 전산 오류가 아닌 현재 대기 규칙의 실패다.
- 과거에 빨랐던 병원이 현재는 느림: 모두 선정됐지만 V2의 선정은 고정3보다 평균 131.13초 늦었다. 과거 관측을 오래 신뢰하는 위험이 드러났다.
- 가까운 병원은 느리고 조금 먼 병원은 빠름: V2는 문의를 줄였지만 선정이 고정3보다 128.25초 늦었다. 가까운 병원을 기다리는 비용과 빠른 확정의 균형이 필요하다.
- 모든 병원이 수용 불가: 네 정책 모두 0/8명이다. 알고리즘은 수용 자원을 만들지 못한다.

## 비교를 공정하게 만든 방식

1. 병원·운영 자원·과거 문의 사건만 있는 초기 SQLite DB를 만들고 정책별 독립 복제본을 사용했다. 각 분기의 논리 SQL 스냅샷 해시가 같다.
2. 환자·병원 쌍마다 검토시간·무응답 여부·수용 여부를 실행 전에 생성해 모든 정책이 공유한다. 문의 순서나 정책 이름으로 난수를 다시 뽑지 않는다. 미래 결과는 정책에 제공하지 않는다.
3. 정책은 실제 서버의 후보 필터, 문의 작업, 유효성 검사, 사건 기반 관측을 사용한다. 합성 검토 인원·큐·잠재 응답은 실험 실행기만 읽는다.
4. 병원별 FIFO 큐에서 문의를 처리한다. 취소된 미착수 문의는 제거하고, 착수한 문의는 취소돼도 정해진 업무시간을 끝까지 소비한다. 문의 수와 실제 착수 수·업무시간을 따로 기록한다.
5. 같은 초에 끝난 응답을 모두 반영한 뒤 유효한 수용 응답 중 이동시간·병원 ID 순으로 동일하게 확정한다. 실험자의 지연 없는 사람 확정 모사이며 운영 서버에 자동 확정 기능을 추가한 것이 아니다.
6. 환자 발생 후 300초까지 관측한다. 자동 문의 작업이 EXHAUSTED여도 기존 문의의 기한 내 회신은 인정한다. 정확히 300초 회신은 성공, 이후 회신은 실패 집계 후 억제한다. 실패자의 시간은 0으로 넣지 않는다.
7. 시각은 다음 사건까지 건너뛰지만, 작은 사례에서 1초 폴링과 결과가 같은지 검증했다. 정책 실행 순서를 바꿔도 결과가 같다. 실행 전후 소스 해시도 비교한다.

## 무엇까지 검증했는가

이번 결과는 **서버에 연결한 문의 대상·묶음 규모·추가 문의 대기 규칙의 합성 환경 성능**이다. 현행 119의 실제 코드나 전화 업무를 재현하지 않았다. 공식 병원 선정 평균 18분을 개별 병원의 응답시간으로 사용하지 않았다.

병원 자원을 충분히 두어 문의 부하를 분리했다. 실제 의료진·병상 부족, 환자별 임상 조건, 이송 중 상태 변화·재배정, CP-SAT와의 비교, 실제 이동 및 치료 결과는 검증하지 않았다. 기본 시연의 소아 2기관에 제한하지 않고, 충분한 후보 8곳을 갖는 합성 일반 응급 조건을 사용했다.

## 다음 개선 실험

이번 seed 6101~6108은 이미 결과를 확인한 개발 자료로 취급한다. 이 결과를 보고 정책을 수정한 뒤 같은 자료에서 얻은 수치를 독립 검증 성과로 발표하면 안 된다.

- 무응답이 누적될 때 다음 후보 확인이 180초 이상 늦어지는 현상을 줄이는 상한 규칙을 비교한다.
- 오래된 과거 회신의 영향과 현재 응답이 달라지는 경우를 고려해 시간 가중치·변화 감지를 비교한다.
- 문의 최소화만 최적화하지 않고, 300초 내 미선정 수·최장 대기·문의 업무량을 함께 평가한다.
- 설정 후보를 개발 자료에서 고정한 뒤 아직 사용하지 않은 seed에서 확인한다. 변경 전 V2와 고정1·3·5를 계속 비교군으로 남긴다.
- 이후 실제 도로 입력과 치료조건·자원 경합을 확장하고, 이송 중 변경 사건을 지도 시뮬레이션과 연결한다.

## 실행

```powershell
python -m server.inquiry_experiment --output simulation_results/server_inquiry_comparison_new
python -m server.inquiry_experiment_audit simulation_results/server_inquiry_comparison_new.json --output simulation_results/server_inquiry_comparison_new_audit.json
python scripts/test_suites.py python test_server_inquiry_experiment -v
```

기존 결과 파일이 있으면 실행기가 덮어쓰기를 거부한다. 임시 DB만 사용하며 운영·시연 DB와 외부 API에는 접근하지 않는다. 구현은 `server/inquiry_experiment.py`, 입력 생성은 `server/inquiry_experiment_scenarios.py`다. 이 신규 비교 테스트 17개와 기존 회귀를 포함한 154개가 통과했다.
