# 외부 유입 환자 등록·조회·퇴실

기준: 2026-10-14. 서버 구현과 격리 DB 검증이며 실제 의료기관 연결은 없다.

이송 앱을 거치지 않고 내원한 환자의 자원 사용을 개별 기록한다. 기존에는 등록 때 실제 점유를 늘린 뒤 담당자가 합계를 직접 수정해야 했다. 이제 등록된 기록을 퇴실 처리해 그 기록이 실제 반영한 수량만 한 번 해제할 수 있다. 환자용 웹·병원용 웹의 디자인은 변경하지 않았다.

## API

| 동작 | 경로 | 응답 |
|---|---|---|
| 등록 | `POST /api/hospitals/{hid}/external-arrivals` | `external_arrival_id`, `external_arrival`, `duplicate`, `affected`, `hospital` |
| 목록 | `GET /api/hospitals/{hid}/external-arrivals` | `external_arrivals`, `next_before_id` |
| 상세 | `GET /api/hospitals/{hid}/external-arrivals/{id}` | `external_arrival` |
| 퇴실 | `POST /api/hospitals/{hid}/external-arrivals/{id}/discharge` | 등록과 같은 응답 구조 |

등록 예시:

```json
{
  "request_id": "4963dcb3-f8e7-45a5-9b6e-1cbfdcfa9109",
  "resource_demands": {"ed_bed": 1, "special_team": 1},
  "note": "시연: 시스템 밖 직접 내원",
  "handled_by": "시연 병원 담당자"
}
```

`occurred_at`은 선택적인 UTC epoch 초 정수다. 생략하면 최초 등록 시각을 저장하며, 재전송 시각으로 바꾸지 않는다. `note`는 null 또는 2,000자 이하 문자열, `handled_by`는 1~80자, `request_id`는 1~128자다. 자원 키는 앞뒤 공백이 없는 1~100자 이름, 수량은 양의 정수다. 임상 분류나 실제 환자 개인정보를 새로 추정하지 않는다.

목록은 기본 `state=ACTIVE`, `limit=100`이며 `ACTIVE`, `DISCHARGED`, `LEGACY`, `RECONCILED`, `all`을 지원한다. `limit`은 1~200이다. 최신 ID부터 반환하며 다음 페이지가 있으면 `next_before_id`를 `before_id`로 보낸다. 조회는 기록과 자원·이력을 변경하지 않는다. 병원 경로와 기록의 소속이 다르면 404다. 병원 ID를 쓰는 기존 시연 계약이며 사용자 인증을 대신하지 않는다.

퇴실 예시:

```json
{"expected_version": 1, "handled_by": "시연 병원 담당자"}
```

정상 처리 후 기록은 다음처럼 바뀐다. 아래는 구조를 보여 주는 예시다.

```json
{
  "external_arrival_id": 12,
  "duplicate": false,
  "external_arrival": {
    "id": 12,
    "hospital_id": "H1",
    "state": "DISCHARGED",
    "version": 2,
    "resource_demands": {"ed_bed": 1, "special_team": 1},
    "applied_resource_demands": {"ed_bed": 1},
    "registered_by": "시연 병원 담당자",
    "discharged_by": "시연 병원 담당자"
  }
}
```

실제 응답에는 발생·관측·퇴실 시각, 메모와 요청 ID, 현재 영향 환자와 병원 상세도 포함된다. 내부 요청 비교값과 자원 집계 기준은 API에 노출하지 않는다. 무차감 종결한 기록에는 감사 ID와 처리시각·담당자도 포함된다.

## 중복과 자원 처리

- 프런트엔드는 새 등록을 시작할 때 `request_id`를 한 번 생성하고 네트워크 재시도에도 같은 값을 쓴다. 성공 응답을 받기 전 새 키를 만들면 안 된다. 기존 화면과 호환하도록 키 생략을 허용하므로, 키가 없으면 매 호출이 별개 유입이다.
- 같은 병원·요청 ID·내용으로 재전송하면 기존 기록과 `duplicate: true`를 반환한다. 처리자와 관측 시각은 비교 대상이 아니며 자원·이력·버전을 다시 변경하지 않는다. 퇴실 또는 무차감 종결 후 등록을 재전송해도 다시 점유하지 않는다. 손상된 원장 JSON은 조회에서 null과 `data_errors`로 표시하며 원문은 보존한다. 내용이 달라지면 `409 CONFLICT`다.
- 새 기록은 `ACTIVE → DISCHARGED`로 한 번만 바뀐다. 이미 퇴실한 건은 최초 버전으로 재시도해도 `duplicate: true`다. 활성 기록의 버전이 다르면 `409 CONFLICT`다.
- `resource_demands`는 입력된 요구, `applied_resource_demands`는 실제 운영 자원에 반영한 요구다. 등록 당시 없는 자원을 만들거나 공개 가용병상 수를 운영 총량으로 바꾸지 않는다. 나중에 그 자원이 생겨도 이 기록의 퇴실 때 차감하지 않는다. 기존 자원의 상태가 `unknown`이면 점유만 기록하고 수용 가능 판정은 계속 미확인으로 둔다.
- 등록 때 초과 점유는 실제 발생 사실로 기록한다. 퇴실은 모든 자원을 먼저 검사하며 하나라도 집계가 불일치하면 상태·수량·이력 전체를 취소한다. 같은 집계 세대의 활성 외부 유입 합계보다 현재 점유가 적을 때도 차감하지 않는다.
- 담당자가 운영 자원의 `occupied` 합계를 수동 변경하면 이전 기록의 자동 차감은 `409 RESOURCE_CONFLICT`로 막는다. 이미 수동 정산한 수량을 다시 빼지 않기 위해서다. 합계를 바꾸지 않은 용량·상태 수정은 개별 퇴실을 막지 않는다. 담당자가 이미 정산했음을 확인하면 [무차감 종결 API](ACCOUNTING_RECONCILIATION.md)로 `RECONCILED` 상태로 종료할 수 있다. 정상 퇴실 실패 후 자동 호출하지 않는다. 외부 유입을 퇴실시키려면 정상적으로는 합계를 직접 수정하지 말고 이 API를 사용한다.
- 기존 DB의 과거 유입 기록은 삭제하지 않고 `LEGACY`로 보존한다. 과거에 수동 정산했는지 알 수 없으므로 자동 차감하지 않는다.

등록과 퇴실은 병원 자원 변경에 따른 환자별 조건을 같은 트랜잭션에서 재평가한다. 자원 회복으로 재확인 위험이 사라질 수 있지만 목적지를 자동으로 바꾸지는 않는다. 이미 진행 중인 대체 문의와 병원 판단도 기존 상태 규칙을 따른다.

2026-10-14 일반 도착 환자의 정산도 같은 검사에 연결했다. 외부 유입을 퇴실할 때 일반 도착 환자의 같은 집계 기준 수요까지 보호하고, 일반 환자 퇴실 때도 활성 외부 유입의 점유를 보호한다. [공통 정산과 과거 도착 기록](RESOURCE_ACCOUNTING.md).

## 병원 웹 담당자의 후속 연결

1. 돌발 유입 등록에 고정 `request_id`를 넣고 전송 중 중복 클릭을 막는다.
2. 활성 기록 목록에 발생 시각·자원 요구·실제 반영 수량·메모를 표시한다.
3. 퇴실 시 조회한 `version`을 보내고 성공 후 목록·자원·도착 예정 환자를 다시 조회한다.
4. 409를 자동 재시도로 숨기지 말고 서버 설명과 재조회 선택을 표시한다. `LEGACY`에는 자동 퇴실 버튼을 제공하지 않는다.
5. 퇴실 이력은 `state=DISCHARGED`로 조회한다. 공공 관측 정보와 실제 운영 자원 합계를 구분한다.

## 검증

`python -m unittest test_external_arrivals -v`로 격리된 임시 DB와 로컬 HTTP 서버에서 확인한다. 신규 테스트 26개는 등록·퇴실 재전송, 두 연결의 동시 요청, 병원별 범위·페이지 조회, 읽기 전용 조회, 과거 DB 반복 마이그레이션, 누락·미확인 자원, 수동 보정·수량 부족 시 전체 취소, 조건 회복 후 목적지 유지를 포함한다. 현재 서울 시연 DB를 초기화하거나 실제 병원에 요청하지 않는다.

기존 문의·채팅·조건 재확인·대체 문의·공공 데이터·팀원 입력 앱 연결·조건 변경 지도 재생을 포함한 회귀 테스트 총 574개가 통과했다. 이번 결과는 기능 검증이며 배정 알고리즘의 현장 성능 개선 수치를 뜻하지 않는다.
