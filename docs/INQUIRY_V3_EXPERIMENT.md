# V3 문의 정책 개선과 별도 데이터 검증

2026-10-12. V2의 무응답 대기와 오래된 회신 이력 의존을 개선했다. 개발에서 선택한 **추가 문의 대기 상한 45초·과거 회신 범위 15분**을 고정한 뒤 별도 seed로 평가했다. 합성 환경에서 실패 방어와 문의 수의 균형은 개선됐지만, 모든 조건에서 가장 빠른 정책은 아니다.

[개발 결과](../simulation_results/server_inquiry_v3_development_20261012.md), [검증 결과](../simulation_results/server_inquiry_v3_validation_20261012.md), [검증 원시 기록](../simulation_results/server_inquiry_v3_validation_20261012.json).

## 무엇을 바꿨는가

| 이전 V2의 실패 | V3의 변경 | 보존한 규칙 |
|---|---|---|
| 비용이 유리한 후보가 없으면 무응답 병원을 오래 기다림 | 최근 문의 이후 대기 상한에 도달하면 다음 후보 1곳에 추가 문의 | 첫 1곳, 15초 재평가, 대기 선택지 최대 3곳 |
| 20~25분 전 빠른 병원을 현재도 유리하게 평가 | 회신 관측을 최근 10분 또는 15분으로 제한 | 미래 사건은 사용하지 않음, 표본 부족 시 사전값 |
| 닫힌 문의를 제외하면 오래된 미응답을 기준으로 연속 확장할 위험 | 닫힌 문의도 포함해 가장 최근 전송 시각으로 추가 문의 간격 계산 | 실제 무응답은 거절·취소로 바꾸지 않음 |

상한 도달만으로 무조건 전송하는 것은 아니다. 유효한 수용 응답이 없고 대기 선택지가 3곳 미만이며 미문의 후보와 연락 한도가 남아 있을 때, 15초 재평가에서 추가한다. 기존 V2의 유리한 후보 추가 규칙도 유지한다. 180초가 지난 문의는 환자 자신의 대기 선택지에서 제외할 수 있지만 전역 미해결 업무량에는 남긴다. 전체 한도는 10곳·300초다. 모두 개발용 설정이다.

## 개발에서 선택하고 검증에서는 바꾸지 않았다

1. 사전 후보: 대기 상한 45·60·90초 × 회신 이력 600·900초, 총 6개.
2. 개발: 이전에 확인한 seed 6101~6108과 같은 8개 유형, 64시나리오. 기존 4개 정책과 후보 6개로 640분기를 실행했다.
3. 선택: 유형별 비중을 같게 두고 **실패율 → 실패를 300초로 포함한 대기 → 문의 수** 순으로 비교했다. 동률이면 정책 이름으로 고정했다. 선택 결과는 `v3_w45_h900`이다.
4. 잠금: 개발 보고서 해시·정책 전체 설정·기준 정책 설정·11개 소스 지문·개발 seed를 [잠금 파일](../simulation_results/server_inquiry_v3_development_20261012_lock.json)에 저장했다.
5. 검증: 잠금 파일을 먼저 검사하고 미사용 seed 7101~7112, 같은 생성기의 8개 유형에서 96시나리오×5정책=480분기를 실행했다. 정책당 동일 환자 264명이다. 결과를 본 뒤 설정을 다시 고르지 않았다.

기존 고정1·3·5·V2의 개발 256분기는 이전 보고서와 전체 명세·DB 스냅샷·환경·환자 결과·지표·판단·원시 사건이 완전히 같았다. 개선 코드를 추가하면서 비교군의 동작을 바꾸지 않았음을 확인했다. 소스 파일 자체는 개선 코드를 포함하므로 이전 보고서와 지문이 다르며, 이전 감사 보고서는 당시 기록으로 보존했다.

## 검증 결과

전체 환자의 72.7%가 두 다수 환자 유형에 속하므로, 전체 환자 집계와 유형 균등 집계를 함께 봐야 한다. 아래는 **8개 유형을 같은 비중으로 평가한 결과**다. 제한 대기는 실패 환자를 300초로 포함한다.

| 정책 | 유형별 성공률 평균 | 제한 대기 평균(초) | 문의/환자 평균 |
|---|---:|---:|---:|
| 고정 1곳 | 83.59% | 132.39 | 3.08 |
| 고정 3곳 | 84.51% | 94.79 | 4.95 |
| 고정 5곳 | 84.51% | 85.25 | 6.00 |
| V2 | 74.87% | 135.90 | 2.24 |
| V3 | 87.50% | 87.07 | 2.57 |

V3는 고정3 대비 유형 균등 제한 대기를 **8.14%**, 문의를 **47.99%** 줄였다. 고정5의 제한 대기는 V3보다 1.82초 짧았다. V3의 문의 수는 V2보다 **14.88% 많았다**. 선정 실패를 줄이기 위해 추가 문의를 사용하는 절충이다.

전체 264명 기준으로는 고정3 229명, V2 239명, V3 252명이 300초 안에 선정됐다. 고정3과 V3 모두 선정된 229명에서 V3의 선정은 평균 **37.08초**, 선정시간+합성 이동시간은 **56.09초** 빨랐다. V3만 선정된 환자는 23명, 고정3만 선정된 환자는 0명, 둘 다 실패한 환자는 12명이다.

V2와 V3 모두 선정된 239명에서는 선정이 평균 **12.91초**, 예상 도착이 **6.09초** 빨랐다. V3만 선정된 환자는 13명, V2만 선정된 환자는 0명이다. 다만 이 239명 중 26명은 V3의 선정이 더 늦었으며 최대 지연은 108초였다. 평균 개선이 모든 환자의 개선을 뜻하지 않는다.

전체 환자 기준 문의는 고정3 **6.125→2.398건/환자**지만, V2 **1.587→2.398건/환자**로 늘었다. 착수한 합성 검토 업무시간도 고정3 **325.79→124.77초/환자**, V2 **101.83→124.77초/환자**였다. 이는 모의 검토 작업량이며 병원의 실제 업무시간 감소율이 아니다.

## 구현과 검증 증거

- 정책: [inquiry_v3.py](../server/inquiry_v3.py), [순수 계산 계약](../server/inquiry_policies.py), [서버 워크플로](../server/inquiry_workflow.py).
- 실험: [개발·검증 실행기](../server/inquiry_v3_experiment.py), [독립 감사](../server/inquiry_experiment_audit.py).
- 공개 API와 시연 선택창에 `observed_v3`를 연결했다. 실제 설정은 [선택 파일](../config/inquiry_v3_selected.json)로 고정하며 서버 시작 때 읽는다. 기본 정책은 계속 `fixed_3`다.
- 관련 전체 회귀 **176개 통과**. 선택 파일 적용 후 V3 22개 재검증도 통과했다. 상한 경계·닫힌 문의 이후 간격·최대 동시 대기·과거/미래 이력·늦은 수용·설정 불일치의 원자성·개발/검증 분리·잠금 변조를 확인했다.
- 실제 Chrome에서 PC 1440px·모바일 390px의 정책 선택·최초 1곳·설명·새로고침 복원·사람 확정 대기를 확인했다. 가로 넘침·브라우저 오류·QA 정리 실패가 없었다. 로컬 증거는 `.codex-build/inquiry-v3/`에 보관한다.
- [개발 감사](../simulation_results/server_inquiry_v3_development_20261012_audit.json) **166,479개**, [검증 감사](../simulation_results/server_inquiry_v3_validation_20261012_audit.json) **153,725개** 검사 통과. 원시 기록·FIFO·분모·선택·해시·소스 지문을 독립 재집계했다. 초기 SQL 원문은 산출물에 없어 스냅샷은 기록된 해시의 일치까지 검사했다.

## 해석 범위와 다음 작업

이 결과는 실제 서버 문의 코드를 **합성 병원·환자·회신·이동시간·검토 인원**에서 실행한 것이다. 현행 119 체계의 복제, 실제 응답률 개선, 임상 효과, 최적성 증명이 아니다. 검증은 같은 8개 유형의 새 seed이며 새로운 유형이나 실제 지역으로의 일반화를 증명하지 않는다. 자원 부족, 이송 중 조건 변경과 재배정, CP-SAT 비교는 이번 실험에 포함하지 않았다. 수용과 목적지는 사람이 확정하며, 실험에서는 모든 정책에 같은 지연 없는 확정 규칙을 적용했다.

서버 실험의 원시 문의·회신·선정 이력은 [지도 재생](SERVER_REPLAY.md)에 연결했다. 유형별 첫seed8사례를 결과와 무관하게 선택해 좋은 결과와 느린 반례를 모두 보여준다. 기존 지도 사례와 서버 기록의 범위는 구분한다. 다음에는 새로운 개발 자료에서 첫 문의 규모와 대기 정책을 개선하고, 담당 인원·이력 변화 속도·정보 누락을 바꾼 새 조건으로 다시 고정 검증한다. 이번 검증 seed를 다음 개선의 독립 검증으로 재사용하지 않는다.
