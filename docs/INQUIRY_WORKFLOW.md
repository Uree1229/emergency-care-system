# 초기 병원 자동 문의

2026-10-12 구현. 환자정보 제출 후 서버가 후보를 골라 문의하고, 회신·경과시간에 따라 다음 후보를 확인한다. 고정 1·3·5곳, 관측 기반 V2, 대기 상한과 최근 이력 범위를 추가한 V3를 선택할 수 있다. 운영 서버에서 개선 효과가 검증됐다는 뜻은 아니다.

## 화면 연결

환자 생성 `POST /api/patients` 본문에 `"auto_inquiry": true`를 추가한다. `"inquiry_policy": "observed_v2"`로 정책을 지정하며 생략하면 `fixed_3`다. 자동 문의를 생략하거나 false면 수동 문의를 유지한다. false와 정책을 함께 지정하면 해당 정책의 PAUSED 작업을 저장한다. 위치와 환자별 치료 요구는 기존 입력 형식을 사용한다. 서버 재시작 후에도 활성 작업은 DB에서 복구된다.

| 동작 | 경로·본문 | 응답 |
|---|---|---|
| 초기 자동 문의 활성화 | 환자 생성 본문에 `auto_inquiry: true` | 환자 상세의 `inquiry_workflow` |
| 정책 목록 | `GET /api/inquiry-policies` | 정책 이름·버전·개발 설정 |
| 조회 | `GET /api/patients/{pid}/inquiry-workflow` | 아래 작업 메타데이터 |
| 시작·재개 | `POST /api/patients/{pid}/inquiry-workflow`, `{"enabled":true,"policy_name":"observed_v2"}` | 작업 메타데이터, 정책명 생략 가능 |
| 일시정지 | 같은 POST, `{"enabled":false}` | 작업 메타데이터 |
| 판단 이력 | `GET /api/patients/{pid}/inquiry-decisions?limit=20` | 최신순 결정 목록, limit 1~100 |

환자 상세 GET에도 `inquiry_workflow`가 포함된다. 자동 문의를 만든 적이 없으면 `state: NOT_STARTED`, `enabled: false`다. 조회 요청은 문의를 보내지 않는다. 독립 백그라운드 워커가 기본 1초 주기로 실행한다.

주요 필드: `enabled`, `state`, `round_no`, `contacted_count`, `contacted_hospital_ids`, `pending_count`, `valid_accepted_inquiry_ids`, `next_evaluation_at`, `deadline_at`, `stop_reason`, `last_error`, `policy`, `latest_decision`. 시각은 UTC epoch 초다. NOT_STARTED에는 아직 저장된 작업 시각이 없다.

정책 이름·버전·전체 명세를 작업에 저장한다. 실행 중 다른 정책으로 바꾸면 409이며, 먼저 일시정지하고 WAITING 상태에서 전환해야 한다. 같은 정책의 반복 시작은 제한시간을 연장하지 않는다. 저장된 버전·명세와 현재 코드가 다르면 상태를 바꾸기 전에 409로 거부한다. 정책 전환 후에도 기존 문의는 보존한다. 한 사례의 정책을 도중에 바꾼 결과는 독립 정책 비교 실험이 아니다.

## 현재 규칙

1. 필요한 진료 분야와 활성 수용 제한으로 후보를 거른다. 신선한 운영 자원 정보에서 부족이 확인된 병원에는 자동 문의하지 않는다. 미확인·오래된 정보는 확인 대상으로 남긴다. 공공 API 관측값을 수용 확답이나 운영 자원 총량으로 쓰지 않는다.
2. 고정 정책은 기존 후보 정렬인 운영 자원 충족 여부와 예상 이동시간 순서를 사용해 미문의 병원 최대 1·3·5곳에 보낸다. 관측 기반 정책은 아래 비용 계산으로 후보를 고른다. 아직 문의하지 않은 모든 적합 후보가 탐색 대상이며, 별도의 10→20km 반경 정책은 이번 단계에 넣지 않았다.
3. 유효한 수용 응답이 있으면 추가 문의를 멈추고 `AWAITING_CONFIRMATION`으로 둔다. 유효성은 만료·환자 정보 버전·진료 제한·운영 자원 충돌로 확인한다. 수용 응답의 유효성이 사라지면 남은 탐색 시간 안에서 재평가한다.
4. 고정 정책은 응답이 없으면 60초 후 다음 후보를 확인한다. 진행 중인 문의가 모두 끝나면 60초 전에도 다음 묶음을 보낸다. 관측 기반 정책의 재평가 주기는 15초다. 기존 미응답은 PENDING/CHECKING으로 남으며 수용 불가로 바꾸지 않는다.
5. 한 환자에 총 10곳까지만 자동 문의한다. 마지막 묶음의 회신 대기를 거친 뒤 추가 판단을 요청한다. 새 후보가 없어도 미응답 문의가 남아 있으면 제한시간 안에서 회신을 감시하고 후보를 재확인한다.
6. 유효한 수용 응답을 확보하지 못한 상태로 시작부터 300초가 지나거나, 더 문의할 후보가 없고 진행 중인 문의도 없으면 `EXHAUSTED`로 멈추고 담당자 확인 메시지를 남긴다. 확보한 유효 응답은 300초 뒤에도 사람의 확정을 기다린다. 남아 있는 문의와 뒤늦은 병원 응답은 기존 API로 계속 확인할 수 있다.

모든 시간·문의 수는 개발용 설정이다. 환자의 임상적 허용 대기시간이나 최적 정책으로 검증된 값이 아니다. 수동 문의도 총 연락 병원 수에 포함하며, 자동 작업은 이미 연락한 병원에 재문의하지 않는다. 명시적 재시작도 기존 연락 기록을 보존한다.

## 관측 기반 V2와 판단 기록

`server/inquiry_policies.py`는 DB에 접근하지 않는 정책 계약이다. `observed_v2`는 `simulation/observed_inquiry.py`의 비용 계산을 초 단위 서버 입력에 연결한다. 예상 이동시간에 관측 회신시간, 병원별 미해결 문의 부담, 보정한 시간초과 비율을 더해 후보를 비교한다. 병원의 실제 치료 자원이 곧 생길지 예측하거나 수용 가능 확률을 계산하는 모델은 아니다.

- 처음에는 1곳에 문의하고 15초마다 다시 판단한다. 120초 이후에도 새로운 후보의 비용이 기존 대기 후보보다 유리할 때만 1곳을 추가한다. 무조건 120초마다 추가하는 방식이 아니다.
- 정책상 대기 문의 한도는 3곳이다. 180초가 지난 문의는 환자 자신의 대기 선택지에서 빠질 수 있지만, 실제 문의는 PENDING/CHECKING을 유지하고 전역 미해결 업무량에도 남는다. 뒤늦은 수용 응답은 기존 유효성 검사를 거쳐 사용할 수 있다.
- 최근 30분 관측을 사용한다. 병원별 표본이 2개 미만이면 전체 표본, 그것도 부족하면 180초 사전값을 쓴다. 시간초과 패널티 360초, 미해결 문의당 부담 60초 역시 실험 설정이다.
- 사건 이력으로 문의 시도별 최초 병원 회신을 한 번만 센다. 확인 중·추가 질문도 회신이며 수용 확답과 다르다. 180초 후 최초 회신은 과거 시간초과 관측을 바꾸지 않는다. 시간초과 전 취소·재문의로 끝난 시도와 미래 사건을 잘못 학습하지 않는다.

판단마다 `inquiry_policy_decisions`에 정책 이름·버전·작업 버전·사유·문의 병원 ID·집계 근거를 기록한다. 같은 작업 버전의 중복 기록을 막고 타 환자의 이름·증상·질문 내용은 근거에 넣지 않는다. 타임라인은 문의 전송과 주요 대기 사유 변경을 표시하며 매 15초 판단을 전부 메시지로 보내지 않는다.

관측 기록은 여러 사례와 정책에서 공유된다. 공정한 정책 비교에는 같은 초기 DB·사건 이력을 복제한 독립 실행이 필요하다. 현재 사건 재구성은 전체 관련 이력을 읽으므로 장기 운영에는 증분 집계가 필요하다. 서버 어댑터와 기존 실험 전체의 실행 조건은 다르다. 어댑터 자체를 사용한 합성 환경 비교와 실패 조건은 [서버 정책 비교](INQUIRY_EXPERIMENT.md)에 정리했다. 실제 운영 효과는 별도 검증 대상이다.

## 관측 기반 V3

`observed_v3`는 V2의 후보 비용 계산을 유지하면서 다음 두 규칙을 추가한다. 첫 1곳 문의, 15초 재평가, 대기 선택지 최대 3곳, 총 10곳·300초 한도는 유지한다.

- 최근 문의 전송 이후 지정한 상한까지 기다려도 수용 응답을 확보하지 못하면, 대기 선택지에 여유가 있을 때 다음 후보 1곳에 추가 문의한다. 닫힌 문의의 전송 시각도 포함하므로 오래된 문의 하나 때문에 매 15초마다 연속 확장하지 않는다. 기존 문의를 거절·취소로 바꾸지는 않는다.
- 후보 비용 계산에 사용할 과거 회신을 최근 10분 또는 15분으로 제한한다. 오래된 회신의 병원·결과 내용과 미래 사건은 점수에 사용하지 않는다. 병원의 치료 자원 회복을 예측하는 기능은 아니다.

개발 후보는 대기 상한 45·60·90초와 이력 범위 10·15분을 조합한 6개다. 공개 API는 기존 4개와 `observed_v3`만 목록에 표시한다. 내부 실험 이름은 화면 목록에서 숨긴다. 공개 V3가 사용할 후보는 `config/inquiry_v3_selected.json`으로 선택하며 서버 시작 때 한 번 읽는다. 전체 설정을 저장한 기존 작업은 코드·선택 설정이 달라지면 기존과 같이 409로 보호한다. 기본 정책은 계속 `fixed_3`다.

각 판단 근거에 이력 범위, 사용·제외한 과거 기록 수, 최근 문의 이후 경과시간, 추가 문의 상한 도달 여부를 남긴다. 개발 선택과 별도 seed 평가 절차는 [V3 개발·검증](INQUIRY_V3_EXPERIMENT.md)을 참고한다. 이 값들은 실험 설정이며 임상 기준이 아니다.

## 상태와 업무 경계

`QUEUED → RUNNING → AWAITING_CONFIRMATION → COMPLETED`가 기본 흐름이다. 수용 응답을 확보하기 전 한도 종료는 `EXHAUSTED`, 사용자 중지는 `PAUSED`, 계산 오류는 `ERROR`다. 일시정지나 오류·한도 종료 뒤 재시작하면 탐색 제한시간을 새로 잡으며, 이미 활성인 작업에 반복 시작 요청을 보내도 제한시간을 연장하지 않는다.

목적지 확정·이송 취소와 초기 자동 문의 중지는 하나의 트랜잭션으로 반영한다. 이 문서의 작업은 **초기 WAITING 환자**만 다룬다. 수용 응답과 목적지 확정은 사람이 처리한다. 수용 확정 이후에는 별도 [조건 재확인·대체 문의 워크플로](TRANSPORT_REVIEW.md)를 구현했다. 감시를 명시적으로 켜고 병원이 조정 필요로 판단한 뒤 대체 문의가 진행되며, 목적지 변경은 여전히 사람이 확정한다.

후보와 이동시간 계산은 DB 쓰기 잠금 밖에서 수행하고, 반영 직전 환자 버전·입력 변경 버전·작업 버전을 다시 확인한다. 계산 도중 회신·일시정지·취소·자원 변경이 생기면 이전 결과는 적용하지 않는다. 여러 워커가 동시에 실행돼도 같은 묶음을 중복 등록하지 않는다.
예정된 수용 제한이 계산 중 시작되는 경우도 적용 시각에 재검사한다. 실제 이동시간 API의 순차 호출이 오래 걸리면 같은 워커의 다음 작업이 지연될 수 있다. 현재 시연은 외부 호출을 사용하지 않으며, 실제 API 운영 연결에는 별도의 전체 계산 시간 제한과 병렬화가 필요하다.

대화 타임라인에는 시작·일시정지·문의 묶음·수용 확보·대기·한도 종료가 시스템 메시지로 표시된다. 메시지 전송 기능과 의료 판단은 별개다.

## 실행과 시연

```powershell
python -m server.chat_demo --db data/inquiry-policy-demo.db --port 18018
```

`http://127.0.0.1:18018/conversation-demo.html`에서 새 시연의 자동 문의와 정책을 선택한다. 환자 등록 후 별도 문의 버튼 없이 서버가 문의를 만들고, 병원 응답은 시연 버튼으로 실행한다. 현재 사례의 실제 정책과 최신 판단 근거는 별도로 표시한다. 수용 응답 후 사람이 확정하면 선택 병원이 대화에 참여한다. 이 별도 시연 UI와 함께 2026-10-13 [모바일·병원 연결본](UI_INTEGRATION.md)에서도 각 역할이 직접 문의·응답·확정을 진행할 수 있다.

기본 소아 시나리오는 적합한 병원이 2곳이므로 고정 3곳과 5곳 모두 2곳에만 문의한다. 차이가 사라진 오류가 아니라 후보 수 제한이다. 충분한 후보가 있는 일반 응급 시나리오에서 1·3·5곳의 차이를 확인한다.

일반 서버도 문의 워커를 기본 실행한다. `--no-planner`는 솔버 워커만 끄며 문의 워커는 유지한다. 문의 워커를 끄려면 `--no-inquiry-worker`를 사용한다.

검증 코드는 `test_inquiry_workflow.py`, `test_inquiry_policies.py`, `test_inquiry_v3.py`다. 자동/수동 분리, 필터·순서, 무응답·불가 분리, 응답 만료·조건 변경, 한도·중지·재개, 동시 실행, 계산 중 변경, 실제 HTTP와 조회 없는 백그라운드 실행에 더해 정책 선택·전환·기록·관측 순서·과거 정보만 사용하는지 확인한다. 이는 구현 검증이며 병원 선정시간의 임상적 개선 검증은 아니다.
