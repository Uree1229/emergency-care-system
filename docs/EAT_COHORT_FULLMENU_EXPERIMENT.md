# 세 후보 제한 해제와 전체 허용 조합 평가

상태: 별도 후보 `eat_cohort_fullmenu_l15_f`의 훈련 360환경·1,242명 검증을 마쳤다. 두 구간의 전체 선정 대기는 감소했지만 기존 성공 환자 2명을 잃어 보존 조건에 실패했다. 후보를 채택하지 않고 새 개발·별도 검증은 실행하지 않는다. 부모 소스·증거는 보존했다.

## 목표

사용자의 요청에 따라 직전 Stoploss에서 성공했던 환자가 실패로 바뀌지 않는 것을 이번 검증의 하드 조건으로 추가한다. 성공 수가 같거나 더 많아도 기존 성공 환자를 잃으면 통과하지 못한다. 정책 계산에는 성공 결과나 성공 환자 목록을 입력하지 않는다. 이 조건은 저장된 결과를 비교하는 검증 단계에서 판정한다.

| 훈련 구간 | CS 성공 / 선정 대기 | 부모 Stoploss 성공 / 선정 대기 | 기존 목표 | 추가 보존·감소 조건 |
|---|---:|---:|---|---|
| 기존 240환경·827명 | 689 / 111,858초 | 692 / 113,429초 | 성공 692 이상·대기 113,296초 이하 | 부모 성공 손실 0명·대기 엄격 감소 |
| 추가 120환경·415명 | 364 / 53,498초 | 363 / 54,627초 | 성공 364 이상·대기 53,498초 미만 | 부모 성공 손실 0명·대기 엄격 감소 |

두 자료는 이미 관측한 훈련 자료다. 구간을 합쳐 실패나 대기 증가를 상쇄하지 않는다. 기존 구간의 대기 목표는 D의 113,374초보다 최소 78초 단축하는 것이다. 실패 선정 대기는 300초, 실패 도착 비용은 1,800초로 계산한다. 선정 대기·도착·개별 성공·개인 최대 지연을 따로 보고한다.

## 확장 범위

기존 Stoploss의 평가 활성화 조건은 유지한다. 활성화되지 않은 그룹은 부모 행동을 그대로 사용하고, 활성화된 그룹에서만 최대 세 가지 메뉴 제한을 해제한다. 기존 후보와 점수는 원문 그대로 앞에 두고, 원래 JOINT 표에서 허용된 나머지 행을 표의 인덱스 순서대로 전부 평가한다. 동률이면 부모 Stoploss의 실제 선택을 우선한다.

여기서 JOINT의 `feasible`은 같은 후보 병원·문의 개수를 가진 조합 중 현재 두 환자의 예측 수용 확률과 예측 비용이 H 기준을 악화시키지 않는다는 기존 조건이다. 실제 자원 제약만을 뜻하지 않는다. 이 사전 조건·후보 병원·문의 개수·실제 동시 문의 한도는 유지한다. 최대 세 후보 제한만 해제한다.

과거 저장 자료의 별도 범위 검사에서는 180개 그룹 중 30개가 평가를 활성화했다. 이 30개 그룹의 원래 표는 6,350행, 허용 행은 3,028개였고 기존 메뉴는 합계 80개였다. 메뉴 밖 허용 행은 2,948개이며 30개 그룹 모두 추가 행이 있었다. 그룹별 허용 행은 5~225개다. 이는 부모 입력에서의 범위 진단이며 새 후보의 성능 결과나 실제 평가 행 수로 미리 계산하지 않는다.

6개 병원에서 환자마다 2곳을 문의하는 경우 전체 조합 표는 225행이며 일반 코드 상한은 400행이다. 모든 허용 행을 평가하고, 새 빔 제한이나 실행시간 기반 중단은 두지 않는다. 이 범위 검사는 `diagnosis/parent-menu-coverage.json`에 해시와 함께 보존했다.

## 행별 계산과 증거

새 행은 번호만 추가할 수 없다. 현재 공개 입력과 그 행의 문의에 맞춰 다음을 재구성한다.

1. Dynamic의 같은 시점 CS 참조 후속 문의 투영.
2. Recourse의 초기 예상 작업량과 이미 문의 중인 환자의 점수.
3. Followplan의 환자별 미래 문의 계획과 초기 회신 분포.
4. 봉인된 Stoploss 계산의 미래 대기·환자별 수용 확률·선정 대기.

우선순위별 수용 확률을 먼저, 동률이면 전체 선정 대기를 줄이는 목적함수와 확률·시간 허용 오차는 그대로다. 새 행은 한 행씩 계산하고 중간 자료를 해제한다. 저장 증거에는 독립 감사할 수 있는 Dynamic 투영과 최종 환자별 점수를 남긴다. 나머지 중간 점수는 감사기가 공개 투영과 봉인된 독립 계산에서 다시 구성한다. 부모 전체 제안과 기존 행은 별도로 그대로 보존한다.

실제 행동은 현재 두 환자의 문의뿐이다. 참조 후속 문의는 미래 행동이나 수용을 보장하지 않는다. 원래 문의 10곳·동시 문의 4건·A/H·종료 장벽·원자적 공동 적용·전 환자 FIFO와 병원 수용 확인 절차는 유지한다. 미래 사건·결과·미등록 환자·실제 처리 시작시각 등 공개되지 않은 정보는 정책에 넣지 않는다.

## 사전 고정과 검증

부모 Stoploss 봉인은 `e30dc4afebefb5fd297b98a0af8b4751d852207496f93f7f5b3e658125f9abd7`이다. 소스 522개·참조 2,071개·압축 원문 3,480개를 보존하고 새 소스 16개를 더한 538개를 검사·고정한다. 문서 목록의 역사적 해시 변경은 이력을 승계하며 새 재결속은 하지 않는다.

- 훈련 360환경: 새 후보만 각각 한 번 실행하고 비교군 18개·6,480분기는 봉인된 기록을 재사용한다. 모든 원문 저장 후 두 구간의 기존 목표·부모 성공 손실 0명·부모 대비 선정 대기 엄격 감소를 각각 요구한다.

- 별도 검증 368환경: 새 개발도 통과할 때만 실행한다. 같은 점 조건과 부모 성공 보존에 더해 세 비교군 각각 실패 차이 95% 상한 0 이하·대기 차이 95% 상한 0 미만을 요구한다. 시나리오 단위 짝 부트스트랩 10,000회다. 지표별 주변 95% 구간이며 전체 조건의 공동 95% 보장은 아니다.

새 입력은 소스 고정 뒤 생성하고 과거 미실행 입력의 난수도 재사용하지 않는다. 입력 명세 848개, 최대 새 실행은 9,632분기다. 성능 재실행·결과 제외·사후 설정 변경은 하지 않는다. 실패 뒤 후속 단계는 차단한다. 운영 서버와 기본 `fixed_3`는 유지한다.

독립 감사는 기존 부모 제안·원래 허용 표·모든 추가 행의 포함·순서·공개 투영·최종 점수·동률·실제 출력·전 환자 FIFO를 확인한다. 고정 기능 예제에서는 세 행을 넘는 자연 평가와 추가 행의 감사를 요구한다. 의미 감사는 모든 원문 저장 뒤 네 프로세스에서 수행하고 원문·전체 소스·인덱스에 결속한 사례별 증명을 남긴다. 유효한 증명은 재실행하지 않는다. 별도 표준 라이브러리 회계기는 정책·시뮬레이터를 실행하지 않고 환자 식별자까지 대조한다.

### 실제 평가 범위와 개인 지연

새 실행에서는 180개 공동 처리 그룹 중 31개가 부모 활성화 조건을 충족했다. 허용 3,208행을 전부 평가했고, 그중 3,125행이 해당 현재 상태의 부모 메뉴 밖 행이었다. 부모 Stoploss의 그 시점 선택과 달라진 그룹은 22개였다. 부모 저장 자료에서의 30그룹·3,028행과 새 실행의 범위는 구분한다. 새 행동 이후의 상태가 달라질 수 있다.

Stoploss 대비 개인 선정 대기는 기존 최대 139초·추가 최대 42초 늘었고, 두 정책에서 모두 성공한 환자의 최대 도착 지연은 기존 345초·추가 281초였다. 실패 도착 비용 1,800초를 포함한 J는 기존 841.782초로 부모보다 0.908초 높고, 추가는 818.704초로 부모보다 3.925초 낮았다. 전체 선정 대기 감소가 모든 환자의 개선이나 도착 개선을 뜻하지 않는다.

전체 실행·의미 감사·수집 벽시계 시간은 약 1,494.94초였다. 정책 계산시간으로 해석하지 않는다. 후보 확장에 따른 계산 비용도 현장 적용 전 별도 확인해야 한다. 성능 재실행·결과 제외·사후 설정 변경은 없다.

### 성공 손실 진단과 후속 후보

기존 성공을 잃은 두 사례의 저장된 근거를 검사했다. 각각의 확장 행 선택에서 해당 환자의 예측 수용 확률은 약 0.013573·0.013123 낮아졌지만 전체 우선순위 4 확률의 합은 높아졌다. 전자는 뒤 첫 문의 환자, 후자는 현재 두 환자 중 한 명이었다. 이 관측은 목적함수가 개별 확률 하락을 허용한다는 제한을 보여주며, 실제 실패 원인을 확정하지 않는다. 원문·인덱스·전체 소스 검증과 수치는 `diagnosis/success-regression-research.json`에 기록했다.

별도 후속 후보에서는 현재 점수를 계산한 모든 환자의 예측 수용 확률이 Stoploss 선택보다 낮아지는 행을 제외하는 일반 보호 조건을 검증한다. 실제 성공 식별자를 정책에 넣지 않는다. 이 Fullmenu 원문과 설정을 수정하지 않고 별도 후보·새 소스 고정·새 검증으로 진행한다. Fullmenu의 새 개발·별도 검증 단계는 차단한다.

### 회계기 복구 이력

처음 실행한 고정 회계기는 보존 이력 반복문의 지역 변수 `digest`가 같은 이름의 해시 함수를 가려 최종 증거 해시 검사에서 실패했다. 실패 당시 알고리즘·원문·조건은 변경하지 않았다. 고정된 회계기 원본도 그대로 보존하고, 지역 변수 이름 수정·복구 하위 폴더의 경로 해석·복구 출처 표시만 반영한 `recovery/finalize_phase_v2.py`를 별도로 추가했다. 수치 함수·통과 조건·단언·임계값은 동일하다. 원래 실패와 복구 코드의 해시를 `diagnosis/accounting-recovery.json`에 남기고 독립 검토 뒤 전체 회계를 다시 수행한다. 성능이나 의미 감사를 재실행하지 않는다.
