# 공동 첫 문의 배분 검증 — 2026-10-21

연구 후보 `eat_joint_first_l15_f`를 구현하고, 이미 본 120개 환경·434명으로 한 번 비교했다. **원래 R이 복구한 정확한 4건은 모두 유지했고, 혼합 환경의 선정 대기 합계는 EAT보다 155초 감소했다. 그러나 R·H에서 성공했던 다른 환자 1명을 잃어 전체 성공 보존 기준은 통과하지 못했다.** 실패 수가 같아도 성공한 환자가 달라졌으므로 통과로 처리하지 않았다.

연구 코드와 모든 결과를 보존했다. 새 개발·별도 검증 실행은 하지 않았으며, 운영 기본 정책 `fixed_3`와 실제 서버·UI·DB는 변경하지 않았다.

## 적용한 방식과 범위

- 현재 등록되어 있고, 첫 판단 시점이 되었으며, 기존 문의·정책 판단이 없는 대기 환자를 공개 작업 목록에서 찾는다. 시작시각·환자 ID 순서로 최대 두 명씩 묶는다. 미래 환자·실제 병원 작업자 수·미공개 수용 결과는 정책 입력으로 주지 않는다.
- 두 환자에게 **같은 커밋 시점의 공개 정보**로 기존 H 제안을 각각 계산한다. 각 제안의 즉시 문의 수를 고정하고, 각자 가까운 후보 6곳에서 그 수만큼 고르는 조합을 최대 400개 비교한다. 이 문의 수는 원래 순차 실행 H의 문의 수와 항상 같다는 뜻이 아니다.
- 같은 병원에 두 문의가 겹치면 후순위 환자에게 선순위 문의 한 건의 추정 업무시간을 더한다. 기존 추정 작업자 수 1을 유지한다. 실제 숨겨진 업무시간·작업자 수는 사용하지 않는다.
- 개인별 **모형상 선정확률이 감소하지 않고**, 기존 도착·실패·즉시 문의 비용이 증가하지 않는 조합 중 모형상 전체 첫 수용 대기가 가장 짧은 조합을 고른다. 기준안보다 엄격히 개선되지 않으면 기준 조합을 유지한다. 이는 실제 결과의 무손실 보장이 아니다.
- 실제 전송할 현재 문의만 공동 결정한다. H가 제안한 미래 문의 계획은 즉시 문의 수를 정하는 데만 사용하며, 미래 계획의 실행 가능성이나 병상을 예약했다고 해석하지 않는다.
- 두 환자의 상태·버전·공개 기록·문의 자격을 모두 재확인한 뒤 한 SQLite 트랜잭션에서 적용한다. 한 명이라도 달라졌거나 적용에 실패하면 전체를 취소한다. 한 명만 있는 경우와 후속 판단은 H 계산을 사용한다.

공동 첫 문의를 기존 개별 재평가보다 먼저 처리하는 실행 조정도 들어갔다. **후보 선택뿐 아니라 공통 정보 시점·판단 순서·원자적 적용을 합친 후보**이며, 원래 실행 순서나 이후 입력 경로가 같다고 주장하지 않는다. 각 효과를 분리하는 추가 성능 실험은 하지 않았다. H의 공개 시간 경계 A/H와 잔여시간 계산은 그대로 사용한다.
