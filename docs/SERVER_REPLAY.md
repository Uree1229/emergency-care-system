# 서버 문의 정책의 지도 재생

2026-10-12. 고정3·관측V2·개발에서 선택한V3의 **서버 실행 기록**을 같은 지도와 시간축에서 재생한다. 새 알고리즘을 실행하는 화면이 아니라 저장된 문의·회신·병원 선정 결과를 보여주는 화면이다.

## 실행과 사용

```powershell
python -m simulation.server_replay_adapter
python -m simulation.viewer_server --reuse-data --no-browser --port 18005
```

지도: `http://127.0.0.1:18005/?scenario=server-simultaneous_w1-7101`.

사례 선택창의 서버 문의 정책 그룹에서 8개 조건을 고를 수 있다. 고정3·V2·V3는 동일한 환자와 병원 조건에서 독립 실행한 기록이다. 재생·일시정지·배속·시간 막대와 이전/다음 사건 버튼으로 문의·회신·확정 시점을 비교한다. 여러 환자 사례에서는 환자 선택창으로 한 환자의 사건과 이동만 확인한다. 서버 사례의 결과 시간은 초로 표시한다.

## 어떤 사례를 보여주는가

V3 검증 보고서(`simulation_results/server_inquiry_v3_validation_20261012.json`)의 각 유형에서 가장 낮은 검증 seed7101을 선택했다. 결과가 좋은 사례를 골라 넣은 것이 아니며, 다음 8사례×3정책=24분기를 기존 지도 사례 뒤에 추가한다.

| 조건 ID | 관찰할 점 |
|---|---|
| `simultaneous_w1` | 여러 환자와 병원 담당1명. 문의를 많이 보낼 때 검토 대기열이 커지는 흐름 |
| `staggered_w2` | 환자 발생 시점이 서로 다름. 환자별 선정·이동·예상 도착의 시각 |
| `no_response_near` | 가까운 두 병원이 회신하지 않음. V2 미배정과 V3의 추가 문의, 고정3보다90초 늦은 결과 |
| `delayed_near_fast_far` | 가까운 병원은 늦고 먼 병원은 빠름. V3가 고정3보다45초 늦게 선정되는 반례 |
| `historical_shift` | 과거 회신 이력이 현재와 다름. 오래된 정보 사용의 영향 |
| `history_helpful` | 과거 이력이 현재와 일치. 관측 정책이 먼저 적합 후보에 문의하는 흐름 |
| `immediate_all_accept` | 모두 곧바로 수용. 고정3보다V3가2초 늦는 작은 차이도 유지 |
| `all_unavailable_control` | 모두 수용 불가. 모든 정책이 선정하지 못하는 대조군 |

위 수치는 seed7101의 사례 설명이다. 96개 검증 시나리오의 평균 효과와 구분한다. 전체 검증의 성과·남은 약점은 [V3 결과](INQUIRY_V3_EXPERIMENT.md)를 참고한다.

## 원본과 재생의 관계

- 입력: `simulation_results/server_inquiry_v3_validation_20261012.json`. 수정하지 않는다.
- 변환기: [server_replay_adapter.py](../simulation/server_replay_adapter.py).
- 출력: `simulation/viewer/server_replay_data.json`. 입력 파일의SHA256과 실제 출처 경로를 보존한다.
- 화면: [app.js](../simulation/viewer/app.js), [index.html](../simulation/viewer/index.html), [styles.css](../simulation/viewer/styles.css).
- 기존 `map_replay_data.json`은 그대로 사용한다. 서버 기록 파일이 없어도 기존 지도 사례는 재생한다.

원시trace의 문의 전송·검토 시작/종료·수용/불가·무응답·취소·확정을1:1로 변환한다. 시각은 원본 초(`at_seconds`)와 화면 분(`t`)을 함께 남긴다. 같은 초에는 실제 서버의 **회신·확정 → 정책 판단 → 추가 문의·검토 시작** 순서를 따른다. 자세한 판단 근거가 저장되지 않은 후속 사건은 ‘근거 미저장’으로 표시하고 진행 중 문의 수를0으로 추정하지 않는다.

서버의 `estimated_arrival_seconds`는 **환자 발생 이후 경과시간**이다. 지도상의 공통 예상 도착시각은 `created_at + estimated_arrival_seconds`, 이동 구간은 `selected_at`부터 이 시각까지다. 따라서 각 구간의 길이는 `travel_seconds`와 같다. 서로 다른 시각에 발생하는 환자에게도 같은 기준을 적용한다.

처리 대기 평균은 모든 접수 문의에 대해 검토 시작 또는 시작 전 취소까지 기다린 시간을 합산한다. 이미 착수한 검토는 취소돼도 업무시간을 소비하며, 시작 전 취소는 검토 업무를 소비하지 않는다. 회신 없음은 거절과 다르며, 취소 뒤의 회신은 배정에 반영하지 않는다.

## 재생 범위

병원·환자·회신·이동시간은 모두 서버 실험의 합성값이다. 경로는 합성 위치 간 직선 추정이며 실제 도로·긴급차량 이동을 재현하지 않는다. 서버에 환자 정보가 등록되는 시점부터 시작한다. 119 출동·현장 도착·처치 시각은 원본에 없어 만들지 않는다.

병원 도착은 선정시각과 합성 이동시간을 합한 **예상 도착**이다. 치료 시작·완료, 이송 중 조건 변경, 목적지 변경, 전원은 이번 서버 기록에 없으므로 표시하지 않는다. 기존 지도 사례에는 별도의 합성 전원·치료가 있으며 데이터 범위가 다르다.

## 검증과 다음 작업

새 회귀12개를 포함한 관련 **65개 테스트가 통과했다**. 원본의 전480분기에서 절대 도착시각·이동시간·평균을 대조하고, 원시 사건 순서·상세 출처·선택 정책·취소 대기를 확인했다. 회신·문의·선정 통계는 재계산한 정책 결과로 바꾸지 않는다.

실제 Chrome과 로컬HTTP에서 서버8사례·기존21사례를 확인했다. 원본의 문의·확정 수, 처리 대기열, 예상 도착시각과 결과표가 일치했고, 재생·정지·배속·슬라이더·사건 이동·환자 필터가 동작했다. 1440px·390px에서 가로 넘침·브라우저 오류·HTTP 오류가 없었다. 모바일 서버 사례의 범례는 환자와 차량을 가리지 않도록 상단에 배치했다. QA·캡처는 `.codex-build/server-replay-20261012/qa-report.json`과 같은 폴더에 보관했다.

2026-10-13 후속: 서버의 조건 변경·수용 재확인·대체 문의·사람의 목적지 변경 사건을 별도로 기록해 지도에 연결했다. [서버 조건 변경 재생](TRANSPORT_REPLAY.md)의 4종은 기능 시연이며 이번 문의 실험 결과에 전원 효과를 추가하지 않는다. 문의 정책을 다시 개선한다면 이번 검증seed를 독립 검증으로 재사용하지 않는다.
