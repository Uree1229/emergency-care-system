# 실제 회복 보고를 기억하는 재문의 개선 실험

기존 frontier 대비 개발 기준을 모두 충족한 조합이 없어 이번 후보를 채택하지 않았다. 새 검증 성능은 실행하지 않고 기존 frontier를 유지했다.

| 후보 | 배정 | 처치 지표 개선 / 악화 | 최대 제한 악화(분) | 총 순대기 변화(환자·분) | 문의 변화 |
|---|---|---:|---:|---:|---:|
| eager | H1 | 12 / 3 | 2.00 | -6.00 | -9 |
| eager | C1 | 12 / 3 | 2.00 | -6.00 | -9 |
| latched | H1 | 12 / 3 | 1.25 | +0.75 | -15 |
| latched | C1 | 12 / 3 | 1.25 | +0.75 | -15 |

이 기록은 합성 시뮬레이션 연구 결과다. 운영 서버·화면·DB와 기본 문의 정책 `fixed_3`는 수정하지 않았다.

## 문제와 변경

병원에서 실제 수용 불가 응답을 받은 뒤 자원 회복 보고를 받더라도, 다른 문의가 진행 중이면 회복 정보가 다음 문의 시점에 활용되지 못할 수 있다. 기존 frontier 문의 정책과 H1/C1 배정은 유지하면서, 실제로 받은 회복 보고를 근거로 재문의 자격을 한 번 되돌리는 실험을 추가했다.

- eager: 다른 문의가 진행 중일 때 회복 병원에도 정상 문의를 보낸다.
- latched: 회복 정보를 기억했다가 기존 문의가 모두 끝나고 유효 수용 응답이 없을 때 재문의한다. 회복 병원 외 정상 미방문 후보가 있으면 기존 절차를 따른다.
- 실제 임상 수용 불가 응답과, 그 이후에 관측된 자원 회복이 필요하다. busy 제어 응답·무응답·타임아웃을 임상 거절로 취급하지 않는다.
- 필요한 모든 자원이 같은 실제 보고에서 신선하고 충분해야 한다. 오래된 낙관 정보·부분 정보·같은 내용의 시각 갱신은 회복 허가를 새로 만들지 않는다.
- 초기 미수용·미확정 환자만 대상이며 환자 조건당 실제 재문의 1회다. 기존 tried 집합이 2개 이상일 때만 해당 병원 하나를 임시 허용해 원래 문의 회차가 초기화되지 않게 한다.
- 실제 문의 시각·응답 유효기간·기존 FIFO 업무와 인력·동시 3곳 및 회차 10회 한도를 유지한다. 새 문의에는 실제 병원 업무 비용이 발생한다.
- latched는 실제 회복 근거가 있을 때 기존 재시도 대기를 한 번 깨울 수 있다. 원래 retry_at와 실제 깨운 원인을 원문에 별도로 기록한다.

## 사전 고정한 비교

기존 109종과 새 경계 12종을 합쳐 121종을 사용했다. 44101~44103은 이미 관측한 개발 시드다. 기존 327개 입력은 원본 전체 분기와 이전 완전 원문 감사 증명을 그대로 재사용했다. 이를 신규 실행이나 신규 감사로 세지 않는다. 새 경계 입력에서는 frontier/safe/prototype/protected/fixed3 각각 H1/C1의 10개 참조를 실제 실행했다. 새 검증에도 같은 참조를 사용하도록 사전 고정했으며 실제 검증 실행 여부는 개발 기준 통과로 결정했다. 이전 capability/cooperative 4개 참조는 새 신선 비교에서 생략했고 과거 증거는 보존했다.

새 목표는 기존 문의 감소를 유지하면서 회복 지연을 줄이는 것이다. frontier 대비 개인 처치·최종 도착 악화나 처치 성공 상실이 없어야 하며, 각 환경의 총 순대기·제한 처치시간 합·문의가 증가하지 않아야 한다. 총 순대기와 제한 처치시간 합은 엄격히 감소해야 한다. 문의는 비증가를 요구하며 추가적인 엄격 감소를 요구하지 않는다. safe와 기존 배정 기반에 대한 별도 도입 기준도 유지했다.

## 핵심 반례와 다음 개선 지점

다음 시각은 개발 seed 44101의 대표 원문이다. eager의 `slow_reopen_maturity`에서는 H04가 4.25분에 수용했지만, 4분에 추가한 H01 문의가 아직 처리 중이어서 정상 확정 조건이 막혔다. frontier/latched는 즉시 확정해 12.25분에 도착·처치했고 eager는 2분 대기 후 확정해 14.25분으로 늦어졌다.

latched의 `recovery_then_decline`에서는 4분 회복 보고를 보고 4.75분에 재문의했으나, 이후 5~8분 실제 병상 중단으로 7.25분에 재거절됐다. 누적 문의가 많은 H01은 frontier 순위에서 밀려 H02(8.25)·H03(8.75)·H04(9.5)를 다시 거친 뒤 H01에 11.25분 문의해 14.75분에 도착·처치했다. 기존 frontier는 병상이 복구된 8분에 H01에 문의해 13.5분에 도착·처치했다.

이 두 악화 원환경에서 C1의 실제 18개 배정 기록은 모두 OPTIMAL/fallback=False였다. 따라서 위 차이는 50ms 계산 제한 실패가 아닌 실제 문의·확정 경로의 변화다. 다음 설계에서는 실제 재거절 뒤 새 회복 보고가 도착한 병원이 누적 문의 수 때문에 뒤로 밀리는 문제를 분리해 검증해야 한다. 추가 문의의 실제 업무 비용, 기존 수용 확정, 실제 문의 횟수와 회차 한도를 유지해야 한다. 이 후속 설계가 개선된다는 주장은 이번 결과에 포함하지 않는다.

## 검사와 보존

- 단위·통합 검사 2166개 통과, 이전과 같은 선택적 로컬 HTTP 바인딩 검사 6개만 제외.
- 작은 시드 7: 121개 환경, 새 분기 484개. 전체 원문을 저장한 뒤 감사했다.
- 신규 12종의 실제 경계 도달 여부를 별도 원문으로 점검했다. 도달 10/12종, 선언한 모든 경계 도달: False. stale_recovery는 보고 수신 전에 확정됐고 duplicate_recovery_feeds는 token 소모 자체가 없어 두 의사결정 경계를 검증했다고 주장하지 않는다. 상세 근거는 `reachability.json`에 보존했다.
- 과거 회귀 31개 입력, 실제 새 실행 124개와 별도 저장 원문 독립 감사. 기본 회귀 기준 통과: True.
- 이전 자료 7,942개와 기존 과학 소스 146개를 변경 없이 보존했다. 새 소스 10개를 더한 156개를 입력 생성·성과 평가 전에 고정했다.
- 새 검증 시드의 과거 사용 여부는 JSON/JSONL/gzip 8,305개 파일의 실제 시드 필드를 검사했다. 일치와 읽기 오류는 없었다.
- 개발 단위검사 작성 중 실제 발생하지 않는 이벤트를 찾는 fixture 오류 1건을 수리했다. 초기 전체 검사 결과도 보존하고 고정 소스의 전체 검사를 다시 실시했다.

첫 통합 점검은 21번째 환경에서 회차 복원 불일치로 중단했고, 생성된 82개 원문과 감사 완료 81개 기록을 모두 보존했다. 조사 결과 회복 근거가 없는 환자에게도 latched 추가 점검을 호출하면서 정상 basecall의 회차 초기화가 앞당겨질 수 있었다. 실제 회복 자격이 있는 경우에만 추가 호출하도록 제한하고, 정상 회차 전환의 감사 재현과 회귀 검사를 보강했다. 수리는 소스 고정 및 예약 시드 성능 실행 전에 완료했다.

두 번째 통합 점검은 119번째 환경에서 원래 보고 갱신 콜백의 같은 시각 재진입을 감사기가 빠뜨려 중단했다. 생성된 473개 원문과 감사 완료 472개 기록을 보존했고, 실제 원 보고 갱신 사건을 근거로 정상 회차 진입만 재현하도록 감사기를 수리했다. 또한 새 경계 두 환경은 병상 3개 중 1개 중단만으로는 실제 거절을 일으키지 못했으므로, 기존 방식의 동일 시각 중단 사건 3개를 사용해 실제 거절 경계를 점검했다. 기존 109개 입력은 바꾸지 않았다. 이 수리와 작은 시드 7·8 확인도 소스 고정과 예약 성능 실행 전에 끝냈다.

개발 결과가 완성되기 전, 독립 감사 helper가 잠금 파일 경로를 `config/`로 읽고 실행기는 `simulation/`에 쓰는 경로 불일치를 발견했다. 고정 원본은 보존하고 해당 경로 문자열 1개만 바꾼 `audit_artifacts_v2.py`로 감사를 실행했다. 나머지 바이트가 동일함과 두 helper·동결 증명의 SHA를 `independent-audit-path-corrigendum.json`으로 바인딩했다. 알고리즘 소스·입력·선택·성과 결과는 바꾸지 않았고 성능 분기는 재실행하지 않았다.

개발 완료 뒤 읽기 전용 후처리에서 번호가 없는 표시 사건과 번호가 있는 실제 서버 사건이 같은 원문에 함께 있는 형식을 확인했다. 원래 분석 helper와 실패 기록을 보존하고 `analyze_v2.py`에서 실제 번호의 부분열과 원래 목록 위치를 각각 검사했다. 원문에 번호를 새로 붙이거나 사건을 제거하지 않았으며, 원문·알고리즘·선택 결과를 바꾸거나 성능 실행을 반복하지 않았다. 수리 범위와 두 helper의 SHA는 `analysis-legacy-event-order-repair.json`에 기록했다.

## 해석의 범위

순대기 합은 이동을 제외한 환자의 탐색·병원·전원 준비 대기를 합친 값이며 단위는 환자·분이다. 병원 문의 큐 대기와는 구분한다. 미처치 환자의 제한 처치시간은 관찰 종료로 제한한 비교 지표다. 최대 제한 악화를 실제로 관측한 처치 지연이라고 표현하지 않는다. 개인 순대기도 별도로 진단한다.

고정 3곳 참조는 문의 회차 10회 한도가 없는 다른 기반이므로 부분 변경의 인과 효과나 전체 우월성을 주장하지 않는다. 저장 참조의 CPU 측정은 다른 실행 시점의 값이며 정책 성능 판단 기준으로 사용하지 않는다. 50ms 배정 제한의 timeout/fallback도 재실행하거나 결과에서 제외하지 않는다.

재문의는 실제 새 업무를 발생시키므로 향후 환자의 대기와 기존 응답의 성숙 시점에 영향을 줄 수 있다. 미래 환자·미래 자원·미래 응답시간을 사용하지 않았고 보편적인 무악화를 보장하지 않는다. 독립 감사는 실제 원문 사건과 현재 상태로 재문의 원인을 재현하지만 로그에 없는 모든 내부 retry_at 대입을 독립적으로 복원한 증명은 아니다.
