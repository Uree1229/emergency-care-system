# EAT 대기 추정 개선: 공개된 FIFO 전체의 잔여 업무 추정

사전 단계 기준을 통과하지 못해 후속 새 성능 실행을 진행하지 않았으며, 이 후보는 채택하지 않는다. 최종 단계는 **기존 자료 회귀 확인**다. 기존 서비스 기본값 `fixed_3`은 유지했다.

## 바꾼 한 가지

기존 R은 선두 업무의 나이를 반영한 잔여 시간에 뒤 문의들의 전체 평균 업무량을 더했다. 새 `eat_fifo_l15_f`는 **공개된 FIFO 목록 전체에서 표시된 회신이 없다는 조건 아래 남은 업무량**을 추정한다. 앞선 문의가 실제로 끝났더라도 회신하지 않았을 가능성 등을 모델에 넣어, 보이는 문의 수를 모두 아직 시작하지 않은 업무로 간주할 때 생기는 오차를 줄이려는 한 가지 변경이다.

수치 계산은 원래 **5초 격자에서 완료 시각을 올림하는 DP 근사**를 사용한다. 연속시간 실제 업무의 정확한 해나 실제 작업자 수의 관측이 아니다. 빈 목록·문의 한 건(n=1)·경과 0초·회신 확률 1(r=1)·이미 표시된 회신·다른 설정상 처리자 수·수치 underflow 등의 경계와 보호 경로를 계산 근거와 검사에 남긴다. 격자 올림과 유한한 수치 범위에 따른 근사 한계를 숨기지 않는다.

**단일 처리자 가정**은 정책의 설계 모델이다. 실제 병원 인원이나 숨은 완료 상태를 감지한 것이 아니며, 실제 처리 인원·미래 회신·자원 보고를 새로 정책에 주지 않았다. 어떤 입력에서 분석식이나 보호 경로를 쓰는지 증거에 기록해, 실제 모델 변경과 fallback을 구분할 수 있게 한다.

기존 R의 자기 대기 문의 수용 CDF, 이동시간순 후보, 문의 비용, 계획 계산과 검토 주기·확정 흐름·동시 문의 한도는 유지한다. 같은 코드 구조를 유지한다는 뜻이며, 비용 추정이 바뀌어 병원 선택과 이후 경로가 달라질 수 있다. 이전 batch/guard의 문의 묶음 교정은 섞지 않았다. 이 FIFO 추정만으로 뒤에 발생하는 환자의 기회를 보존하거나 모든 R 성공 환자를 자동으로 지킨다고 보장하지 않으며, 실제 실험 결과의 별도 게이트로 확인한다.

이전 전체 묶음 후보는 R 성공 9명과 기존 복구 네 명 중 두 명을 잃어 기각했다. 이후 동일 개수 guard는 네 복구 환자를 모두 지켰지만 다른 R 성공 네 명을 잃고 다른 네 명의 성공으로 상쇄돼 역시 기각했다. 실패 기록과 봉인은 그대로 두며, 이번 FIFO 후보의 성공을 사전에 가정하지 않는다. **보존 기준의 부모는 기각한 guard 봉인이고, repair의 수치 비교·600개 캐시는 원래 R 자료**다.

## 단계와 고정 기준

1. **기존 자료 회귀 확인(repair)**: R에서 네 환자를 복구했던 이미 확인된 120개 환경 전체를 사용했다. 새 후보만 환경당 한 분기씩 **120개 신규 실행**, 부모의 기존 다섯 분기 **600개는 캐시 참조로 명시**했다. 원래 네 환자를 각각 지키는지와 혼합·스트레스 전체에서 R 성공 환자를 잃지 않는지 검사한다. 이 자료는 설계에 사용한 학습 자료이며 독립 검증이 아니다.
2. repair 보고서·감사·잠금이 통과한 경우에만 새 개발 **120개 환경 × 6분기 = 720개**를 실행한다. 혼합 96개와 스트레스 8유형 × 3 seed다. 비교 정책도 모두 새로 실행한다.
3. 새 개발 통과 후에만 별도 검증 **368개 환경 × 6분기 = 2,208개**를 한 번 실행한다. 혼합 320개와 스트레스 8유형 × 6 seed다. 기존 성과를 보고 후보·설정·판정 기준을 바꾸거나 검증을 반복하지 않는다.

최대 신규 실행은 120 + 720 + 2,208 = **3,048분기**이며 부모 캐시 600개는 별도로 센다. 이번 실제 실행은 신규 **120개**, 캐시 **600개**다.

주 지표 **W는 환자 발생부터 병원 선정까지의 대기**이며 실패 환자에게 300초를 부여해 전체 환자를 집계한다. 이동·도착 후 처치 대기를 더한 지표가 아니다. **J는 선정 성공 시 추정 도착시간, 실패 시 300 + 1,500 = 1,800초인 환자 평균**이다. 실패 비용 600·3,000초 민감도도 원 보고서에 남겼다.

각 단계의 통과 조건은 **기존 EAT와 R 모두보다 W 합계가 작고**, R 성공 환자를 혼합·스트레스 전체에서 잃지 않으며, 실패 수·J가 두 기준보다 늘지 않고, 문의 수·병원 검토 업무가 `fixed_3` 이하인 것이다. repair에서는 정확한 네 복구 환자를 각각 지켜야 한다. 검증은 EAT·R 각각에 대해 시나리오 단위 부트스트랩 10,000회의 **환자당 W 변화 95% 구간 상한 < 0**도 요구한다. W/J 주 판정에서는 스트레스를 제외하되 성공 보존 게이트에는 포함한다.

고정 소스 301개와 후보·게이트를 먼저 동결하고 608개 단계 입력의 해시를 만들었다. 새 namespace의 역할별 128비트 seed 425개는 서로 분리하고 이전 shortlist·R·batch·guard namespace와 보고된 검증 seed와 겹치지 않게 확인했다. 전체 과거 글로벌 파일을 다시 검색했다는 주장은 하지 않는다.

원래 R에서 복구된 정확한 네 환자의 보존 결과: **3/4**. 식별자는 동결 protocol과 보고서 `recovery_check`에 전부 남겼다.



새 개발 실행 0회, 별도 검증 실행 0회다. 후속 단계가 실행되지 않았다면 앞 단계 게이트 실패에 따른 것으로, 미실행 단계의 성과를 주장하지 않는다. 개별 지연·실패 전환을 전체 개선으로 숨기지 않으며, 모든 미래 상황의 무손해는 주장하지 않는다.

## 검사·원문 감사·보존

선택한 기존 EAT·확정·잔여 업무와 새 묶음 정책·기록 연결·감사·단계 잠금 검사 **124개**가 통과했다. 과거 전체 프로젝트 검사 재실행은 아니다. 정상 잠금과 실패·변경 잠금의 단계 진입 경계도 검사했다.

신규 저장 gzip **120개·120개 완전 분기**와 명시한 기존 repair 캐시 gzip **120개·600분기**의 압축/해제 SHA256, 동결 입력 해시, 같은 초기 스냅샷·환경, 환자별 보고서, W/J/실패·문의 및 실제 `review_started` 업무 합계를 대조했다. 두 주 기준의 부트스트랩 구간과 전체 R 성공 보존, 네 복구 식별자, report/audit/lock의 단계별 해시 연결도 원문에서 재집계했다. 불리한 원문 제외·성능 재실행은 하지 않았다. 감사와 최종 집계는 저장 자료만 읽고 정책이나 시뮬레이션을 실행하지 않았다.

기존 **291개 소스·106개 참조 경로**와 새 동결 **301개 소스**를 확인했다. 이 실험의 명시된 부모 캐시 120개 외의 과거 원문 증거는 이름과 해시가 고정된 부모 봉인 증명을 재사용하며, 이전 대형 글로벌 원문 전체를 재해시했다고 주장하지 않는다. 기존 `docs/README.md`, 운영 서비스·UI·실제 DB는 그대로다. 운영 채택은 하지 않았다.

검증 범위는 합성 병원 문의의 선정 대기다. 임상 예후·실제 병상 확보·도착 후 치료 대기 또는 공동 배정 H1/C1 성능을 직접 증명하지 않는다.
