# 치료조건 카탈로그와 병원 정보의 사용 기준

작성일: 2026-10-11

이 문서는 안성·평택에서 발생한 가상 환자를 주변 8개 시의 실제 응급의료기관 목록에 연결하는 실험에서 **무엇을 치료조건으로 입력하고, 어떤 공개 정보로 확인할 수 있는지** 정의한다. 기계가 읽는 조건 묶음은 [treatment_requirements.json](../../config/treatment_requirements.json)에 있다.

조건 묶음은 프로젝트의 **실험 설정**이다. 증상에 따른 진단, 환자 중증도 분류, 임상적으로 허용되는 대기시간을 정하는 지침이 아니다. 실제 적용에는 의료진 검토와 병원의 환자별 수용 확인이 필요하다.

## 1. 대상 지역과 데이터의 경계

| 구분 | 범위 |
|---|---|
| 환자 발생 지역 | 경기도 안성시·평택시 |
| 초기 병원 후보 | 경기도 안성시·평택시·오산시·화성시·용인시·수원시, 충청남도 천안시·아산시 |
| 실제 공개 데이터 | 병원 식별자·이름·위치·등록 진료과·시설 수·공개 가용 관측 |
| 병원 웹에서 확인할 데이터 | 환자별 수용 응답, 담당 팀의 현재 가용 여부, 연령·체중 등 제한, 수용 당시 조건의 유지 여부 |
| 가상 실험 데이터 | 환자 발생, 필요한 조건, 응답 지연·무응답, 전문팀 수요·점유, 상태 변화 사건 |

이 지역 범위는 한 번의 실험에 사용할 후보 집합이다. 전국의 치료가능기관을 모두 포함하거나, 해당 범위 안에서 모든 환자의 병원을 확보할 수 있다는 뜻이 아니다. 어떤 후보도 확인되지 않으면 미배정·추가 탐색 필요로 기록한다.

2026-10-11 실제 수집에서는 **8개 시의 병원 34곳, 상세 34건, 가용병상 28건, 중증질환 원문 28건**을 확보했다. 모든 병원에 진료과 목록이 있었으나, 병원 목록에 있는 모든 기관이 가용병상 API에 나타나는 것은 아니었다. 실제 수집 DB에는 운영 자원과 환자를 생성하지 않았다. 지역별 건수와 수집시각은 최신 수집 결과 포인터(`data/regional_snapshots/latest.json`)가 가리키는 스냅샷의 `summary.json`에서 확인한다.

수집된 진료과 목록에는 **심장내과·순환기내과의 정확한 이름이 없었다.** `내과`가 등록돼 있다는 이유로 이를 심장내과로 바꾸지 않는다. 이 결과는 해당 권역에 심장 진료 병원이 없다는 뜻이 아니라, 이 공개 필드만으로 세부 진료 분야를 확인할 수 없다는 뜻이다.

## 2. 치료조건은 세 층으로 나눈다

| 층 | 예시 | 확보 방법 | 자동 판단에서의 의미 |
|---|---|---|---|
| 등록 진료 분야·시설 | 정형외과 등록, 수술실 6실, NICU 시설 수 | NMC 병원 상세 API | 문의 대상을 평가할 근거. 현재 진료·수술 가능의 확답 아님 |
| 현재 자원 관측 | 응급실 가용수, CT 가용 표시 | NMC 가용병상 API, 병원 웹 | 특정 시각의 관측. 환자별 수용 응답과 구분 |
| 환자별 실제 치료·수용 조건 | 해당 연령의 소아 진료 가능, 고위험 분만과 신생아 집중치료 동시 가능 | 병원의 수용 응답·추가 질의, 의료진 확인 | 해당 환자의 후보 적합성과 확정 판단에 사용할 확인 근거 |

예를 들어 **산부인과와 소아청소년과가 등록돼 있다는 사실**은 공개 데이터로 확인할 수 있다. 그러나 그 사실만으로 지금 해당 산모를 분만시키고 신생아에게 집중치료를 제공할 수 있다고 결론 내리지 않는다.

## 3. 공개 API에서 확인한 필드

공식 근거는 [국립중앙의료원 전국 응급의료기관 정보 조회 서비스](https://www.data.go.kr/data/15000563/openapi.do)의 참고문서 **V13 활용가이드(개정 2026-08-27)**다. 가이드의 오퍼레이션 5(기본정보)와 오퍼레이션 1(실시간 가용병상)의 응답표·XML 예제를 대조했다. 필드의 설명과 해당 지역에서 실제 값이 제공되는지는 구분한다.

### 3.1 병원 상세: `getEgytBassInfoInqire`

| 원본 필드 | 문서상 의미 | 내부에서 보존할 값 | 해서는 안 되는 해석 |
|---|---|---|---|
| `dgidIdName` | 진료과목 | 쉼표로 분리한 등록 진료과 이름과 원문 | 현재 전문의·당직·전문시술팀 가용으로 해석 |
| `dutyEryn` | 응급실 운영 여부(1/2) | 원문과 운영 여부 확인 상태 | 응급환자 전원 수용 가능으로 해석 |
| `hperyn` | 응급실 | 0 이상의 정수인 시설 수 | 현재 잔여 가용수로 해석 |
| `hpopyn` | 수술실 | 0 이상의 정수인 시설 수 | 수술팀·마취과·수술실이 지금 모두 가용하다고 해석 |
| `hpicuyn` | 일반중환자실 | 0 이상의 정수인 시설 수 | 현재 간호 인력이 배치된 가용 병상으로 해석 |
| `hpcuyn` | 신경중환자실 | 0 이상의 정수인 시설 수 | 일반 ICU·신경외과 수술 역량과 혼용 |
| `hpccuyn` | 흉부중환자실 | 0 이상의 정수인 시설 수 | 심장 중재시술 가능과 동일시 |
| `hpnicuyn` | 신생아중환자실 | 0 이상의 정수인 시설 수 | 신생아의 현재 수용 확답으로 해석 |
| `hpgryn` | 입원실 | 0 이상의 정수인 시설 수 | 퇴원·전실이 가능한 현재 여유로 해석 |
| `dutyTime1s`~`dutyTime8c` | 요일별 진료시간 | 필요 시 원문 보존 | 응급실·각 진료과 당직시간으로 해석 |

상세 응답에는 `hvec`, `hvoc`, `MKioskTy*` 등도 섞여 있다. **상세의 가용 숫자로 별도 가용병상 관측을 덮어쓰지 않는다.** 특히 상세의 `MKioskTy1`~`11`·`25`와 최신 중증질환 API의 `MKioskTy1`~`28`은 같은 숫자라도 의미가 달라 사용할 오퍼레이션을 함께 저장해야 한다.

시설 정규화 키는 `hperyn→ed_bed`, `hpicuyn→general_icu_bed`, `hpcuyn→neurological_icu_bed`, `hpccuyn→thoracic_icu_bed`, `hpnicuyn→nicu_bed`, `hpopyn→operating_room`, `hpgryn→inpatient_bed`다. 이 키는 상세의 시설 수를 식별하며, 현재 운영 자원이나 공개 잔여수로 자동 투영하지 않는다.

### 3.2 가용병상: `getEmrrmRltmUsefulSckbdInfoInqire`

| 원본 필드 | 관측 의미 | 카탈로그 대응 키 | 처리 |
|---|---|---|---|
| `hvec` | 일반 응급실 가용수 | `ed_bed` | 유효한 0 이상의 정수만 수치로 저장 |
| `hvoc` | 수술실 공개 가용수 | `operating_room` | 시설 수 `hpopyn`과 구분 |
| `hvicc` | 일반 중환자실 공개 가용수 | `icu_bed` | 0 이상 정수 정규화 완료. 시설 수 `hpicuyn`과 구분. 솔버의 ICU 자원 지원은 후속 확장 |
| `hvncc` | 신생아 중환자실 공개 가용수 | `nicu_bed` | 누락은 0이 아닌 미확인 |
| `hv42` | 분만실 공개 관측 | 수량 `delivery_room`, 표시 `service_availability` | 숫자는 수량, Y/N은 별도 bool. Y/N을 슬롯 1/0으로 바꾸지 않음 |
| `hvctayn` | CT 가용 표시 | `ct` | 장비의 관측 상태만 보존 |
| `hvmriayn` | MRI 가용 표시 | `mri` | 장비의 관측 상태만 보존 |
| `hvangioayn` | 혈관촬영기 가용 표시 | `angiography` | 중재시술팀 가용과 구분 |
| `hvventiayn` | 인공호흡기 가용 표시 | `ventilator` | 환자에 맞는 장비·인력 여부는 별도 확인 |
| `hvventisoayn` | 조산아 인공호흡기 가용 표시 | `neonatal_ventilator` | 미확정 값 코드 원문 보존 |
| `hvincuayn` | 인큐베이터 가용 표시 | `incubator` | 미확정 값 코드 원문 보존 |
| `hvidate` | 원본 입력시각 | `source_observed_at` | 서버 수집시각 `fetched_at`과 구분 |

숫자 필드는 음수·공백·특수값·누락을 미확인으로 둔다. 장비 표시의 `Y`·`N`과 `N1` 같은 값은 구분한다. `N1`을 숫자 1 또는 단순한 N으로 잘라 해석하지 않는다. 장비 표시가 Y여도 특정 환자의 치료 가능을 확정하지 않는다.

분만실 `hv42`의 실제 원문은 28곳 중 Y 10곳·N 1곳·누락 17곳이었다. 이를 별도 `service_availability`로 저장했다. 조건 평가의 `service_availability_evidence`에서 표시 근거를 확인할 수 있지만, 분만실 수량·고위험 분만·산과수술·NICU 조건을 충족한 것으로 바꾸지 않는다. 시각 미상·오래된 관측의 확인 필요 정책은 동일하다.

### 3.3 현재 상세 실응답에서 확인한 예

평택 상세 실응답(`data/public_probe/detail_A2100028.json`)의 굿모닝병원 자료에는 정형외과·신경외과·산부인과·소아청소년과·응급의학과 등이 등록돼 있다. 시설 값으로는 `hperyn=27`, `hpicuyn=27`, `hpopyn=6`이 제공됐고 `hpnicuyn`은 없다.

이 자료의 의미는 **등록된 과와 공개 시설 값이 존재한다는 것**까지다. `내과`가 있다고 심장 중재시술 가능을 확정하거나, `hpnicuyn`이 없다고 NICU가 없다고 결론 내리지 않는다. 원본 응답에 환자별 수용 확인은 없으며, 상세 값만으로 정보가 현재 시각에 갱신됐다고 판단하지 않는다.

## 4. 6개 치료조건 묶음

아래는 알고리즘 시험을 위한 조건의 예다. 의료진이 환자의 진료 필요를 판단했다는 가정 아래 사용하는 **가상 수요**이며, 증상과 조건을 자동으로 연결하지 않는다. `1`은 실험용 단위로, 임상적 처치 자원의 표준량이 아니다.

| ID | 실험용 조건 묶음 | 기본 모델 수요 | 추가로 확인할 조건 |
|---|---|---|---|
| `TR_GENERAL_ED` | 일반 응급 평가 | 응급의학, `ed_bed=1` | 현재 환자의 상태·필요 처치 수용 가능 여부 |
| `TR_ORTHOPEDIC` | 정형외과 평가 | 정형외과, `ed_bed=1`, `special_team=1` | 손상 형태에 맞는 담당자·검사·처치. 수술이면 추가 조건 |
| `TR_CARDIAC_INTERVENTION` | 심장 중재시술 필요 | 심장내과, `ed_bed=1`, `special_team=1` | 필요한 재관류 중재시술, 전문팀·시설·시술 후 치료 |
| `TR_NEUROSURGICAL` | 뇌신경 응급수술·중환자 치료 | 신경외과, `ed_bed=1`, `special_team=1` | CT·응급수술·마취·수술실 1·ICU 1을 가정한 확장 조건 |
| `TR_PEDIATRIC` | 소아 응급 평가 | 소아청소년과, `ed_bed=1`, `special_team=1` | 연령·체중별 제한, 담당자와 필요한 추가 처치 |
| `TR_HIGH_RISK_BIRTH_NEONATAL` | 고위험 분만과 신생아 집중치료 동시 필요 | 산부인과·소아청소년과, `ed_bed=1`, `special_team=1` | 고위험 분만·신생아 집중치료, 분만실 1·NICU 1, 필요 시 수술·마취·호흡 지원 |

`TR_CARDIAC_INTERVENTION`의 필수 장비 관측 조건은 `angiography`, `TR_NEUROSURGICAL`은 `ct`로 명시했다. 이 장비 수요 역시 해당 가상 시나리오의 설정이며, 모든 심장·뇌신경 환자에게 적용되는 임상 규칙이 아니다.

고위험 분만·신생아 프로필은 **인큐베이터와 조산아 인공호흡기를 일괄 필수로 넣지 않는다.** 기본 `equipment`는 비어 있고, `optional_equipment`에 두 장비를 별도로 기록했다. 실제 환자 상태에 대해 의료진이 필요를 지정하거나 가상 시나리오에 수요를 명시했을 때만 해당 장비를 `equipment`에 추가해 비교한다. 현재 비교기는 `optional_equipment`를 자동 요구사항으로 처리하지 않는다.

### 조건을 추가하는 방법

- 심장내과: 상세의 `내과`만으로 대응시키지 않는다. 별도 심장내과·순환기내과 등록이 있어도 중재시술 여부는 확인한다.
- 뇌신경: `신경과`와 `신경외과`를 같은 역량으로 취급하지 않는다. 수술과 중환자실 조건은 해당 가상 환자에게 명시적으로 부여한다.
- 소아: 소아청소년과 등록만으로 모든 연령·체중의 환자 또는 신생아 집중치료를 포함하지 않는다.
- 분만·신생아: 분만 가능 병원 집합과 신생아 집중치료 가능 병원 집합의 교집합을 확인한다. 분만실 숫자만으로 고위험 분만 가능을 판단하지 않는다. 다태아이면 NICU 수요 등의 실험값도 달라져야 한다.

등록 진료과는 쉼표 분리와 앞뒤 공백 제거 후 **이름의 정확한 일치**로 근거를 만든다. 별도 표에 정의한 이름만 대응시키며, 문자열의 일부가 같다는 이유로 전문 분야를 확장하지 않는다. 이름이 없거나 목록이 비어 있으면 미확인으로 남긴다. 정확한 이름이 있어도 상태는 등록 근거 충족이지, 현재 수용 확정이 아니다.

## 5. 필터링과 확정의 규칙

각 조건은 `supported`(해당 종류의 근거 있음), `confirmed_unmet`(현재 충족 불가 확인), `verification_required`(확인 필요)로 구분한다. **등록 근거의 supported와 현재 수용 가능의 supported는 서로 다른 층의 판정**이다.

실제 공개 데이터 비교기 `server/treatment_data.py`의 결과 코드는 `MATCH`, `EXCLUDED`, `NEEDS_CONFIRMATION`이다. `MATCH`도 요청한 공개 근거의 일치를 뜻할 뿐 수용 확정이 아니다. 이 카탈로그에는 모든 프로필에 사람 확인 항목이 있으므로 공개 정보만 입력한 종합 판정은 `NEEDS_CONFIRMATION`으로 남는 것이 정상이다.

기본 비교에서는 공개 가용수 부족도 `NEEDS_CONFIRMATION`으로 처리한다. 실험에서 `exclude_public_unavailability=True`를 명시한 경우에만 최신 관측의 가용 부족을 **현재 문의 차수의 잠정 제외**로 처리한다. 영구 제외하거나, 오래된 관측으로 불가를 확정하지 않는다.

| 입력 | 후보 처리 | 화면에 보여줄 의미 |
|---|---|---|
| 정형외과가 등록돼 있음 | 등록 근거가 있는 후보로 평가 | 정형외과 등록 확인, 현재 진료는 확인 필요 |
| 진료과 목록이 없거나 해당 이름이 없음 | 현재 정보만으로 확정 배제하지 않음 | 등록 정보 미확인 또는 해당 분야 추가 확인 필요 |
| 오래된 가용수 또는 원본 시각 없음 | 현재 수용 불가로 확정하지 않음 | 관측시각·갱신 상태 확인 필요 |
| 공개 가용수가 0 | 현재 수용 가능 여부를 재확인할 근거 | 공개 관측상 0, 병원 확인 필요 |
| 병원이 해당 환자의 필수조건 충족 불가를 회신 | 유효한 응답 기간에는 후보 제외 | 불가 사유·시각·적용 조건 표시 |
| 병원이 현재 환자 정보에 대해 수용 회신 | 확정 판단의 입력으로 사용 | 응답시각·유효기간·전제 조건 표시 |

부분 정보가 없다는 이유로 실제 적합한 병원을 빠뜨리는 문제와, 약한 근거로 진료 가능을 확정하는 문제를 함께 피해야 한다. 데이터가 미확인인 후보는 확인 항목을 남기고 병원에 문의한다. 병원 답변이 최신 수용 근거가 되며, 이후 조건이 달라지면 영향을 받는 환자만 재확인한다.

공공 가용수는 병원 웹의 운영 자원과 별도 보관한다. 잔여수를 총량으로 넣은 뒤 occupied를 다시 차감하거나, 공개 가용수를 해당 환자에게 확보한 예약 자원으로 사용하지 않는다.

### 카탈로그가 비교기에 전달하는 항목

| JSON 항목 | 용도 |
|---|---|
| `required_capabilities` + `department_evidence.groups` | 명시된 진료과 이름의 정확한 일치 비교 |
| `resource_demands` | 기본 수요 `ed_bed`·`special_team` |
| `extended_resource_demands` | 수술실·ICU·분만실·NICU 등 확장 수요. 비교기에 전달하되 현 솔버 지원과 구분 |
| `equipment` | 해당 프로필에 명시적으로 부여한 필수 장비 관측 조건 |
| `optional_equipment` | 환자별로 필요가 지정될 때 추가할 선택 항목. 기본 비교에서는 검사하지 않음 |
| `required_services` | 전문시술·치료 서비스. 공개 진료과·장비만으로 확정하지 않고 사람 확인 필요로 표시 |
| `human_confirmation` | 병원과 의료진이 해당 환자에 대해 확인할 사항 |
| `evidence_field_ids` | 참고 가능한 원본 필드의 카탈로그 ID. 열거한 필드 전체가 필수조건이라는 뜻이 아님 |

## 6. 확보 경로와 출처 표시

| 필요한 정보 | 확보 경로 | 실험에서의 취급 |
|---|---|---|
| 등록 진료과·응급실 운영·시설 수 | NMC 상세 API | `public` 관측과 원본 필드 유지 |
| 신고 전문의 수·장비 보유대수·특수진료·시설 수 | 심평원 API, 34기관 실제 연계·12종 408관측 저장 | 치료조건별 등록 근거로 연결. 신고값을 현재 당직·가용수로 사용하지 않음 |
| 응급실 운영 신고값·연락처·수용 관련 메시지 | 심평원 상세 및 NMC 메시지 API | 확인 문맥으로 제공. 자유문이나 적용 기간으로 환자 수용을 자동 확정하지 않음 |
| 병상·장비의 공개 가용 표시 | NMC 가용병상 API | `public` 관측, 입력시각·수집시각 분리 |
| 실제 환자의 치료조건 | 의료진·구급대 입력 | 사람이 확인한 입력인지 확인 필요 입력인지 구분 |
| 환자의 치료조건을 충족할 현재 전문팀 | 병원 응답·운영 입력 | `hospital_reported`; 공개 진료과 수로 추정하지 않음 |
| 응답시간·무응답·자원 점유 | 실제 운영 기록이 생기기 전에는 가상 생성 | `synthetic` 및 seed·분포·시나리오 ID 기록 |
| 예상 이동시간 | 향후 도로 경로 API | 미연결 시 근사값임을 표시하고 실측처럼 설명하지 않음 |
| 수용 확정 당시 조건과 변경 여부 | 서버 이벤트·병원 재확인 | 환자 버전·응답 유효기간·변경 사유와 함께 보존 |

같은 병원의 실제 좌표를 사용하더라도 전문팀·점유가 가상 설정이면 **그 병원의 실제 운영 상태를 재현한 것이라고 설명하지 않는다.** 공개 병원 목록과 가상 운영 상태를 결합한 실험이라고 표시한다. 실험 설정으로 공개 자료나 병원 운영 입력을 덮어쓰지 않는다.

조건의 근거를 전달할 때는 다음 항목을 남긴다.

```json
{
  "condition_id": "neonatal_intensive_care",
  "evidence_kind": "facility_count",
  "source": "public",
  "operation": "getEgytBassInfoInqire",
  "field": "hpnicuyn",
  "raw_value": null,
  "value": null,
  "source_observed_at": null,
  "fetched_at": "수집시각",
  "status": "verification_required",
  "patient_acceptance_confirmed": false
}
```

실제로 없는 시각을 생성해서 채우지 않는다. 예시의 미확인 값을 false나 0으로 바꾸지 않는다.

## 7. 현재 솔버에서 검증할 수 있는 범위

현재 솔버 어댑터는 `ed_bed`와 `special_team`만 처리한다. 전문팀 1단위는 실험용 집계값이며, 실제의 산부인과·마취과·신생아팀을 각각 확보했다는 뜻이 아니다.

- 일반 응급·정형외과·소아 프로필의 기본 수요는 현재 자원 모델과 호환된다. 그래도 유효한 병원 응답과 확인된 운영 자원이 있어야 솔버의 배정 후보로 쓸 수 있다.
- 심장 중재 프로필에는 전문시술 확인이 추가로 필요하다. 심장내과 등록·집계팀 숫자만 비교한 실험은 중재시술 조건 검증으로 설명하지 않는다.
- 뇌신경 수술·산모와 신생아 프로필은 수술실·중환자실·분만실·NICU 등 확장 자원과 서비스 조건을 함께 다뤄야 한다. 카탈로그에 적었다는 이유로 현 솔버에서 해당 교집합 계산이 구현됐다고 설명하지 않는다.
- 확장 조건을 지원하기 전에는 미지원 경고·사람 확인을 유지하고, 자원 요구를 몰래 제거해 배정하지 않는다.

즉 이번 정리의 산출물은 **실제 공개 병원 정보의 근거와 한계, 실험에 사용할 조건 묶음, 각 조건의 추가 확인 사항**이다. 임상적 적합성 검증이나 실제 병원 운영 자원 확보가 완료된 것은 아니다.

권역 수집·조건 정리와, 다양한 알고리즘을 실행해 성능을 비교하는 작업도 구분한다. 34개 병원 수집과 조건 비교 결과가 확보됐다는 사실만으로 선정시간 개선·문의 감소·임상적 성과가 검증된 것은 아니다. 현재 솔버의 병원 수 제한은 32곳이므로 34곳 전체를 한 번에 최적화하려면 제한 조정 또는 후보 축소 정책의 명시가 추가로 필요하다.

## 서비스 연결 (2026-10-11)

NMC와 심평원 자료를 함께 평가하고 병원 조회·환자 후보·배정 결과 API에 연결했다. `extra.treatment_profile_id`로 프로필을 명시하며 증상에서 자동 진단하지 않는다. 등록 근거와 현재 가용수는 분리하고 미확인 항목은 병원에 확인한다. 프로필 확장 자원도 환자 요구에 반영하며 솔버 미지원 자원은 `NEEDS_REVIEW`다. [구현·실제 수집 결과](API추가수집_치료조건판정연결_20261011.md)를 참조한다.
