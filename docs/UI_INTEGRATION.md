# 모바일·병원 화면과 공통 서버 연결

2026-10-13. `patient-ui/`와 `hospital-ui/`를 같은 공통 서버와 DB에 연결했다. 기존 역할들을 한 화면에서 대신 실행하는 `conversation-demo.html`도 보존한다.

2026-10-14 연결 재점검: 기존 두 화면에서 등록→질문·답변→수용→사람 확정·출발→대화→조건 변경·대체 문의→사람 변경→도착·퇴실을 별도 합성 DB와 실제 Chrome으로 재검증했다. 7개 흐름 통과, JS 오류·네트워크 실패0건. 추천 API는 정상 동작하며 `availability`와 병원별 입력 부족 사유를 보강했다. **추천 패널과 외부 유입 목록·개별 퇴실 버튼은 아직 UI 미구현이며 해당 기능은 API로 검증했다.** 팀원 UI 코드는 수정하지 않았다. [연결할 필드와 팀원별 작업](TEAM_RECOMMENDATION_INTEGRATION.md).

팀원 최신945c413의 원본 환자 입력 화면에서도 이 공통 이송 화면으로 이어갈 수 있다. 원본 입력 앱은 별도 FastAPI이며 동의 후 공통 서버에 환자 상태·위치를 보내 같은 이송ID로 이동한다. [원본 앱 실행과 연결](TEAM_PATIENT_CONNECTION_20261013.md)을 확인한다.

## 실행

```powershell
python -m server.chat_demo --db data/ui-integration-demo.db --port 18020
```

- 이송자: `http://127.0.0.1:18020/patient/`
- 병원: `http://127.0.0.1:18020/hospital/?hid=H04`
- 기존 건은 모바일에 `?pid=환자ID`, 병원에 `?hid=병원ID&pid=환자ID`를 붙여 연다.
- 두 화면 모두 같은 출처를 API 기본 주소로 사용한다. 별도 정적 웹 서버를 사용하면 `?server=http://서버주소:포트`를 지정한다.
- 병원 변경 작업에는 상단 담당자 이름이 필요하다. 이것은 처리 기록용이며 계정 인증은 아니다.

현재 준비된 A/B 가상 사례는 `.codex-build/ui-integration-20261013/showcase.json`에 기록했다. A만 전문팀을 필요로 하고 B는 필요로 하지 않는다. 전문팀 점유 후 A는 병원 재확인 필요, B는 조건 감시 유지 상태다. 준비 스크립트는 기존 사례를 자동 정리하지 않으므로 재실행 전 자기 사례와 점유를 확인한다.

- 준비 A: `http://127.0.0.1:18020/patient/?pid=UI-SHOW-f44fbb091c-A`
- 병원 A: `http://127.0.0.1:18020/hospital/?hid=H04&pid=UI-SHOW-f44fbb091c-A`
- 비교 B: `http://127.0.0.1:18020/patient/?pid=UI-SHOW-f44fbb091c-B`

병원에서 담당자와 판단 사유를 입력한 뒤 유지/조정을 선택한다. 조정을 진행하려면 모바일에서 현재 관측 좌표를 먼저 갱신한다. 대체 문의가 도착한 병원의 병원 화면에서 수용 응답을 보내고, 모바일에서 새 목적지를 확정한다.

`chat_demo`는 병원 목록이 없는 새 DB에만 가상 병원을 넣는다. 기존 DB를 초기화하지 않으며 실제 공공 DB와 섞지 않는다. 이번 실행은 실제 지도·의료 API를 호출하지 않고 합성 이동 추정을 사용한다. 배정 솔버 워커를 사용하는 운영 실행과도 구분한다.

## 파일과 역할

| 영역 | 구현 |
|---|---|
| 모바일 | `patient-ui/index.html`, `styles.css`, `app.js` |
| 병원 | 기존 `hospital-ui/index.html`의 문의 화면에 탭과 기능 추가 |
| 같은 서버에서 제공 | `server/app.py`의 `/patient/`, `/hospital/` 정적 경로 |
| 업무와 저장 | 기존 공통 API와 SQLite DB, 초기 문의·조건 재확인 워커 |

환자 연결본은 팀원 커밋 `181b99a613b943eed661ec8bc0f35bf9b71814d0`의 시작 화면과 등록 화면의 표현을 이어받았다. 기존 FastAPI 앱·미리보기 복사본·`emergency.db`는 수정하거나 가져오지 않았다. 연결본에는 별도 DB가 없고 환자 상세 정보는 URL로 전달하지 않는다.

## 연결된 흐름

1. 모바일에서 확인한 환자 상태·치료 요구·위치를 입력하고 동의 후 공통 서버에 저장한다. 미확인은 그대로 저장한다.
2. 후보 병원에 직접 문의하거나 공개 정책으로 서버 자동 문의를 시작한다. 모바일은 문의·회신·불가·질문을 확인한다.
3. 병원에서 추가 질문을 보내고 모바일에서 답한다. 병원은 별도 수용 응답을 전송한다.
4. 모바일에서 유효 응답으로 목적지를 확정하고 별도로 출발한다. 확정 후 해당 병원이 대화에 참여한다.
5. 이송자가 조건 감시를 켠다. 병원은 자원 변경과 가상 돌발 유입을 등록하고 환자별 재확인 사유를 확인한다.
6. 병원은 최신 검토 버전과 위험 해시로 유지/조정 판단을 전송한다. 조정 후 서버가 대체병원에 문의한다.
7. 새 병원의 수용 응답을 확보해도 기존 목적지는 유지한다. 모바일에서 사람이 변경해야 새 병원이 대화에 참여한다.
8. 병원이 도착·퇴실을 확인한다. 모바일 상태와 점유가 갱신되고 대화는 읽기 전용이 된다.

자유채팅은 수용·출발·조정·목적지 변경을 처리하지 않는다. 임상 입력 버전이나 배정 계산도 바꾸지 않는다. 직접 입력한 좌표 관측의 갱신을 제공하며 GPS 자동 수집으로 표시하지 않는다.

## 검증 범위

실제 Chrome의 독립 모바일·병원 화면에서 전체 흐름을 조작했다. 메시지 HTML 원문은 텍스트로 표시했고, 응답 유실 후 동일 ID 재전송은 한 번만 저장됐다. 자원이 다른 A/B 영향 분리, 오래된 병원 판단의 409 거부, 목적지 변경 후 이전 병원의 새 대화 차단, 200개를 넘는 메시지의 페이지·순서·중복 처리, 도착·퇴실 후 읽기 전용을 확인했다. 390px 모바일에서 새로고침 후 변경 대기 상태와 가로 넘침도 확인했다.

검증 스크립트와 결과는 `.codex-build/ui-integration-20261013/qa.cjs`, `qa-report.json`에 있다. 최종 **12개 브라우저 검사 모두 통과**했고 오류·정리 실패는 없었다. 이전 9개 전체 흐름 검사는 `qa-report-initial.json`에 보존했다. 환자 전환의 좌표 초기화와 저장 지연 중 문맥 전환 방지, 자동 문의 시작·중지도 실제 화면에서 확인했다. 같은 서버의 정적 파일 제공·경로 밖 접근 차단을 포함한 서버 회귀 **277개 통과**. 로그는 같은 폴더의 `tests.log`다.
