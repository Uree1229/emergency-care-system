# 메인 음성·이송과 검토·추천·알림 연결

2026-10-30. 잔여 작업 1·2번의 **로컬 구현과 합성 기능 검증을 완료했다.** 기존 서버 API·솔버·운영 배정 기준을 유지하며 구급대 메인, 환자 진행, 병원 화면을 연결했다. 새 알고리즘 후보나 성능 비교실험은 추가하지 않았다. 실제 마이크·휴대폰·사람 대상 사용성 측정과 최종발표 제작은 별도 범위다.

## 연결한 업무 흐름

| 구간 | 이번 연결 |
|---|---|
| 간편 음성→메인 | 기존 같은 초안 전달·버전 확인을 보존. 실패 시 빈 초안으로 대체하지 않음 |
| 메인 확인 질문 | 최신 질문·직접/음성 답변·읽기·미측정·검토 보류·변경 전후를 표시. 보류와 미측정을 구분하고 빈 값을 정상이나 0으로 채우지 않음 |
| 최초 환자 등록 | 위치·동의·기록 확인 후 명시 등록. 반환된 같은 환자 ID·작업자로 진행 화면 연결 |
| 대기 환자 수정 | 일반 submit으로 우회하지 않고 치료조건 조회·선택 미리보기·토큰/두 버전 확인·명시 적용 사용. 감소하는 조건은 별도 확인 |
| 확정·이송 중 수정 | 일반 등록·적용을 차단하고 같은 환자·작업자의 별도 임상변경 검토 화면으로 연결. 현재 병원의 판단 후 반영하는 기존 절차 유지 |
| 환자 진행 | 추천 상태·워커 가동 여부·현재 입력 검토·명시 재계산과 같은 환자의 음성/임상변경 링크 제공 |
| 병원 검토 | 선택 환자의 추천과 현재 입력 검토를 표시. 미확정 문의의 입력 안내도 별도 현재 조회로 확인 |
| 중요 알림 | 양쪽 화면에서 새 사건 페이지 조회·중복 제거·미확인 복원, 표시 수신과 사용자의 확인 동작을 분리 |

새 환자 등록은 자동 문의 시작·병원 수용·목적지 확정과 별개다. 진행 화면에서 문의를 명시적으로 시작하고, 병원의 유효한 응답을 사람이 확정한다. 추천 카드가 실패하거나 워커가 비활성이어도 기존 수동 수용 확정 경로를 막지 않는다.

이송 중 임상변경은 별도 화면에서 현재 정보로 초안을 연결해 변경안을 작성하고 병원 판단을 받는다. 메인에서 일반 환자 등록을 다시 여는 경로가 아니다. 이 별도 화면의 복귀 링크도 같은 환자 ID와 작업자를 유지한다.

## 검토와 오래된 상태 처리

- 대기 중 적용은 현재 음성 세션·환자 ID와 각각의 버전, 검토 토큰, 선택을 사용한다. 입력·선택·버전이 달라지면 이전 변경안과 확인 체크를 폐기한다.
- ‘기존 치료조건 유지’를 고른 상태에서 조회·초안 확인을 해도 실제 미리보기와 전송 선택을 `keep`으로 유지한다. 서버 제안이 없으면 기존 유지안을 표시한다.
- 조건 감소·제거는 별도 확인이 필요하다. 409이면 최신 상태와 변경안을 다시 조회하고 확인 체크를 해제한다.
- 응답 유실 시 원래 요청 ID·본문을 유지해 재시도한다. 불확실한 요청이 남은 상태에서 다른 환자나 요청으로 바꾸지 않는다.
- 추천은 `READY`와 현재 버전·기한을 만족할 때만 내용을 사용한다. `STALE`·만료·환자/서버 전환 시 이전 내용을 제거한다. 도착·종료 후에는 추천 대상 아님으로 표시한다.
- 워커 `DISABLED`·`STOPPED`와 계산 대기 상태를 구분하고 명시 재계산 버튼을 제한한다. 추천은 예약·수용 확답·목적지 변경 명령이 아니다.
- 현재 입력 안내는 현재 조회값만 사용한다. 저장된 과거 추천의 `result.input_review`를 현재 값으로 대신 표시하지 않는다.

치료조건은 필요한 진료·자원·우선순위와 변경 전후를 한글 항목으로 정리하고 원래 코드·프로필 ID도 보존한다. 기존 환자의 검토 영역은 넓게 표시하며 사이드바는 작은 화면 높이에서 스크롤할 수 있다.

## 알림 수신·확인의 의미

GET 성공만으로 수신을 기록하지 않는다. 문서가 보이고 해당 사건 행이 화면과 스크롤 영역에 실제 표시된 뒤 `delivered`를 기록한다. 담당자가 확인 버튼을 눌렀을 때만 `acknowledge`를 기록한다. 알림 확인으로 수용 유지·조정·목적지 확정을 실행하지 않는다.

환자·병원·서버·작업자·화면 세대가 바뀌면 이전 응답을 버린다. 일반 사건 커서와 과거 미확인 조회는 분리한다. 복귀·온라인 복구 때 미확인을 다시 읽으며, 실패한 수신/확인 요청은 같은 범위·사건·본문으로 재시도한다. 다른 사건의 성공이나 단순 GET 성공으로 미해결 오류를 숨기지 않는다.

환자 진행·음성 연결의 작업자 ID는 음성 API와 같은 **영문·숫자 시작, 영문/숫자/`.`/`_`/`:`/`@`/`-`, 1~80자**를 사용한다. 잘못된 query·저장값·수동 입력은 그대로 보여 주고 오류를 안내한다. 다른 ID로 자동 교체하지 않으며 해당 알림·연결 동작을 제한한다. 작업자 ID는 시연용 식별자이고 로그인·권한 인증을 대신하지 않는다. 병원은 담당자 이름과 별도 생성 식별자를 사용하며, 중요 알림의 식별자를 기존 통화·계측 식별자와 구분한다.

브라우저는 이 PC의 1280×720 환경이다. 입력은 합성 인식문을 직접 입력한 기능 검사이며 마이크나 새 STT 정확도 시험이 아니다. TTS의 실제 발음·하드웨어 버튼·안드로이드·다른 물리 PC·실제 사용자 업무시간은 이번 결과에 포함하지 않는다. UI 검사 성공을 임상 안전성·병원 부담 감소·알고리즘 우월성으로 해석하지 않는다.

검증 자료는 `.codex-build/main-workflow-20261030/`에 있다. `focused-tests-final.tap`, `browser/patient-before-apply.json`, `patient-after-apply.json`, `treatment-keep-selection.json`, `new-patient-route.json`, `full-db-verification.json`과 최종 검증 기록을 함께 보존한다. 테스트 DB는 각 새 실행 폴더의 `synthetic-ui.db`이며 기존 업무 DB를 초기화하지 않았다.

## 실행과 확인 주소

정규 공통 실행은 [팀 공통 실행](TEAM_COMMON_RUNTIME_20261030.md)의 full 모드를 사용한다. 이 작업의 격리 검증 서버가 켜져 있는 동안에는 다음 주소로 볼 수 있다.

- [메인 음성·기록 화면](http://127.0.0.1:18049/paramedic/).
- [기존 대기 환자 진행 화면](http://127.0.0.1:18049/patient/?pid=ER-W1&actor_id=workflow-crew).
- [병원 화면](http://127.0.0.1:18049/hospital/?hid=ER-H1).

각 화면의 현재 환자·서버·작업자와 워커 상태를 확인한다. 시연 자원과 수용 응답에는 유효시간이 있어, 저장 당시 성공한 추천을 나중에도 유효하다고 가정하지 않는다. 이미 소비된 시연 상태는 그대로 보존한다.

새 격리 DB가 필요한 경우에만 다른 빈 폴더와 포트를 지정한다.

```powershell
$workflowPython = 'C:\Users\PC\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe'
& $workflowPython -X utf8 .codex-build/main-workflow-20261030/start_demo.py --output .codex-build/main-workflow-20261030/new-fixture --port 18050
```

기존 출력은 거절하고 로컬 주소에만 바인딩한다. 검증기는 합성 자료와 거리 추정을 사용하며 외부 병원·길찾기 API를 호출하지 않는다. 이 검증 서버의 준비를 팀 최종 공유본 배포나 다른 PC 설치 완료로 세지 않는다.
