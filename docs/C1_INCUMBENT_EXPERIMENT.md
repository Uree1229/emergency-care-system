# C1 시간 부족 시 초기 배정안 보강 실험

앞선 실험에서 실제 50ms C1이 모델 구성 중 예산을 소진해 단순 탐욕 배정으로 돌아가고, 같은 입력의 과거 최적 배정보다 한 환자의 처치가 35분 늦어진 기록을 확인했다. 이번 단계는 미채택 조기 확정 정책과 분리해, 원래 normal 문의·확정 흐름에서 C1의 대체 배정안을 보강한다.

## 변경

원래 탐욕 배정에서 미배정 환자 한 명이 갈 수 있는 병원에 다른 환자가 배정되어 있다면, 그 환자를 실제 유효 수용 응답이 있는 다른 병원으로 옮겨 두 명을 모두 배정하는 첫 유효 개선안 하나를 저장한다. 기존 배정 환자를 탈락시키지 않고, 전체 자원 제약과 원래 사전식 목적함수를 다시 검사한다. 미래 환자·추가 자원 보고는 사용하지 않는다.

후보 검사는 최대 128개, 초기해 준비는 최대 5ms로 제한한다. 초기해·모델 구성·두 단계 CP-SAT는 lazy import 이후 시작하는 동일 예산을 공유한다. 초기해를 warm hint와 fallback으로 쓰며, 더 나쁜 solver incumbent는 채택하지 않는다. 초기해는 최적성 증명이 아니다.

원래 greedy와 Stable의 동률 처리 본문, snapshot, solver 호출 함수, normal Replay 클래스는 그대로다. solver가 계산한 현재 모델의 1차·2차 최적성만 각각 별도 증명 플래그로 기록한다. 초기해의 기존 환자 보존은 최종 CP-SAT가 모든 이전 탐욕 배정을 고정한다는 뜻이 아니다.

이는 협력적 시간 제한이다. OS가 계산 도중 멈추는 상황의 실제 wall time 상한이나, 더 복잡한 여러 환자 교환을 보장하지 않는다.

## 사전 고정과 범위

기존 149가족은 그대로 두고 실제 1ms 예산 경계 6가족을 추가했다. 개발 44101~44103의 465환경, 신규 501분기, 완전한 과거 원문·감사 894분기를 사용했다. 과거 실행을 신규 실행이나 신규 CPU로 세지 않았다.

C1의 old/new는 같은 환경에서 같은 예산을 사용한다. 일반 50ms와 실제 1ms 스트레스는 별도 표로 집계한다. H1은 원래 50ms의 진단 기준이며 1ms C1과 예산을 맞춘 우열 비교가 아니다. 문의 정책·조기 확정·물리 자원·보고 주기는 변경하지 않았다.

1차 기준은 기존 성공 상실·개인 처치/최종 도착 악화·환경별 순대기/제한 처치/문의 증가가 모두 없고, 전체 순대기와 제한 처치 합이 엄격히 감소하는 것이다. 두 예산 계층을 합친 개발 기준이므로, 1ms의 이득만으로 통과해도 일반 50ms 성능 향상을 뜻하지 않는다. 운영 채택은 이번 실험의 평가 대상이 아니다.

자동 검사 2595개와 seed7 167분기의 전체 원문 감사를 통과했다. 기존 선택적 로컬 HTTP 검사 6개 제외는 유지했다. 실제 seed7 첫 시도 8분기/5개 고정 fixture도 보존했다. controlled-clock 단위 fault test와 실제 native 실행 결과를 구분했다.

예약 54101~54106은 과거 JSON/JSONL/gzip seed 필드 감사를 완료한 뒤 소스를 고정하고 입력만 생성했다. 개발 기준이 실패하면 예약 성능 실행은 하지 않는다.

## 초기해와 실제 solver 결과

| 조건 | 초기해 검사 기록 | 실제 증강 | 기존 C1 fallback | 새 C1 fallback |
|---|---:|---:|---:|---:|
| 일반 50ms | 733 | 21 | 1 | 2 |
| 스트레스 1ms | 39 | 15 | 0 | 0 |

일반 50ms의 새 C1 실제 wall 최대 1118.824ms, 공유 deadline 초과 최대 76.823ms. wall은 lazy import·snapshot 등을 포함하며 동일 예산은 실제 wall 상한을 뜻하지 않는다. 이는 신규 실행 기록의 시간이며 cache의 시간을 신규 CPU로 세지 않았다.

스트레스 1ms의 새 C1 실제 wall 최대 1.276ms, 공유 deadline 초과 최대 0.188ms. wall은 lazy import·snapshot 등을 포함하며 동일 예산은 실제 wall 상한을 뜻하지 않는다. 이는 신규 실행 기록의 시간이며 cache의 시간을 신규 CPU로 세지 않았다.

모든 native 실제 결과와 fallback을 포함했다. 불리한 결과의 재실행·제외는 하지 않았다. 일반 50ms의 과거 cache와 현재 실행은 동일 wall-clock 실현이 아니므로, 모든 차이를 초기해 효과로 귀속하지 않는다.

`c1_incumbent_chain_limit` 가족은 실제 seed7에서 일부 환자의 준비 시점이 달라 단일 교환이 가능했다. 이 이름만으로 실제 두 blocker 필요 상황이 검증되었다고 주장하지 않는다.

이 표의 이전 reserve는 미채택 조기 확정 실험의 실제 원문이며 이번 primary 기준은 과거 normal C1이다. 과거 35분 악화가 나온 native 스케줄링을 강제로 재현하거나 반복해 유리한 실행을 고르지 않았다. 동일 모델 확인과 이번 실제 초기해 적용은 전체 미래 결과의 개선 보장이나 강제 시간초과 시험이 아니다.

## 판정

개발 1차 기준: 미통과. 실패 항목: strict_total_wait_reduction, strict_capped_treatment_reduction.

개발 기준 미통과로 예약 성능 검증은 생략했다.

`adopted=False`, 운영 기본 `fixed_3` 유지. 병원/환자 앱·서버·DB에 적용하지 않았다. safe/protected와 이전 미채택 조기 확정 정책의 완전 증거는 보존했으며 이번 새 우열/운영 채택 주장의 범위에는 포함하지 않았다.

## 증거 보존

기존 과학 소스 211개와 봉인된 실행 원문·감사 증거는 그대로 유지했다. 선행 봉인 이후 다른 작업이 `docs/README.md`에 267바이트의 문서 링크 한 줄을 추가한 사실은 별도 명시했다. 현재 파일을 되돌리지 않고 6,977바이트 원본과 7,244바이트 현재본을 각각 해시와 함께 보관했다. 따라서 모든 과거 원래 경로의 바이트가 불변이라고 주장하지 않는다.

- `simulation/c1_incumbent_{assignment,engine,audit,scenarios,experiment}.py`: 구현·원형 단계·독립 감사·입력·사전 비교 계약.
- `simulation_results/c1_incumbent_development_20261020.json`과 `_cases/`: 최초 실제 실행 원문과 cache 증명.
- `.codex-build/c1-incumbent-20261020/development-independent-audit.json`: 모든 신규 분기 재감사와 사건 기반 대기·업무 집계.
- 같은 build의 `pre-development-freeze.json`, `preservation/`, `seed-audit/`, `verification.json`: 사전 고정·문서 예외 명시·예약 seed 감사·최종 봉인.

## 결과가 같았던 이유: 사후 진단

초기해가 원래 greedy보다 개선된 기록은 일반 50ms 21회, 1ms 15회다. 기존 C1의 최종 해보다 개선되었다는 뜻은 아니다. 실제 1ms 18환경의 대응 배정 39쌍에서 입력·자원 근거·제안·실제 배정·목적값·gate·사건 순서가 모두 정확히 같았다.

정식 1ms에서는 old/new C1 모두 fallback이 0회였다. 따라서 이 개발 실험은 실제 fallback 시 환자 개선 효과를 관측하지 못했다. seed7 사전 진단의 실제 fallback과 controlled-clock 단위 시험은 별도 증거로 남기며 정식 결과를 대체하지 않는다.

1ms 최적성 상태는 기존 OPTIMAL 19/1차만 증명 20, 새 OPTIMAL 29/1차만 증명 10이었다. 대응 배정에서는 증명이 강화된 12회와 약해진 2회가 있었다. 순증가를 일관된 속도 향상이나 임상 성능 개선으로 해석하지 않는다.

과거 35분 사례에서는 같은 현재 모델에 대해 모델 구성 전에 좋은 초기해를 확보했다는 기계적 증거가 있다. 이번 비교 기준 normal은 이미 좋은 해였고 새 실행도 최종 최적해를 찾았다. 과거 실패를 강제 재현하지 않았으므로 알고리즘만으로 35분을 단축했다는 새 성능 결론은 낼 수 없다.

이 진단은 정식 결과를 확인한 뒤 시행한 읽기 전용 분석이다. 규칙·시간 예산·채택 기준을 바꾸거나 성능을 재실행하지 않았다.
