# 기준 배정 알고리즘 동결과 음성→배정→조건 변경 연결 검증

2026-10-30. 서버 담당 작업이다. 기존 알고리즘의 목적함수·기본값은 변경하지 않았고, 새 동결 검사 도구와 전체 흐름 검증 도구를 추가했다. Claude의 UI·음성 해석 코드, 기존 실행 서버와 시연 DB는 수정하지 않았다.

## 1. 고정한 기준

기준 ID는 `server-allocation-baseline-20261030-v1`이다. **현재 서버에서 실제로 사용하는 경로**를 고정했다. 연구용 G2/G5·문의 개선 후보를 운영 기본값으로 교체한 작업이 아니다.

| 항목 | 고정 내용 |
|---|---|
| 최초 문의 | `fixed_3`, 버전 `1`: 동시 3곳, 대기 60초, 최대 10곳, 작업 제한 300초 |
| 배정 계산 | `server.worker.bounded_solve → solver_improved.solve`, CP-SAT `severity_first` |
| 목적함수 | 실험 우선순위 가중치 4→2→1 순으로 미배정 수를 사전식 최소화한 뒤, 같은 군 순으로 시작시각−발생시각 합 최소화 |
| 계산 제한 | 기본 3초, 단일 탐색 작업자·난수 seed 0, 시간제한 시 기존 검증된 순차 대체 해 사용 |

| 모델 기본값 | 시간창 120분, 처치 1,800초, 대기 3,600초. 분 단위 정수화 |
| 시제품 크기 제한 | 환자 64명·병원 32개 초과 등은 검토 필요로 처리 |
| 목적지 | 추천과 확정은 별도. 확정 목적지는 잠금 유지, 대체 수용과 담당자 변경 절차 필요 |
| 실행 환경 | Python 3.12.14, OR-Tools 9.15.6755, SQLite 3.53.1 |

시간·가중치·규모 제한은 프로젝트 실험 설정이다. 임상 중증도·허용 대기시간·안전성을 검증한 기준이 아니다.

잠금 파일: `config/server_allocation_baseline_20261030.json`. 솔버·서버 어댑터·자원 집계·치료조건·문의·이송 재확인 등의 **핵심 21개 파일** SHA-256과 설정·실행 환경을 기록했다.

최종 manifest digest:

```text
642e0cf3b18c9129a3ac17af9cbc7d04e9cda12d47093a5af1b773b03290ac0d
```

검사는 읽기 전용이다. 코드·설정·라이브러리가 달라지면 실패와 변경 목록을 반환하며 잠금 파일을 자동 갱신하지 않는다. 실행 중 서버를 막거나 다른 개발자의 변경을 되돌리는 장치는 아니다. CLI 인자·DB별 문의 정책을 자동 강제하지도 않으므로 검증 실행에서는 3초·`fixed_3` 사용을 별도로 기록했다.

Claude 담당 음성 파서와 UI는 알고리즘 동결 대상에서 제외했다. 음성·API 연결 의존 소스는 이번 실행 전후에 별도로 비교하고 사본을 보존했다. 공용 DB·서비스 파일 변경도 잠금 불일치로 나타날 수 있으므로 이후에는 변경 내용을 검토하고 별도 기준 버전을 추가한다. 기존 v1 결과를 새 결과로 덮어쓰지 않는다.

## 2. 전체 흐름 검증 결과

**최종 9개 시나리오·114개 확인 항목 통과.** 새 합성 DB·로컬 HTTP 서버에서 실제 업무 API와 문의·배정·대체 문의 코드를 사용했다. 시각은 통제하고 워커 주기를 직접 호출해 재현성을 확보했다. 가짜 솔버 응답을 주입하지 않았다.

| 시나리오 | 확인한 핵심 결과 | 최종 상태 |
|---|---|---|
| 정상 등록·이송 | 음성 초안→확인→제출→문의→병원 수용→추천→담당자 확정→출발→도착. 도착 예정 수요와 실제 점유 중복 없음 | `ARRIVED` |
| 확정 전 치료조건 변경 | 미제출 초안은 기존 수용에 영향 없음. 명시 적용 후 옛 수용 종료·과거 추천 무효·새 조건 문의와 수용 뒤 재추천 | `ARRIVED` |
| 이송 중 자원 변화·수용 유지 | 감시를 명시 활성화한 뒤 부족 감지·재확인 사건 조회. 병원의 `keep` 판단으로 기존 목적지 유지 | `IN_TRANSIT` |
| 이송 중 자원 변화·목적지 변경 | 오래된 판단 409 거절→병원 `adjust`→대체 문의. 새 수용 전 변경 거절, 새 수용만으로도 자동 변경 없음. 현재 위치와 담당자 변경 후 도착 | `ARRIVED` |
| 선택 항목 미측정 | 혈압 확인 불가를 참고 정보로 표시하고 기존 유효 수용·확정 가능 여부 유지 | `WAITING` |
| 병원 미응답 | 문의 제한시간 종료 후 담당자 확인 필요. 미응답을 거절·수용으로 바꾸거나 임의 확정하지 않음 | `WAITING` |
| 가용 자원 없음 | 새 문의·수용·배정을 만들어내지 않고 탐색 종료·미배정 상태 반환 | `WAITING` |
| 오래된 치료조건 승인 | 초안이 바뀐 뒤 옛 검토 토큰 적용은 409 거절. 환자 버전과 기존 수용 유지 | `WAITING` |
| 첫 문의 필수 입력 누락 | R1 필수 5칸 누락 시 409. 환자·문의가 부분 생성되지 않음 | `NO_PATIENT` |

실제 `worker.run_once(..., seconds=3)` 계산은 **10회**였다. 이번 작은 합성 입력에서는 모두 `OPTIMAL`, `fallback=false`, `lex_optimal=true`를 반환했다. 이 결과로 대규모 입력의 최적성이나 현행 체계 대비 우위를 주장하지 않는다. 각 계산의 전체 메타데이터를 보존했다.

다음 경로는 구분해서 검증했다.

- **목적지 확정 전:** 음성 변경 → 치료조건 미리보기·확인 → 원자적 적용 → 기존 수용 종료 → 새 버전의 문의·수용 → CP-SAT 재추천.
- **목적지 확정·이송 중:** 병원 조건 변화 → `transport-review` 재확인 → 병원 `keep/adjust` 판단 → 별도 대체 문의 → 새 수용 → 담당자의 `change-destination`.

CP-SAT이 이송 중 목적지를 자동으로 바꾼 것으로 표현하지 않는다. 현재 음성 치료조건 적용 API는 `WAITING` 환자 대상이며 이송 중 환자의 음성 임상정보 수정까지 구현했다고 주장하지 않는다.

## 3. 회귀와 재현 근거

관련 서버 회귀 **559개 통과**, 실패·오류 0개, 검사 전후 대상 소스 해시 일치. 기존 531개에 기준 잠금 15개·음성부터 이송 조건 변경까지 HTTP 통합 5개·재현 도구 보호 검증 8개를 추가했다.

도구 보호 검증에는 기존 출력 폴더 재사용 거절, 기준 변경 시 DB 생성 전 중단, 시나리오 실패 보존, 의존 소스 변경·최종 해시 조회 오류의 전체 실패 처리, 초기 서버 시작 실패 시 열린 DB 정리가 포함된다. 이송 통합 검증에는 특정 자원을 쓰는 환자만 영향 표시, 신규 여유 0과 기존 확정 수요 구분, 오래된 병원 판단 거절도 포함된다.

최종 실행에는 다음을 보존했다.

- `protocol.json`: 실행 전에 정한 시나리오·기준 digest·계산 예산·문의 정책·이동시간 제공자·시각 제어 방식.
- `report.json`: API 호출 상태, 확인 항목, 솔버 상태·대체 해·최적 증명 여부, 기준 검사, 소스 해시.
- `report.md`: 시나리오별 결과 요약.
- `sources/`: 이번 연결 검증에 사용한 서버·설정·필수 의존 **69개 파일** 사본. 핵심 기준 21개와 범위가 다르다.
- 시나리오별 `fixture.db`: 합성 데이터만 들어 있는 독립 DB.

최종 실행 폴더는 `.codex-build/voice-allocation-e2e-20261030/final-run`이다. 개발용 최초 실행은 `development-run-01`에 별도로 보존했다. 두 실행을 서로 다른 환자 모집단의 성능 검증 표본으로 합산하지 않는다.

전달용 보고서·잠금·소스 압축 사본은 `outputs/allocation_baseline_e2e_20261030/`에 있다. 합성 DB는 전달본에 복제하지 않았다. 전체 회귀의 개별 파일 해시는 `server-verification.json`에서 확인할 수 있다.

## 4. 재실행

동결된 소스와 위 실행 환경이 있는 프로젝트 루트에서 실행한다.

```powershell
python -m server.allocation_baseline check --json
python -m server.voice_allocation_rehearsal --output .codex-build/voice-allocation-e2e-new-run
```

출력 폴더는 반드시 새 경로여야 한다. 기존 폴더·기존 DB·외부 서버 주소를 지정해 재사용하는 기능은 제공하지 않는다. 시나리오 또는 무결성 검사 실패 시 종료 코드는 1이다. 기준 검사 자체가 실패하면 새 검증 DB 생성 전에 중단한다.

이번 추가 회귀만 실행하려면 다음을 사용한다.

```powershell
python -m unittest test_allocation_baseline test_voice_allocation_transport_flow test_voice_allocation_rehearsal -v
```

기존 559개 통합 회귀의 실행기와 상세 로그는 `.codex-build/voice-allocation-e2e-20261030/verify.py`, `server-verification.json`, `server-verification.log`에 있다.

## 5. 이 검증 이후 남는 작업

이번 결과는 **기능 연결과 상태 일관성** 검증이다. 실제 마이크/STT, Claude UI 조작, 실제 병원의 응답·자원 갱신, 카카오 도로 이동시간, 앱 푸시 전달 완료, 의료진 사용성·임상 효과는 시험하지 않았다. 최초 음성 입력은 합성된 인식 텍스트를 API로 보냈다. 병원 응답과 구급대원의 확인은 역할을 대신한 API 호출이다.

다음에는 이 동결 기준을 유지하면서 UI 담당자가 같은 API 순서를 연결하고 실제 마이크부터 확인한다. 알고리즘 성과 비교는 별도의 미사용 데이터와 사전 지표로 진행해야 하며, 이번 9개 기능 시나리오를 속도 개선·예후 개선의 통계 근거로 사용하지 않는다.
