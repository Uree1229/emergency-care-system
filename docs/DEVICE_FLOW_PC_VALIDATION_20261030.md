# 전체 흐름·오류 복구의 PC 검증

**현재 PC의 앱내 브라우저에서 전체 흐름과 복구를 확인했고, 발견한 병원 작업자 재시도 문제를 수정했다.** 사용자가 지금은 이 PC만 사용할 수 있다고 답해 휴대폰·다른 물리 기기 시험은 진행하지 않았다. 따라서 잔여 4번 전체 판정은 **부분 완료**다. 실제 사람의 발화·마이크·소음이나 의료 현장 성능을 측정한 결과가 아니다.

## 사용한 버전과 범위

- 전체 업무 흐름: `team-common-20261030-v1`, 소스 ID `team-20261030-8a6c4b3c1386ff24`의 별도 사본·새 합성 DB.
- 수정본: `team-common-20261030-v1.1`, 소스 ID `team-20261030-9959804fc7d6d55a`. v1에서 병원 작업자 재시도 관련 소스·테스트 3개와 버전 문서 3개만 변경했다. 이후 개발 폴더의 다른 음성·지도 변경은 포함하지 않았다.
- Python 3.12.14 / SQLite 3.53.1 / 고정된 10개 의존성, full 문의·배정 워커 실행. 운영 정책은 `fixed_3 + CP-SAT severity_first, 3초` 유지.
- Windows PC의 ChatGPT 앱내 브라우저, 관측 화면 1265×720. 별도 Whale 창 제어는 도구 연결에 실패해 그 브라우저의 동작을 검증했다고 세지 않았다.
- 응답 유실·지연·503은 시험용 loopback 프록시로 재현했다. 실제 Wi-Fi 단절이나 휴대폰의 절전·네트워크 전환 시험과 다르다. 방화벽·CA 신뢰·네트워크 설정은 변경하지 않았다.

## 실제 화면에서 통과한 흐름

새 합성 환자 `VOICE-c05f0a3a88824b12ab165174fbe726ea`를 직접 입력·등록했다. 등록 전 환자 0건에서 **1건만 생성**됐고, 같은 ID로 아래 단계를 수행했다.

| 단계 | 확인한 결과 |
|---|---|
| 입력·등록 | R1 항목을 검토·확인한 뒤 합성 위치·동의를 명시해 등록 |
| 문의·수용·추천 | 실제 문의 워커가 3곳에 문의, H01의 수용 응답 이후 CP-SAT 추천 생성. 수용·추천만으로 목적지는 바뀌지 않음 |
| 확정·출발 | 구급대 화면에서 H01을 명시 확정하고 출발·조건 감시 활성화 |
| 임상변경 요청 | 맥박 90→120 관찰을 별도 변경안으로 전송. 병원 판단 전까지 환자 원본 맥박 90·목적지 H01 유지 |
| 병원 검토 | 최신 조건을 다시 확인하고 조정을 명시 결정. 새 관찰 반영 후에도 목적지는 H01 유지 |
| 대체 수용·변경 | 현재 관측 위치를 직접 갱신하고 H02 운영 자원을 값을 보존해 재확인. H02 수용 후에도 H01을 유지하다 담당자의 목적지 변경 버튼으로만 H02로 변경 |
| 도착 | H02 병원 화면에서 도착 확인. 최종 **ARRIVED, 환자 버전 7, H02, 환자 총 1건** |

화면 조작은 브라우저 도구로 수행했고, 별도 읽기 전용 DB 조회와 프록시의 요청·응답 해시로 대조했다. 실제 이동·GPS·실제 병원의 수용 판단이 아니다. [도착 화면](../.codex-build/device-flow-20261030/browser/arrived-viewport.png), [최종 읽기 기록](../.codex-build/device-flow-20261030/R-v1-final-readonly.json)에 증거를 보존했다.

## 오류·복구

| 상황 | 실제 관측 |
|---|---|
| 입력 저장 응답 유실 | 서버 응답을 끊은 뒤 같은 요청 재시도. 같은 요청 본문 해시, 발화 1건·초안 버전 2 유지 |
| 등록 응답 유실 후 새로고침 | 기본 메인 URL에서 같은 초안·등록 환자 복원. 환자 1건 유지 |
| 정상 초안 새로고침 | 저장된 같은 초안과 입력 필드 복원 |
| 수용 버튼 중복 클릭 | 응답을 6초 지연하고 실제 더블클릭. 처리 중 버튼 비활성, 해당 POST는 1회 |
| 임상변경 요청 유실·복귀 | 새로고침 뒤 원래 요청 보존. 다른 구급대 작업자는 HTTP 전에 차단, 원 작업자로 복귀하면 같은 본문·ID로 저장 결과 복구 |
| 오래된 검토 409 | 자원 관측이 600초를 넘어 조건 토큰이 바뀐 경우 이전 판단 차단. 기존 환자정보 보존. 최신 목록을 수동 조회·재확인한 뒤 적용 |
| 알림 수신·확인·복귀 | H02 목적지 변경 알림의 표시 수신과 명시 확인 시각을 따로 기록. 미확인 조회로 복귀. 알림 확인 자체가 수용이나 목적지 변경을 실행하지 않음 |
| 일시 503·재연결 | 환자 조회를 한 번 차단해 오류 표시 확인. 다시 조회하면 같은 ID의 ARRIVED 상태 복구 |
| 병원 담당자 변경 후 재시도 | v1 결함 재현 후 v1.1에서 다른 담당자·새로고침 기본 담당자의 재시도 차단, 원래 담당자 ID로 돌아왔을 때만 정확한 요청으로 복구 |
| 서버 종료·재기동 | 실제 시험 서버를 정상 종료해 화면의 접속 실패 확인. v1.1을 같은 원 DB로 다시 켜고 기존 화면에서 같은 ARRIVED v7/H02 환자 복구. 업무 데이터 해시·환자 1건·원본 시각 보존, 자원 시각 자동 갱신 없음 |

처음 409였던 응답을 끊은 경우는 **저장 성공의 복구**로 세지 않았다. 후속 최신 검토의 200 응답 유실과 구분했다. 409는 자원 나이가 601초가 된 사건과 토큰 구성·서버 응답으로 교차 확인했다.

## 수정한 문제

v1은 임상변경 결정 요청의 병원 담당자 A를 본문에 보존했지만, 화면의 병원 담당자를 B로 바꿔도 A의 요청을 재전송할 수 있었다. 서버 기록이 B로 바뀐 것은 아니지만 현재 화면의 담당자와 재시도 주체가 달랐다.

v1.1은 **기존 pending 본문의 원 병원 담당자**를 확인한다. 담당자를 바꾸면 병원 승인 체크를 해제하고 원 ID를 안내한다. 다른 담당자·새로고침 기본값은 HTTP 전에 차단한다. 구급대 변경안 전송의 작업자 범위는 별도로 유지하고, 원 요청의 ID·본문·버전·토큰을 바꾸지 않는다. 기존 v1 형식의 보존 요청도 처리한다.

수정본의 별도 합성 fixture에서 결정 응답을 끊은 뒤 B로 변경·재시도, 새로고침·기본 담당자 재시도, A 복귀·정확 재시도를 실제 화면으로 확인했다. 이 fixture의 사전 설정은 API로 수행했으며, 앞의 전체 화면 흐름과 구분한다. 화면 회귀 **1,065개 통과**, 서버·버전 회귀 **57개 통과·Windows 심볼릭 링크 권한 1개 생략**. 임시 DB를 배포 폴더 안에 만든 첫 검사 실패는 보존하고, 별도 개발 검사 사본에서 재검사했다.

[v1.1 실행본 ZIP](../outputs/team_release_20261030/team-common-20261030-v1.1.zip)은 429개 소스 파일과 검증 요약을 담고, 압축 해제 후 정확한 파일 명세를 다시 검사해 통과했다. [체크섬](../outputs/team_release_20261030/zip-integrity-v1.1.json)을 함께 보존했다. 이번 임시 런타임 3개는 워커까지 정상 종료했다. 프록시 2개는 활성 연결이 없는 것을 확인한 뒤 지정 프로세스만 종료했으며, 런타임의 정상 종료와 구분해 기록했다. 기존 서버·DB는 정리 대상에 포함하지 않았다.

## 남은 확인

- 같은 Wi-Fi의 휴대폰·다른 물리 기기, 독립 브라우저, OS 네트워크 단절·전환·절전 복구.
- 실제 마이크·새 발화·소음 조건 시험과 사람의 사용성 측정.
- 메인의 **미저장 요청까지 포함한 강제 새로고침**, `actor_id`/`pid` query 진입별 초안 복원은 이번 성공 판정에 포함하지 않았다. 기본 URL에서 이미 저장된 결과 복원과 구분한다.

4번을 전체 완료로 바꾸려면 미실행 범위를 실제 사용할 기기에서 이어서 수행해야 한다. [PC 검사 행렬](../.codex-build/device-flow-20261030/pc-verification.md), [수정 실행본](../outputs/team_release_20261030/team-common-20261030-v1.1/source/docs/TEAM_RELEASE_20261030.md)을 기준으로 이어간다. 최종발표 제작과 추가 알고리즘 실험은 진행하지 않았다.
