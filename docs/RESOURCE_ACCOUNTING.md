# 도착·퇴실 자원 정산과 수용 제한 검증

기준: 2026-10-14. 공통 서버와 DB 수정이며 환자·병원 앱 코드는 변경하지 않았다.

## 수정한 오류

일반 이송 환자는 도착·퇴실 때 현재 요구 자원을 전체 점유에 더하고 빼고 있었다. 도착 당시 없던 자원이 나중에 등록되면 퇴실 때 그 새 자원까지 차감했다. 또 담당자가 점유 합계를 수동 정산한 후 다른 환자가 들어오면, 이전 환자의 퇴실이 새 환자의 점유를 차감할 수 있었다.

격리 DB에서 기존 동작을 재현한 뒤 수정했다. 예를 들어 도착 때 전문팀 자원을 반영하지 않은 환자는, 나중에 전문팀의 실제 점유가 2로 등록돼도 퇴실 때 해당 점유를 차감하지 않는다.

수용 제한은 잘못된 종료 시각을 먼저 저장한 뒤 반환 과정에서 오류가 발생했다. 이후 병원·후보 조회도 계속 실패했다. 이제 입력을 쓰기 전에 검증하고, 이미 저장된 잘못된 시각은 원본을 보존해 재확인 대상으로 표시한다.

## 도착 시 실제 반영량 저장

새 도착 확인은 `patients.arrival_accounting`에 다음 내부 기록을 저장한다.

```json
{
  "version": 1,
  "hospital_id": "H1",
  "applied_resource_demands": {"ed_bed": 1},
  "applied_resource_epochs": {"ed_bed": "event:1"}
}
```

위 값은 구조 예시다. 요구 자원 전체와 실제 점유에 반영한 자원은 구분한다. 도착 당시 운영 자원이 없는 항목은 반영하지 않으며, 나중에 생겼다고 이 기록의 해제 대상에 추가하지 않는다. 기존 자원의 상태가 `unknown`이면 실제 점유만 기록하며 수용 가능 판정은 여전히 미확인이다.

운영 자원이 전혀 없었던 도착도 빈 적용 목록을 가진 유효한 기록을 저장한다. 빈 기록은 과거 기록의 null과 다르다. 모든 자원을 검사한 후 도착·점유·이력을 같은 트랜잭션에서 반영하며 정수 저장 범위를 넘으면 전체 처리를 거절한다.

내부 점유 기준은 환자 상세·도착 예정 목록·대화에 노출하지 않는다. 처리 이력에는 실제 반영·해제한 자원 수량만 기록한다.

## 퇴실 검증

`POST /api/hospitals/{hid}/patients/{pid}/discharge` 경로와 정상 성공 응답은 유지한다.

1. 환자가 해당 병원에 도착한 상태인지 확인한다.
2. 도착 당시 실제 반영한 자원과 집계 기준을 읽는다.
3. 같은 병원의 도착 환자와 활성 외부 유입 기록을 함께 집계한다.
4. 저장 당시 집계 기준과 현재 기준이 같고, 현재 점유가 관리 중인 합계를 충족하는지 확인한다.
5. 모든 자원이 통과하면 저장된 적용량만 해제하고 환자를 종료한다. 해당 병원으로 오는 다른 환자의 조건도 재평가한다.

한 자원이라도 삭제·집계 부족·수동 보정·원장 불일치가 있으면 `409 RESOURCE_CONFLICT`다. 자원 일부만 차감하거나 환자만 종료하지 않으며 상태·자원·이력·배정 입력 버전을 모두 유지한다. 다른 환자의 점유를 차감하지 않기 위한 정산 오류이며 임상적 수용 불가 판정을 뜻하지 않는다.

담당자가 `occupied` 수치를 바꾸면 집계 기준이 새로 생긴다. 같은 점유 수로 용량·상태만 수정하는 경우에는 기준을 유지해 정상 퇴실을 막지 않는다. 외부 유입의 등록·퇴실도 같은 검증을 사용한다.

기존 일반 환자의 반복 퇴실은 기존 계약대로 `INVALID_STATE`다. 외부 유입의 반복 퇴실은 기존 중복 성공 계약을 유지한다.

## 과거 기록과 별도 정산이 필요한 경우

- 기존 DB는 삭제하지 않고 nullable `arrival_accounting` 필드를 추가한다.
- 이미 도착해 원장이 없는 과거 환자는 어떤 수량을 반영·정산했는지 추정하지 않는다. 자동 퇴실은 `409 INVALID_STATE`로 막는다.
- 원장이 손상됐거나 수동 점유 보정과 일치하지 않으면 자동 차감하지 않는다. 문법상 잘못된 원장 JSON도 퇴실을 409로 거절하며 환자 조회는 유지한다. 저장된 원문을 자동 복구하지 않는다.
- 담당자가 이미 수동 정산했음을 확인한 기록은 [차감 없는 정산 확인·종결 API](ACCOUNTING_RECONCILIATION.md)로 종료할 수 있다. 대상과 전체 자원의 최신 버전, 사유·담당자·명시적 확인이 필수다. 자동 퇴실 충돌 후 이 API를 자동 호출해서는 안 된다.

## 수용 제한 입력

기존 등록 경로는 유지하고 선택적인 `starts_at` 전달을 연결했다.

```json
{
  "scope": "all",
  "reason": "시연: 인력 확인 필요",
  "starts_at": 1791939000,
  "ends_at": 1791939600,
  "handled_by": "시연 담당자"
}
```

| 항목 | 검증 |
|---|---|
| `scope` | 앞뒤 공백 제거 후 1~100자 문자열 |
| `reason` | 앞뒤 공백 제거 후 1~2,000자 문자열 |
| `handled_by` | 앞뒤 공백 제거 후 1~80자 문자열. 생략 시 기존 기본값 |
| `starts_at` | null/생략이면 현재 시각. 명시하면 0 이상 64비트 정수 범위의 epoch 초 |
| `ends_at` | null이면 종료 예정 없음. 명시하면 시작보다 큰 같은 범위의 epoch 초 정수 |

불리언·실수·문자열 날짜·배열·객체·음수·범위 초과·잘못된 시간 순서는 `400 INVALID`로 거절하고 아무것도 저장하지 않는다. 명시적인 `starts_at=0`은 현재 시각으로 바꾸지 않는다. 시작과 종료가 모두 과거여도 순서가 맞으면 만료 후 재확인 규칙을 유지한다.

과거에 저장된 잘못된 시각은 조회에서 `status=recheck`, `validation_error=INVALID_RESTRICTION_DATA`로 표시한다. 조회 때문에 원본을 수정하거나 제한을 해제하지 않는다. 담당자의 기존 제한 해제 API는 사용할 수 있다. 배정 결과를 저장할 때도 잘못된 시작 시각을 직접 비교하지 않아 반복 오류를 막는다.

## 검증

신규 `test_arrival_accounting.py` 26개와 `test_restriction_validation.py` 14개가 통과했다. 잘못된 차감 두 사례, 일반/외부 환자 간 집계, 누락·삭제·미확인 자원, 수동 보정, 복수 자원 전체 취소, 동시 도착·퇴실, 기존 DB 보존, 손상 원장, 제한 입력 HTTP 400과 후속 조회 복구를 포함한다.

실제 시연 DB에 오류 사례를 주입하지 않고 격리 DB에서 검증했다. 화면 담당자는 기존 API를 유지하고 400·409 응답의 설명과 재조회를 처리하면 된다.

전체 회귀 테스트661개와 별도 합성 DB의 실제 Chrome 전체흐름7개도 통과했다. 기존 두 화면에서 문의·사람 확정·출발·채팅·조건 변경·재배정·도착·퇴실을 확인했고 JS 오류·네트워크 실패는0건이었다. 정상 퇴실 후 실제 저장 원장과 자원 점유가 일치하는 것도 확인했다. 증거는 `.codex-build/server-corrections-20261014/`에 보관했다.
