# EAT 문의 후보 선별 실험: 기대 비용으로 여섯 병원 선택

이 후보는 채택하지 않았다. 혼합 개발 **96개 환경·336명**에서 기존 EAT보다 병원 선정 대기 합계가 **1,220초(20분 20초) 증가**했고, 선정 실패도 **61명에서 64명**으로 늘었다. 개발 기준을 통과하지 못해 별도 검증 환경의 성능 실행은 **0회**다. 기존 서비스 기본값 `fixed_3`은 그대로다.

## 변경한 한 가지

기존 `eat_l15_f`는 이동시간이 짧은 병원 최대 여섯 곳을 EAT 계획에 넣는다. 새 `eat_shortlist_l15_f`는 현재 문의 가능한 전체 병원에 대해 **현재 대기 문의와 해당 병원 한 곳을 더했을 때의 기대 도착 비용 + 문의 비용**을 계산하고, 낮은 비용의 최대 여섯 곳을 계획에 넣는다. 동률이면 이동시간·병원 식별자 순으로 정한다. 선별 후 계획의 순회 순서는 원래 이동시간 순서를 유지한다.

EAT의 믿음 추정, 과거 관측 처리, 현재 대기 문의 분포, 계획 시간 격자, 문의 비용 계수 15초, 동시 문의 상한 4곳, 강제 문의 안전 규칙, 최초 유효 수용 회신 즉시 확정은 변경하지 않았다. 미래 회신·미래 수용 결과·시뮬레이션의 숨은 실제 상태를 선별 입력에 추가하지 않았다. 기존 EAT와 확정 규칙 원본은 수정하지 않았다.

## 비교 조건과 지표

- 동일한 새 합성 환경에서 `fixed_3 즉시`, `기존 EAT 즉시`, `후보 EAT 즉시`, `V3 즉시`, `기존 EAT hold120` 다섯 분기를 모두 새로 실행했다. 기존 결과 캐시를 비교 분기로 재사용하지 않았다.
- 혼합 개발 96개 환경과 별도 스트레스 8유형 × 3개 seed, 합계 **120개 환경·600개 완전 분기 원문**을 저장했다. 스트레스 24개 환경은 주 판정에서 제외했다.
- 주 지표 **W**는 환자 발생부터 병원 선정까지의 대기다. 선정 실패 환자는 300초로 제한해 전체 환자 합계를 낸다. 이동시간·병원 도착 후 처치 대기를 합한 지표가 아니다.
- **J**는 선정 성공 시 추정 도착시간, 실패 시 300 + 1,500 = 1,800초를 부여한 환자 평균이다. 실패 비용은 실험 설계값이며 600·3,000초 민감도도 보고했다.
- 개발 통과 조건은 기존 EAT보다 W 합계가 작고, 실패 수·J가 늘지 않으며, 문의 수·병원 검토 업무가 `fixed_3` 이하인 것이다. 후보·설정·입력 생성 방식·판정 기준은 성능 실행 전에 고정했다.
- 고유 namespace의 역할·인덱스를 SHA256으로 변환한 128비트 seed를 사용했다. 기존 EAT·확정 규칙의 보고된 검증 seed와 분리했으며, 모든 과거 대형 원문 파일을 다시 검색한 이력은 아니다.

## 혼합 개발 결과: 96개 환경·전체 336명

| 지표 | 기존 EAT 즉시 | 후보 EAT 즉시 | 후보 − 기존 |
|---|---:|---:|---:|
| 선정 대기 합계 W | 46,366초 | 47,586초 | **+1,220초** |
| 환자당 선정 대기 | 137.994초 | 141.625초 | +3.631초 |
| 선정 실패 | 61명 | 64명 | **+3명** |
| 평균 J | 900.143초 | 909.256초 | **+9.113초** |
| 환자당 문의 수 | 4.940 | 4.997 | +0.057 |
| 환자당 병원 검토 업무 | 304.226초 | 309.134초 | +4.908초 |

환자당 문의 수와 업무는 `fixed_3`의 6.182회·351.247초 이하였지만, 주 비교 대상인 기존 EAT 대비 대기·실패·J가 악화해 개발 기준 세 가지를 통과하지 못했다. `fixed_3` 대비 대기 합계만 1,511초 낮았다는 비교를 채택 근거로 사용하지 않았다.

시나리오 단위 부트스트랩 10,000회로 계산한 환자당 W 변화의 95% 구간은 **−0.659~+8.609초**, J 변화는 **−1.719~+20.565초**다. 구간에 0이 포함되며, 새로운 환경에서 대기를 줄인다는 검증 근거가 아니다. 스트레스 유형별 결과와 실패 비용 민감도는 원 보고서에 별도로 남겼다.

## 개별 환자 손해도 포함

기존 EAT 대비 대기가 줄어든 환자 **25명**, 늘어난 환자 **39명**, 같은 환자 **272명**이다. 기존에 선정되던 환자 중 **4명**이 실패하고, 기존 실패 중 **1명**이 새로 선정됐다. 대기 합계가 늘어난 혼합 환경은 **15개**다. 개별 환자 무악화를 주장하지 않는다.

최대 대기 악화는 개발 원문 `047_189380976736811432035303352488999136178.json.gz`의 P05에서 **19초 → 244초(+225초)**였다. 두 분기 모두 목적지는 H06이었다. 이 사실은 같은 병원에 도달하더라도 문의 순서와 병원 대기열의 상호작용으로 선정이 늦어질 수 있음을 보여주며, 이 문서에서 원인을 하나로 확정하지는 않는다. 다른 환자의 최대 J 악화는 **883초**다.

## 감사 오류를 발견하고 처리한 절차

1. 최초 성능 실행 120개 환경·600개 분기 전체를 저장한 뒤, 원래 감사기가 `actual hospital outcome differs from current open state/potential` 오류를 냈다. 이 시점에는 성능 집계·선택 결과를 보지 않았고 재실행하지 않았다.
2. 고정된 원 감사기를 전체 저장 원문에 적용한 결과 582개 분기는 통과하고 18개에서 같은 유형의 오류가 확인됐다. 실패 기록과 원 감사기 소스는 그대로 보존했다.
3. 시뮬레이터는 같은 초에 회신 완료를 처리한 뒤 문의 종료를 기록한다. 감사기가 회신 시점의 종료 여부를 `종료 시각 ≤ 회신 시각`으로 판정한 것이 문제였다. 별도 감사 보정본에서 **회신 완료의 종료 조회만 `<`로 수정**했다. 업무 시작·대기열 취소 판정의 `≤`는 유지했다. 원문 변환·monkeypatch·정책 변경은 하지 않았다.
4. 보정 감사 검사 10개와 저장 원문 재집계·검증 실행 차단 검사 7개가 통과한 뒤, 보정 소스·검사 결과를 별도 `audit-amendment.json`에 고정했다. 기존 동결 252개 파일과 후보·seed·판정 기준은 그대로였다.
5. 동일한 저장 원문 600개 분기를 다시 감사해 모두 통과했다. 저장 원문만 집계했으며 **성능 재실행 0회, 불리한 결과 제외 0건**이다. 개발 실패 판정 후 검증 성능 실행도 0회다.

## 확인한 범위와 한계

초기 검사는 **85개**가 통과했다. 기존 EAT 19개·확정 규칙 8개와 새 후보 정책·연결·감사·실험 검사 58개를 합친 것이며, 과거 전체 프로젝트 검사 2,595개를 다시 실행한 결과가 아니다. 감사 보정 단계의 **17개**는 별도 검사다. 완전 원문 감사는 저장된 현재 이벤트 순서, 후보 선별 수식, 실제 FIFO 업무·회신·확정·계수의 일관성을 확인한다. 변경하지 않은 EAT 계획 핵심을 별도 구현으로 다시 실행한 것은 아니며, 최적성을 증명하지 않는다.

최종 봉인은 초기 동결 252개 소스·fixture와 감사 보정 Python 8개, 총 **260개 과학 소스 경로**를 다음 실험의 재사용 가능한 기준으로 묶는다. 별도로 초기 보존 기준의 기존 260개 경로를 확인하고, 이번 실험의 압축 원문 120개와 해제 원문의 SHA256을 전부 확인한다. 이전 6.7GB 규모 증거의 보존 증명은 이름과 해시가 고정된 C1 부모 봉인을 재사용하며, 이번에 그 전체 파일을 독립적으로 재검색·재해시했다고 주장하지 않는다. 기존 `docs/README.md`도 수정하지 않았다.

본 실험은 합성 문의·회신·이동 환경의 **병원 선정 대기** 비교다. 임상 결과, 실제 총 처치 대기, 실제 병상 배정·공동 배정 H1/C1 성능을 의미하지 않는다. 서버·UI·실제 데이터베이스에 적용하지 않았으며, 이 후보를 운영 정책으로 채택하지 않는다.
