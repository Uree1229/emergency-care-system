# 해결방안에 따른 배정 알고리즘 초안

작성일: 2026년 10월 2일. [문제 정의와 해결방안](문제정의와_해결방안_초안.md)을 구현하기 위한 설계안.

이 문서는 다음 구현의 기준이다. 현재 서버와 솔버가 모두 연결되었거나 실제 병원에서 검증되었다는 의미는 아니다.

## 1. 알고리즘이 결정할 것

입력된 환자 요구와 병원 상태를 바탕으로 **환자별 목적 병원과 예상 치료 시작시각**을 제안한다. 신규 환자는 여러 병원에 나누어 배정하고, 이동 중인 환자는 목적지를 유지하면서 자원 변화의 영향을 평가한다.

병원 탐색 → 병렬 문의 → 유효 수용 확인 → 자원 일정 배정 → 사용자 확인·서버 확정 → 사건 발생 시 재평가 순서로 구성한다. 문의할 후보와 최종 확정 가능한 후보를 구분한다.

## 2. 해결방안과 알고리즘의 연결

| 문제 ID | 해결방안 | 알고리즘에서 담당할 부분 |
|---|---|---|
| P1 | 필요한 진료를 제공하는 후보 탐색 | 진료 조건 필터와 환자–병원 이동시간 행렬 |
| P2 | 병렬 문의와 조기 응답 활용 | 상위 K개 문의, 응답 사건마다 배정안 갱신 |
| P3 | 환자별 수용 확인과 만료 관리 | 수용 응답·조건 버전·유효시간을 확정 가능 조건으로 검사 |
| P4 | 도착 예정 수요와 자원 경합 반영 | 환자별 병원 선택 변수와 시간대별 자원 용량 제약 |
| P5 | 이동 중 환자 영향 평가·대체 문의 | 목적지 고정, 치료 시작시각 재계산, 조정 필요 표시 |
| P6 | 병원 입력 부담 감소 | 문의 후보 수·확대 정책을 제한하고 필요한 변경만 알림. 화면 사용성은 UI에서 구현 |

## 3. 초기 모델의 범위

- 한 지역의 가상 병원 10곳과 환자 20명 이하로 시작한다.
- 시간 단위는 정수 분, 기본 계획 구간은 120분으로 둔다. 모두 계산 실험 설정이다.
- 환자는 단일 치료 단계에서 진료 자리와 필요시 전문팀을 일정 시간 사용한다고 가정한다.
- 필요한 진료과·자원·우선순위·점유시간은 가상 입력 또는 확인된 값으로 제공한다.
- 수술→ICU처럼 연속된 여러 치료 단계는 후속 확장으로 둔다.
- 실제 치료 중인 환자의 처치를 새 배정을 위해 중단하거나 순서를 자동 변경하지 않는다.

## 4. 입력과 출력

| 입력 | 필수 정보 |
|---|---|
| 환자 | ID, 상태, 최초 요청시각, 현재 위치, 필요 진료·자원, 우선순위와 출처, 예상 점유시간, 허용 시작시각 |
| 병원 | ID, 진료 역량, 자원별 총 용량, 비가용 구간·치료 중 점유 |
| 문의 | 환자–병원별 수용 상태, 응답시각·만료시각, 환자 조건 버전 |
| 이송 | 기존 확정 병원, 현재 위치 기준 ETA, 예정 자원 수요 |
| 계산 | 현재 시각, 입력 스냅샷 버전, 이동시간 추정값, 계산 제한시간 |

미확인 정보를 ‘가용’으로 바꾸지 않는다. 공개 API의 잔여 병상 수와 총 용량을 혼동하거나 이미 반영된 점유를 다시 차감하지 않는다. 초기 솔버는 총 용량과 개별 점유 구간이 있는 가상 캘린더를 기준으로 한다.

출력은 환자별 추천 병원, ETA, 예상 치료 시작시각, 배정 상태·사유, 영향 환자 목록, 입력 버전, 솔버 상태와 계산시간이다. 이동 중 환자의 계산 결과가 나빠져도 실제 목적지 기록을 삭제하지 않는다.

## 5. 후보 생성과 문의 정책

1. 필요한 진료·자원 종류를 제공할 수 있는 병원을 탐색한다. 현재 자원 부족은 즉시 수용 여부와 미래 가능성을 구분해 표시한다.
2. 이동시간을 계산한다. 초기에는 가상 행렬을 사용하고 이후 지도 API와 연결한다. 직접 도로 그래프를 관리할 때에는 Dijkstra 등을 이동시간 전처리에 사용할 수 있다.
3. 초기 문의 후보는 이동시간 기준 상위 K=3곳으로 둔다. K는 설정값이며 제한 때문에 더 좋은 병원이 제외될 수 있다.
4. 병원 응답이 들어오면 현재 유효 응답만으로 재평가한다. 모든 응답을 기다리도록 고정하지 않는다.
5. 유효 수용 병원이 없으면 미배정·응답 대기 이유를 표시하고 후보 확대를 제안한다. 재문의·후보 확대 시 이미 보낸 문의의 상태를 함께 관리한다.
6. 최초 목적지 확정은 서버가 현재 사용 가능하다고 판단한 환자별 수용 응답만 사용한다. 미응답·거절·만료 응답을 시간 비용만 높여 선택하는 방식은 사용하지 않는다.

기존에 확정된 이송은 신규 문의의 만료와 구분한다. 확정 뒤에는 기존 이송 기록과 병원의 수용 유지·조정 판단을 기준으로 관리한다. [서버의 상태·업무 규칙](../API.md)

## 6. 배정 방식

### 기본 비교안: 탐욕 배정

확인된 우선순위가 높은 환자부터, 동률이면 최초 요청이 빠른 환자부터 처리한다. 각 환자에 대해 유효 수용 병원 중 가장 이른 치료 시작이 가능한 병원을 선택하고, 계산 중에는 그 점유를 다음 환자에게 반영한다. 치료 시작이 같으면 이동시간, 병원 ID 순으로 정해 결과를 재현 가능하게 만든다.

탐욕 배정은 B1 비교 정책과 솔버 시간 초과 시 대체안으로 사용한다. 계산 결과는 확정 전까지 제안이며, 실제 자원 점유 기록은 서버의 확정 절차에서 만든다.

### 최적화안: OR-Tools CP-SAT

병원 선택과 자원 사용 구간을 함께 모델링한다. 선택적 시간 구간과 누적 자원 제약을 사용해 병원별 복수 용량을 표현하는 설계로 한다. OR-Tools는 제약 기반 최적화와 스케줄링 모델을 지원한다. [공식 문서](https://developers.google.com/optimization/cp)

초기 제안의 헝가리안 알고리즘은 정적 비용 행렬을 이용한 단순 배정 비교에 사용할 수 있다. 이번 초안은 여러 환자의 시간대별 자원 점유와 기존 이송의 목적지 고정을 포함하므로, 기존 `solver_improved.py`의 CP-SAT 모델을 확장한다.

## 7. 변수와 제약 초안

환자 i, 병원 h, 자원 k, 시각 t를 사용한다.

| 기호 | 의미 |
|---|---|
| x[i,h] | 환자 i를 병원 h에 제안하면 1 |
| u[i] | 신규 환자 i의 실행 가능한 배정이 없으면 1 |
| s[i] | 예상 치료 시작시각 |
| a[i,h] | 현재 위치에서 계산한 도착 가능시각 |
| e[i,h] | 신규 확정에 필요한 진료 조건·유효 수용 응답을 만족하면 1 |
| d[i], q[i,k] | 예상 점유시간, 자원별 요구량 |
| C[h,k,t], B[h,k,t] | 총 운영 용량, 치료 중 점유·비가용 구간의 사용량 |
| r[i], L[i] | 최초 요청시각, 허용 치료 시작시각 |

신규 환자 제약은 다음과 같다.

```text
환자당 한 병원 또는 미배정:  Σ_h x[i,h] + u[i] = 1
확정 가능 후보만 선택:       x[i,h] ≤ e[i,h]
도착 이후 치료:             x[i,h] = 1 → s[i] ≥ a[i,h]
허용 시작시각 준수:          x[i,h] = 1 → s[i] ≤ L[i]
자원 점유:                  [s[i], s[i] + d[i]) 동안 q[i,k] 사용
용량 준수:                  모든 h,k,t에서 B + 새 계획 점유 ≤ C
```

자원 구간은 시작 포함·종료 제외로 계산한다. 10분에 끝나는 점유와 10분에 시작하는 점유는 겹치지 않는다. 계획 구간 끝 이후까지 이어지는 점유도 검사하도록 캘린더를 연장하거나 해당 배정을 제외한다.

치료 중인 환자는 B에 한 번만 반영한다. 기존 확정 이송을 새로운 시간 구간 변수로 모델에 넣으면 같은 예정 수요를 B에 다시 넣지 않는다. 재계산 때 최초 요청시각과 허용 시작시각을 초기화하지 않는다.

## 8. 상태별 고정 규칙

| 상태 | 병원 선택 | 치료 시작시각·점유 처리 |
|---|---|---|
| WAITING | 유효 수용 후보에서 계산 | ETA 이후 실행 가능한 구간 계산 |
| CONFIRMED, 미출발 | 기본적으로 기존 병원 유지 | 새 정보로 예상 시작 재평가. 변경은 별도 확정 절차 |
| IN_TRANSIT | 기존 목적지 고정 | 잔여 이동시간으로 ETA 갱신, 예상 시작은 변경 가능 |
| ARRIVED | 도착 병원 고정 | 도착만으로 치료 시작을 가정하지 않음. 실제 대기·치료 상태 데이터 필요 |
| 치료 시작 확인됨 | 실제 병원·시작시각 고정 | 추정 종료까지 점유. 현재 서버의 ARRIVED와 구분할 데이터가 필요 |
| COMPLETED / CANCELLED | 새 배정 대상에서 제외 | 종료·취소 이후 예정 점유 해제 |

기존 확정·이동 중 환자에 대해서는 신규 환자용 u로 목적지를 없애지 않는다. 기존 병원에서 예상 시작이 L[i]를 넘으면 지연 초과와 조정 필요를 반환하고 해당 환자의 예상 자원 수요를 유지한다. 신규 환자 배정의 허용시간 제약과 기존 이송의 초과 감지를 구분한다.

치료 전의 기존 확정 환자는 `x[i,기존병원]=1`로 두고, 시작시각은 현재 시각·갱신된 ETA 이후로 제한한다. 자원 구간을 다른 신규 환자와 함께 계산한다. 계획 구간 안에 기존 이송을 표현할 수 없으면 구간을 확장하거나 검토 필요를 반환하며, 해당 환자를 임의로 제외하지 않는다.

현재 코드의 `fixed`는 병원과 시작시각을 함께 고정한다. 다음 구현에서는 `destination_locked`와 `treatment_started`를 분리해야 한다. 기존 점유 자체가 용량을 넘으면 입력·운영 충돌을 표시하고 실행 가능하다고 보고하지 않는다.

## 9. 목적함수 초안

계산 대상의 우선순위군 g를 높음·중간·낮음으로 정규화한다. U_g는 신규 환자의 미배정 수다. W_g는 배정된 신규 환자와 치료 전의 기존 확정 환자를 포함한, 요청부터 예상 치료 시작까지의 시간 합이다. 기존 이송의 시작시각도 시간 목표에 포함해 불필요하게 늦은 추정값을 선택하지 않도록 한다.

```text
W_g = Σ (s[i] - r[i])  [배정된 신규 환자 + 치료 전의 기존 확정 환자]

기본 정책 severity_first:
최소화 (U_높음, U_중간, U_낮음, W_높음, W_중간, W_낮음)
```

앞 항목의 최선 값을 유지하면서 다음 항목을 줄이는 순서다. 단순 거리 합보다 수용 가능한 배정 수와 우선순위별 치료 시작 지연을 평가한다. 기존 이송의 지연 초과·조정 필요 수는 별도 결과로 보고한다.

이는 실험용 운영 정책이다. 낮은 군의 배정 수 증가가 높은 군의 지연을 늘리는 상충 사례를 확인하고, 전체 미배정 수를 맨 앞에 추가하는 `total_first`와 비교한다. 임상적으로 적절한 우선순위·허용시간은 멘토·전문가 검토 항목이다.

현재 서버의 자기신고·미확인 우선순위 처리는 UI용 규칙이다. 이를 임상적으로 확인된 우선순위로 해석하지 않고 솔버 입력 변환 규칙을 별도로 정한다. 첫 비교 실험은 우선순위가 주어진 가상 환자로 수행한다.

각 단계가 OPTIMAL로 증명된 경우에만 그 값을 고정하고 다음 단계로 간다. FEASIBLE에서 끝나면 유효한 해를 반환하되 전체 계층 목표의 최적성을 주장하지 않는다.

## 10. 사건 발생 시 재계산

재계산 사건은 신규 환자 등록, 수용 응답 변경·만료, 병원 자원 변경, 출발·도착·취소, 미등록 환자 유입이다. 화면의 2~3초 조회마다 솔버를 실행하지 않고 변경 사건을 모아 중복 계산을 합친다.

첫 구현은 변경 사건마다 작은 규모의 전체 스냅샷을 다시 계산하되, 실제 치료 점유와 기존 목적지를 고정한다. 성능이 필요해지면 영향 병원과 후보가 겹치는 환자까지 포함한 부분 재계산으로 확장한다. 직접 영향 환자만 계산하고 연결된 자원 경합을 누락하지 않도록 한다.

### A 이동 중 B가 먼저 도착한 경우

1. H1이 B의 도착과 자원 점유를 등록한다. 알고리즘은 등록된 관측 시점 이후에만 B를 반영한다.
2. A의 병원을 H1로 고정하고 현재 위치 기준 ETA와 가능한 치료 시작시각을 다시 계산한다.
3. A의 예상 시작이 늦어지면 병원 화면에 영향을 표시한다. 병원이 수용 유지 또는 조정 필요를 판단한다.
4. 조정 필요이면 현재 위치에서 대체 병원에 문의하고 유효한 새 수용 응답으로 대안을 계산한다.
5. 사용자·담당자 확인 후 서버가 새 확정, 이전 예정 수요 해제, 이력 기록을 함께 처리한다.

가상 예: A의 ETA가 t=10, 점유시간 20분, 허용 시작 t=30이다. B가 같은 자원을 t=25까지 사용하면 A의 예상 시작은 t=25다. t=45까지 사용하면 A는 허용시간 초과로 표시된다. H2가 t=6에 새로 수용하고 현재 위치에서 12분 거리이며 자원이 비어 있으면 H2의 예상 시작은 t=18이다. H2 확정 전까지 A의 기존 목적지·예정 수요는 유지한다.

## 11. 계산 제한과 확정 처리

초기 계산 예산은 3초로 둔다. 최신 입력에서 유효한 탐욕 배정안을 먼저 만들고 솔버의 초기해로 제공한다. 솔버가 FEASIBLE 또는 OPTIMAL 해를 반환하면 용량·응답·기한을 다시 검사해 제안한다. 유효한 해를 얻지 못하면 검증된 탐욕 배정안을 사용한다.

입력 충돌로 대체안도 만들 수 없으면 검토 필요를 반환한다. 3초는 실험 설정이며 모델 구성·초기해까지 포함한 전체 제한은 별도 작업 프로세스의 타임아웃으로 구현해야 한다.

서버 확정 시 입력 버전, 환자 버전, 응답 사용 가능 여부와 최신 자원을 트랜잭션 안에서 재확인한다. 다른 확정이 먼저 이루어졌으면 오래된 배정안을 적용하지 않고 다시 계산한다. 긍정 응답만으로 자원을 여러 곳에 점유하지 않는다.

여러 환자의 공동 배정안은 모두 제안 상태다. 개별 확정 순서가 바뀌면 남은 제안의 가용성도 바뀔 수 있으므로, 확정 사건 후 나머지 배정안을 갱신한다.

## 12. 처리 순서 의사코드

```text
변경 사건 수신:
    현재 환자·문의·이송·자원 상태를 버전과 함께 읽는다
    실제 치료 점유와 기존 확정 목적지를 구분한다
    신규 환자의 유효 수용 후보와 현재 위치 기준 이동시간을 만든다
    상태별 고정 규칙을 적용한 탐욕 대체안을 만든다
    같은 입력·제약·목표로 CP-SAT를 제한시간 동안 실행한다
    유효한 솔버 해가 있으면 사용하고, 없으면 유효한 대체안을 사용한다
    기존 이송의 지연 초과·영향 환자를 별도 표시한다
    입력 버전이 바뀌었으면 결과를 폐기하고 재계산한다
    배정 제안과 계산 상태를 저장하고 화면에 제공한다

사용자의 목적지 확정 요청:
    트랜잭션 안에서 최신 응답·환자 버전·자원 여유를 검사한다
    검사 실패 시 재확인·재계산 상태를 반환한다
    성공 시 한 병원의 예정 수요와 목적지를 기록한다
    나머지 문의를 종료하고 남은 환자의 배정안을 갱신한다
```
