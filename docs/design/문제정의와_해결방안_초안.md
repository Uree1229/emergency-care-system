# 문제 정의와 해결방안 초안

작성일: 2026년 10월 2일. 팀·멘토 검토용 초안.

## 1. 프로젝트가 해결하려는 문제

환자를 치료할 수 있는 병원을 찾는 과정에서 병원 탐색, 환자별 수용 확인, 목적지 결정이 반복된다. 병원을 정한 뒤에도 다른 환자 유입이나 자원 상태 변화로 기존 수용 계획을 다시 확인해야 할 수 있다.

우리 프로젝트의 문제는 **환자의 필요 조건, 병원의 수용 응답, 도착 예정 환자의 자원 수요를 함께 관리해 병원 선정과 조정 과정의 지연을 줄이는 것**이다. 환자·이송자용 모바일 웹, 병원용 웹, 공통 서버와 배정 알고리즘을 연결해 이를 시연한다.

연구 질문은 다음 두 가지다.

1. 같은 환자·병원 조건에서 병렬 문의와 상태 변경 알림이 순차 문의보다 병원 선정 지연을 줄이는가?
2. 같은 문의·정보 조건에서 도착 예정 수요를 고려한 배정이 탐욕 배정보다 미배정과 치료 시작 지연을 줄이는가?

아래 항목은 프로젝트에서 다루는 업무상 문제와 위험이다. 전국 현장의 발생률이나 개선 효과를 입증한 통계로 해석하지 않는다.

|---|---|---|---|

| P2 | 한 사람이 병원에 순차 문의하는 비교 흐름에서는 앞 병원의 응답 지연이 다음 문의를 늦춤 | 환자 정보를 한 번 입력하고 제한된 수의 병원에 병렬 문의. 먼저 온 유효 응답부터 배정 평가 | 문의 시작부터 목적지 확정까지의 시간과 병원당 문의 부담을 함께 비교. 시스템 자체가 병원 응답을 보장하지는 못함 |
| P3 | 조회된 가용 정보와 특정 환자의 실제 수용 가능 여부를 혼동하거나 미응답 상태에서 오래 기다릴 수 있음 | 환자별 수용·불가·확인 중·추가 질문 상태를 관리하고 응답시각·만료를 표시. 60초 경고와 120초 재문의 선택 제공 | 미응답·만료 응답으로 확정되는 건수, 응답 누락률 측정. 시간 기준은 시연 설정이며 의료적 대기 허용시간이 아님 |
| P4 | 여러 환자가 같은 병원을 선택하면 현재 가용 수만으로는 도착 예정 수요와 자원 경합을 표현하기 어려움 | 확정 이송의 예정 수요와 치료 중 점유를 반영해 병원·예상 치료 시작시각을 함께 계산. 최종 확정은 서버에서 충돌 검사 | 동시 확정 시 중복 점유가 없는지, 우선순위별 미배정·지연이 어떻게 변하는지 평가. 치료시간 추정 오차는 남음 |
| P5 | 미등록 환자 B가 먼저 도착해 이동 중인 A의 수용 계획에 영향이 생겨도 이를 제때 공유하지 못할 수 있음 | 병원에서 B 유입·자원 변화를 등록하면 영향 환자를 표시하고 A의 목적지를 유지한 채 예상 치료 시작시각 재평가. 병원 판단에 따라 수용 유지 또는 대체 문의 | 변화 관측부터 알림까지의 시간, 목적지 변경·추가 이동 측정. B의 미래 유입이나 병원 미등록 사건은 미리 알 수 없음 |
| P6 | 병원 담당자가 반복 입력과 여러 문의 처리에 부담을 느끼면 응답이 누락될 수 있음 | 수용은 한 번의 조작으로 전송, 불가는 사유 선택, 영향 환자·미응답 문의를 강조하는 병원 화면 | 1·5·10건 동시 문의에서 응답시간 중앙값·95백분위·클릭 수·누락률 측정. 인력 부족 자체는 시스템으로 해소되지 않음 |

## 3. 해결 범위와 필요한 데이터

전문의·수술실·중환자실의 물리적 부족, 지역 의료자원 격차, 법적 책임체계는 별도의 인력·시설·제도 개선이 필요한 문제다. 이번 시스템은 주어진 자원을 찾고 확인하고 배정하는 과정을 지원한다.

국립중앙의료원 공개 API의 서비스 설명에는 응급의료기관 위치·진료 정보, 일부 가용 자원과 중증질환 수용 가능 정보 조회가 포함되어 있다. 이 정보는 후보 탐색의 입력으로 사용한다. 인증키를 통한 실제 필드·결측·갱신시각 검증은 남아 있다. [공식 서비스 설명](https://www.data.go.kr/data/15000563/openapi.do)

| 데이터 | 확보 방법 | 사용 원칙 |
|---|---|---|
| 병원 위치·진료 역량 | 공개 API, 초기에는 가상 병원 | 후보 탐색에 사용하고 현재 수용 확답과 구분 |
| 환자의 필요 진료·자원·우선순위 | 초기에는 가상 시나리오, 확인된 입력 | 일반인의 증상 입력을 확정 진단·임상 중증도로 바꾸지 않음 |
| 환자별 수용 여부·사유 | 병원 웹과 자체 서버 | 해당 환자의 유효한 응답만 최초 확정에 사용 |
| 이동시간 | 초기에는 가상 행렬, 이후 지도 API | 도착시각의 추정값으로 사용 |
| 총 자원 용량·점유 구간·예상 종료시각 | 가상 자원 일정, 향후 병원 입력·연계 | 실제 병원 일정 확보 전에는 합성 데이터임을 표시 |
| 도착 예정 환자 | 자체 시스템의 확정 이송 기록 | 같은 환자의 예정 점유를 중복 반영하지 않음 |
| 시스템 미사용 환자의 유입 | 병원에서 발생 후 등록 | 관측 이후 재평가하며 미래 사건을 알고 있는 것으로 계산하지 않음 |

## 4. 서비스 흐름

1. 환자·이송자가 필요한 정보를 입력한다. 위험 신호 안내와 병원 문의 흐름을 구분하고, 확인되지 않은 진료 조건은 추가 확인 대상으로 표시한다.
2. 서버가 필요한 진료 조건과 위치로 문의 후보를 찾는다.
3. 선택한 후보에 같은 환자 정보를 병렬 전송한다.
4. 병원이 수용, 불가 사유, 확인 중 또는 추가 질문을 응답한다.
5. 유효 수용 응답이 생기면 알고리즘이 이동시간·자원 일정·도착 예정 수요를 고려해 배정안을 갱신한다.
6. 사용자 확인 후 서버가 응답·자원 상태를 다시 검사하고 목적지 한 곳을 확정한다. 나머지 문의를 종료하고 해당 병원에만 예정 수요를 기록한다.
7. 이동 중에는 목적지를 유지하면서 도착 예정시각과 병원 변화를 관리한다.
8. 병원이 신규 유입이나 자원 부족을 등록하면 영향 환자를 재평가한다. 병원이 수용을 유지하면 변경된 추정 시간을 안내한다.
9. 병원이 조정 필요로 판단하면 현재 위치에서 대체 병원에 재문의한다. 새 수용 확인과 담당자·사용자 확인을 거쳐 목적지를 변경한다.

병원의 긍정 응답은 여러 병원의 자원을 동시에 예약하는 의미가 아니다. 목적지 확정과 실제 치료 순서 결정의 권한도 구분한다. 알고리즘의 치료 시작시각은 병원 비교·영향 평가를 위한 추정값이다.

## 5. 주요 시연: A 이송 중 B가 먼저 도착

A는 H1로 이동 중이고 10분 뒤 도착할 예정이다. H1에 시스템을 사용하지 않은 B가 먼저 도착해 A에게 필요한 자원을 사용하게 된다.

- 병원은 B의 자원 점유를 등록한다. B의 진료 우선 판단은 병원에서 수행하고 시스템은 그 결과를 반영한다.
- A의 목적지를 H1로 유지한 채 새 점유를 반영해 예상 치료 시작시각을 다시 계산한다.
- H1이 수용을 유지할 수 있으면 A에게 변경된 상태를 전달한다.
- H1이 조정 필요로 판단하면 현재 위치 기준의 대체 병원을 탐색하고 새로 수용을 확인한다.
- 기존 2순위 병원도 상황이 바뀔 수 있으므로 재확인 없이 자동 변경하지 않는다. 대안이 없으면 조정 필요 상태와 연락 정보를 계속 표시한다.

이 흐름의 목표는 자원 고갈을 없애는 것이 아니라, 변화를 공유하고 재탐색·재확인을 시작하는 시간을 줄이는 것이다. 전체 치료 지연이 줄어드는지는 추가 이동과 병원 응답 부담까지 포함해 실험으로 확인한다.

## 6. 평가와 완료 조건

| 비교 | 동일하게 둘 조건 | 확인할 효과 |
|---|---|---|
| B0: 순차 문의 + 탐욕 배정 / B1: 병렬 문의·변경 알림 + 탐욕 배정 | 환자 발생, 병원 자원, 응답 모델, 외부 유입 | 문의·알림 방식의 효과 |
| B1 / B2: 같은 병렬 문의·변경 알림 + 솔버 배정 | 문의 후보 정책, 관측 시점, 이동시간·자원 추정값 | 배정 알고리즘의 효과 |

핵심 지표는 목적지 확정까지의 시간, 최초 요청부터 실제 치료 시작까지의 시간, 우선순위별 미배정·기한 초과, 목적지 변경 횟수·추가 이동, 병원 문의 수, 계산시간·대체안 사용률이다. 치료를 시작한 환자의 평균만 제시하지 않고 관찰 종료까지 치료하지 못한 환자도 별도 보고한다.

동일한 가상 사건을 최소 30개 seed로 비교하고, 정상 상황 외에 미응답·동시 경합·B 유입·정보 지연·대체 병원 없음 시나리오를 포함한다. 개선 여부와 크기는 결과를 확인한 뒤 작성한다.

현재 문의·응답·확정·돌발 유입의 시연 서버와 독립 솔버는 존재한다. 두 UI의 서버 연결, 솔버 입력 변환, 이동 중 목적지 고정/치료 시작시각 가변 처리, B2 비교가 다음 구현 과제다. [현재 구현 상태](../PROJECT_STATUS.md)
