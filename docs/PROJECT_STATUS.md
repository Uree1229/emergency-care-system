# 프로젝트 현재 상태

기준: 2026년 10월 8일. 아래의 ‘구현’은 시연용 코드의 존재를 뜻하며 실제 의료기관 검증을 뜻하지 않습니다.

## 구현된 시연 기능

- `server/`: 환자 입력 저장·병원 전달, 문의·응답·이송, 배정 워커·추천 API. DB 입력 버전과 수용 응답 만료를 검사하고 이전 결과를 폐기합니다. 확정 충돌 검사는 별도 SQLite 트랜잭션으로 유지합니다.
- `solver_improved.py`: CP-SAT 배정, 우선순위 정책 2개, 자원 수량·시간 제약, 초기해·순차 대체안. 이동 중 환자는 목적지만 고정하고 치료 시작시각을 다시 계산합니다. 기한 초과는 검토 대상으로 표시합니다.
- `hospital-ui/`: 공통 서버를 사용하는 병원 웹. 배정 결과 표시 연결은 남아 있습니다.
- `simulation/`: 같은 seed를 사용한 B0(순차 문의)와 B1(병렬 문의·변경 알림) 비교. 저장된 결과는 가상 시뮬레이션입니다.
- `prototype/`: 서버와 독립된 문의·응답 화면 프로토타입.

## 아직 연결하거나 검증해야 할 것

1. 환자용 모바일 웹의 독립 DB를 공통 API로 전환하고, 추천 API·수용 확인·확정·이송 흐름을 연결.
2. 병원 웹에서 `incoming.planning`의 예상 시작시각·재확인 사유를 표시.
3. 실제 점유 종료시각을 확보해 시간대별 점유 모델을 발전. 현재 점유는 계획 기간 전체에서 유지하며, 치료시간·최대 대기는 임상 기준이 아닌 실험값.
4. 자원 부족으로 기존 목적지가 실행 불가능하면 전체 계획을 재확인 대상으로 반환하는 1차 정책을 병원별 재평가로 세분화.
5. 공공 의료 API 인증키로 실제 응답 필드와 결측·갱신 시각 확인. `server/probe_apis.py`의 미검증 엔드포인트·파라미터를 활용가이드와 대조한 뒤 사용.
6. B2(같은 문의 방식 + 솔버 배정) 비교와 민감도 실험.
7. 로그인·병원별 접근 통제, 임상 기준 검토, 실제 병원 연동은 시연 범위 밖. 실제 환자 정보 사용 금지.

## 바로 다음 순서

| 순서 | 작업 | 완료 확인 |

| 1 | API 응답 필드 매핑 | 원본 응답·코드표·결측 규칙을 `api_field_mapping.md`에 기록 |
| 2 | 화면 연결 | 환자·병원 화면에서 문의→수용→이동→돌발 유입→조정 흐름 시연 |
| 3 | 실제 자원 일정 연계 | 종료시각의 출처를 표시하고 B 유입 후 A의 예상 대기 변화를 검증 |
| 4 | B2 평가 | B0/B1/B2를 동일 seed·정보 조건에서 비교, 미배정과 병원 문의 부담 함께 보고 |
