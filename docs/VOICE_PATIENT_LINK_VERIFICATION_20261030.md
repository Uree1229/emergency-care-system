# 음성 초안 → 환자정보 → 병원 문의 연결 보완

2026-10-30. Codex 서버 담당 작업. `paramedic-ui/`, 기존 팀원의 구급대원·병원 프론트엔드는 수정하지 않았다. Claude의 자동모드 판별과 화면 확인 분기도 보존했다.

## 완료한 보완

| 기존 문제 | 수정한 동작 |
|---|---|
| 수동 입력 환자의 R1·활력징후가 새 음성 초안에 빠짐 | `extra.avpu`, `chief_complaint`, `age_group`, `pre_ktas_level`, 2차 고려사항과 `extra.vitals`의 유효한 값을 읽는다. 서버 우선순위만으로 Pre-KTAS를 역추론하지 않는다. |
| 맥박 한 항목을 저장하면서 기존 혈압·산소포화도 등이 사라짐 | 바뀐 활력징후만 병합한다. 다른 측정값·측정시각·다른 입력 채널의 확장 정보는 유지한다. 기존 공통 측정시각을 새 측정시각으로 바꾸지는 않으며 새 관찰 시각은 음성 필드 메타데이터에 기록한다. |
| 초안에서 삭제한 항목이 환자·병원 정보에는 남음 | 명시적인 삭제를 R1·활력징후 미러에도 적용한다. Pre-KTAS 삭제는 우선순위 `null`, 출처 `unknown`으로 처리하며 낮은 중증도를 추측하지 않는다. |
| 값은 같아도 재확인·미측정 상태가 달라진 제출을 무변경으로 처리 | 상태 변화도 환자정보 변경으로 저장한다. 새 세션에서도 같은 관찰값의 재확인·미측정 상태를 유지한다. 새 수동 값이 과거 값과 다르면 과거 재확인 표시를 상속하지 않는다. |
| 오래된 음성 스냅샷이 최신 수동 입력을 덮어씀 | 현재 환자 필드·명시된 활력징후가 우선이다. 명시적으로 빈 `vitals`에서는 과거 측정값을 복원하지 않는다. 최신 증상 원문과 맞지 않는 과거 구조화 증상은 현재 목록에 합치지 않고 현재 원문을 `baseline_summary`로 보존한다. |
| 기존 환자를 읽고 확인하는 것만으로 수용 응답이 무효화될 가능성 | 값·재확인 상태 모두 같거나 수정 후 되돌린 경우 기존 무변경 제출 동작을 유지한다. 환자 버전과 기존 수용 응답을 유지한다. |

API 요청 본문과 화면 담당자의 호출 순서는 유지한다. DB 스키마 변경·기존 기록 일괄 수정은 없다. 기존 데이터는 세션을 만들 때 호환해 읽고 명시적 제출 시 반영한다.

## API 연결에서 주의할 의미

- `GET /api/voice/capabilities`의 `patient_projection_revision`은 `voice-patient-link-20261030-v1`이다. 기존 `voice_revision`, `connection_revision`은 유지한다.
- 기존 환자의 초안은 `POST /api/voice/sessions`에 `patient_id`를 넣어 만든다. `session.fields`, `field_metadata`, `baseline_summary`, `followup`을 함께 사용한다.
- `needs_clarification:true` 값은 현재 측정값으로 확정된 표시를 하면 안 된다. 새 세션에서도 해당 표시가 유지된다. `followup_unavailable_for`는 확인 불가 답변을 받았다는 뜻이며 정상 판정이 아니다.
- 음성 입력만으로 환자 등록·병원 문의가 실행되지는 않는다. 담당자 화면 확인 뒤 명시적으로 `/submit`을 호출한다.
- 실제 정보·확인 상태를 수정한 제출은 기존 환자정보 수정 계약을 따른다. 기존 문의·수용 응답을 종료하고 병원 재검토가 필요하다. 최신 문의 버전으로 수용 응답을 다시 받는다.
- 현재 음성 `/submit`의 기존 환자 수정 범위는 목적지 확정 전 `WAITING` 상태다. 목적지 확정·이송 중 상태를 이 경로로 덮어쓰지 않는다. 이송 중 기록·재평가와의 연결은 별도 계약 설계가 필요하다.
- 확인 질문 완료는 임상적 준비 완료나 제출 허용 판정이 아니다. 새 세션에서 과거의 미확인 상태를 유지하되, 사람이 확인한 뒤 제출하는 기존 계약을 변경하지 않았다.

## 검증 결과

| 검증 | 결과 | 의미 |
|---|---|---|
| 음성·환자정보 수정·문의·대화·중요 알림·추천 응답·이송 검토 회귀 | **356개 통과, 실패·오류 0** | 기존 174개 음성 회귀와 새 환자정보 반영 회귀 17개, 관련 서버 회귀 포함 |
| 실제 `VoiceClient` + 로컬 HTTP, 초안 흐름 | **12단계 통과** | 긴 문장·질문·수정·취소·재시도·동시 수정 |
| 실제 `VoiceClient` + 로컬 HTTP, 가상 환자·병원 흐름 | **11단계 통과** | 명시적 등록부터 후보 조회·병원 응답·정보 수정·재확인·도착까지 |

가상 환자·병원 흐름에서 확인한 순서:

1. 긴 보고문과 짧은 추가 답변으로 R1 초안 구성.
2. 화면 확인 API → 명시적 환자 등록. 저장 후 응답 유실을 가정한 동일 요청 재시도에도 환자는 한 명.
3. 가상 병원 후보 목록과 추천 상태 조회. CP-SAT 최적화 성능을 측정한 단계는 아니다.
4. 가상 병원에 문의. 병원 조회 결과에서 AVPU·중증도·혈압·맥박 확인.
5. 병원의 추가 질문과 구급대 답변 공유.
6. 병원이 수용해도 목적지는 자동 확정되지 않음.
7. 새 음성 세션에서 맥박만 갱신 → 기존 혈압·체온·산소포화도 보존, 이전 수용 종료.
8. 병원에 변경 알림 전달, 과거 문의 버전의 수용 응답 차단, 최신 정보로 재수용.
9. 명시적인 목적지 확정과 출발, 병원의 도착 예정 환자 조회.
10. 이송 중 음성 초안 제출을 통한 환자 덮어쓰기 차단.
11. 병원 도착, 병상 예상 점유 해제·실제 점유 반영을 함께 확인.

실제 마이크·화면 조작·외부 STT·실제 병원 연락은 사용하지 않았다. 음성 인식 정확도나 임상 효과의 검증 결과가 아니다. 테스트 DB는 실행마다 분리하고 종료 후 정리한다. 테스트 중 관련 소스 해시가 같음을 확인했다.

## 실행본과 기존 기록 보존

로컬 `http://127.0.0.1:18032`에 수정본을 실행했다. 기존 `.codex-build/paramedic-ui-20261030/demo.db`를 사용하고 자동 문의·배정 워커는 끈 상태다. 시작 전 백업은 `.codex-build/voice-patient-link-20261030/before-server-start.db`에 보관했다.

환자·문의·음성 세션·발화·변경 이력·요청·미측정 상태 테이블을 백업과 비교했다. 기존 데이터의 값과 건수가 같음을 확인했으며 결과는 `live-data-preservation.json`에 기록했다. 기존 실제 음성 시험 결과를 시험용 텍스트로 덮어쓰지 않았다.

## 재실행과 다음 연결

```powershell
python -m server.voice_connection_check --patient-flow --node "C:/path/to/node.exe" --output "outputs/voice_patient_flow/new_run"
```

출력 경로는 기존 결과를 덮어쓰지 않는 새 디렉터리여야 한다. `--patient-flow`를 빼면 기존 초안 12단계 검사다. 두 모드 모두 별도의 로컬 서버·임시 DB만 사용하며 기존 시연 DB는 사용하지 않는다.
