# 신규 개선안 2: 현재 부족이 확인된 가까운 후보 때문에 생기는 대기 축소

격리된 합성 시뮬레이션이다. 이전 실험과 모든 원문을 보존하며 운영 기본 `fixed_3`, 서버, 앱, DB는 변경하지 않았다.

결과는 미채택이다. 직전 normal 대비 H1·C1 각각 환자 관측 774건 중 처치가 빨라진 경우 11건, 늦어진 경우 6건이었다. 성공 상실과 문의 증가는 없었지만 배정 방식별 전체 순대기는 각각 44환자·분 증가했고, 개인 처치 지연은 최대 22분이었다.

## 원인과 한 가지 변경

기존 normal의 전체 405환경 원문을 읽어 확인했다. 기존 조기 준비가 NOT_DOMINANT인 657회 중 실제 pending 비교와 기존 공유 용량 조건을 만족한 것은 14회였다. 그중 8회에는 더 가까운 후보가 현재 신선하고 충분하다는 증거가 있어 후보를 제외하면 안 된다. 나머지 6회는 shared_fifo_burst의 두 시드에서 동일 환자가 반복 검토된 기록이며, 더 가까운 후보에 현재 공개 보고와 확정량을 반영한 부족이 확인됐다. 이는 준비 규칙의 도달 근거이며 환자 6명이나 성능 개선 6건이라는 뜻이 아니다.

원 조기 준비 단계가 끝난 뒤, 기존 보호·배정·물리 확인 전에 별도 준비 단계 하나를 추가했다.

- 최초 확정 전 SEARCH 상태에서 원래 NOT_DOMINANT로 보류된 실제 유효 수용 응답만 검토한다.
- 실제 pending 중 더 유리한 이동시간·병원 ID 후보가 하나라도 있으면 보류한다.
- 더 유리한 nonpending 구조적 후보마다 필수 자원 중 적어도 하나의 신선하고 알려진 부족이 있어야 한다. 과거 문의 여부로 후보를 지우지 않는다.
- 더 유리한 후보에 신선한 필수 자원 부족 증거가 하나도 없으면 보류한다. 미확인·노후 정보만으로 부족을 추정하지 않고, 신선하고 충분한 후보도 제외하지 않는다.
- 원래 전체 후보와 snapshot, 현재 등록 환자에 대한 공유 용량, TTL, 기회 보호·pending 보호·배정·최종 실제 자원 검사를 모두 유지한다.
- 새 승격은 별도 사건으로 기록한다. 실제 제출한 pending 업무와 백업 수용 응답은 원 기한·서비스·FIFO로 계속 처리하며, 원 조기 준비 사건으로 사칭하지 않는다.

첫 번째 실험인 선택적 재문의 억제는 성공 상실과 대기 증가로 미채택했다. 그 안을 이번 후보에 조합하지 않았다. 이전 결과는 [PROBE_GUARD_EXPERIMENT.md](PROBE_GUARD_EXPERIMENT.md)에 남겼다.

## 사전 고정과 검증

기존 135환경 유형을 바이트 단위로 유지하고 경계 6개를 추가했다. 공개된 개발 시드 44101~44103의 423환경에서 신규 954분기를 실행하고, 기존 전체 원문과 감사 증명 2430개를 재사용했다. 재사용 실행·CPU는 신규로 세지 않았다.

전체 자동 검사 2455개 통과, seed7 사전 통합 원문 294분기 감사 통과. 원래 여섯 개 선택적 로컬 HTTP 검사 제외는 유지했고 새 검사는 모두 포함했다.

규칙·입력 해시·원문 감사·선택 기준을 개발 성능 실행 전에 고정했다. 예약 시드 50101~50106은 과거 JSON/JSONL/gzip의 실제 seed 필드를 조사한 뒤 소스 고정 후 입력만 생성했다. 새 경계에는 현재 충분한 가까운 후보, 더 가까운 실제 pending, 두 번째 필수 자원, 조기 출발 뒤 미래 중단, 아직 등록되지 않은 단독 후보 환자가 포함된다. 미래 사건과 병원 작업 완료 예정은 정책 입력에 넣지 않는다.

통과 기준은 기존과 같다. 기존 성공 상실·개인 처치/최종 도착 악화·환경별 전체 순대기/제한 처치/문의 증가가 없어야 하며, 전체 순대기와 제한 처치 합은 엄격히 감소해야 한다. safe/protected 대비 조건도 별도로 검사한다.

## 저장 원문을 이용한 사후 원인 분석

최종 보고서와 독립 감사에 결속한 `posthoc-final.json`에 전체 환경의 변화와 실제 승격 사건을 남겼다. `posthoc-first-seed.json`은 그보다 먼저 작성한 첫 시드의 신규 경계 6개·H1 분석이며, 작성 당시 최종 보고서가 없었다는 사실을 보존했다. 분석을 위해 엔진을 다시 실행하거나 규칙·입력을 조정하지 않았다.

실제 조기 준비 승격은 H1·C1 각각 14환경에서 14회 발생했다. 단순 부족과 두 번째 필수 자원 부족은 각 3환경, 기존 `shared_fifo_burst`는 2환경에서 처치가 빨라졌다. 미래 병상 중단 3환경에서는 각각 0.5분 늦어졌고, 후발 단독 후보 환자 3환경에서는 먼저 등록된 환자의 이득과 후발 환자의 손실이 함께 발생했다. 전체 환경별 개선·악화 집계는 두 배정 방식에서 같았다.

첫 시드 `public_offer_later_scarce_patient`에서는 P01의 처치가 7.5분에서 5.5분으로 2분 빨라졌다. 그러나 2분에 등록된 동순위 P03은 H03만 이용할 수 있었고, 이미 확정된 병상 2개 때문에 문의 시작이 2분에서 24분으로 밀렸다. 실제 병원 검토 업무는 양쪽 모두 0.5분이었지만 처치는 6.5분에서 28.5분으로 22분 늦어졌다. 두 환자의 처치까지 시간 변화 합은 +20분이다. 이는 이동을 제외한 순대기 합과 별도 지표다.

첫 시드 미래 중단 경계에서는 P01의 확정이 2.5분에서 1.5분으로 빨라진 뒤, 4분에 H03 병상이 중단됐다. 보존된 실제 H02 수용 응답을 이용해 우회한 결과 처치는 6.5분에서 7분으로 늦어졌다. 조기 확정과 기존 백업·우회 처리가 함께 만든 결과이며, 각 기제의 기여를 분리한 실험은 아니다. 첫 시드의 기본·미래 중단·후발 환자 경계는 1.5분의 정책 입력과 결정이 동일했다. 정책이 아직 발생하지 않은 환자나 병상 중단을 알고 선택한 상황이 아니다.

전체 문의 수, 실제 병원 검토 서비스 시간 합, 제출된 문의의 큐 대기 합은 직전 normal과 같았다. 후발 환자의 손실은 문의가 제출되기 전 병상 확정 때문에 생긴 지연이므로 이 지표만으로 환자 대기 악화를 배제할 수 없다.

C1에서는 새 승격이 없는 6환경에서 기준의 `OPTIMAL`과 달리 `FALLBACK`, `budget_exhausted_before_stage_one`이 기록됐다. 예산은 원래 50ms였으며, 해당 배정 입력·실제 배정·환자 결과·문의 제출 기록은 기준과 같았다. 기준 측의 다른 한 경계에도 fallback 기록이 있어 함께 보존했다. 이번 H1·C1의 환경별 임상 결과가 같다는 사실과 solver 상태 차이를 구분하며, 이 상태 차이를 새 준비 정책의 성능 효과로 귀속하지 않는다.

## 결정과 해석

개발의 사전 기준을 통과하지 못해 예약 검증 성능 실행은 생략했다. 후보는 채택하지 않았고 기존 연구 기준과 운영 기본을 유지했다.

- H1 1차 실패 항목: no_individual_treatment_worsening, no_individual_final_arrival_worsening, no_case_total_wait_increase, no_case_capped_treatment_increase, strict_total_wait_reduction, strict_capped_treatment_reduction. safe/protected 포함 배포 조건: 미통과.
- C1 1차 실패 항목: no_individual_treatment_worsening, no_individual_final_arrival_worsening, no_case_total_wait_increase, no_case_capped_treatment_increase, strict_total_wait_reduction, strict_capped_treatment_reduction. safe/protected 포함 배포 조건: 미통과.

실제 운영 적용은 하지 않았다(`adopted=False`). 개발 배포 조건과 예약 검증 판정을 구분하며, 이 실험의 통과 여부만으로 운영 채택을 주장하지 않는다.

신선한 현재 부족은 미래에도 계속 부족하다는 보장이 아니다. 조기 확정은 뒤에 발생할 환자나 자원 중단과 경합할 수 있다. 이전 문의 억제 실험의 12건 상실을 해결한 변경이라고 주장하지 않는다. C1의 실제 50ms solver 결과와 fallback은 모두 원문에 보존하며 재실행하거나 불리한 실행을 제외하지 않았다. 같은 시각에 재실행하지 않은 캐시 기준과의 CPU 차이나 모든 C1 경로 차이를 준비 정책의 효과로 단정하지 않는다.

## 증거

- `simulation/public_offer_policy.py`, `public_offer_engine.py`: 순수 규칙과 실제 별도 준비 단계.
- `simulation/public_offer_audit.py`: 원문 복원, 새 승격·기회 보호·실제 백업 계보 검증. 원 조기 준비·pending 보호·물리·자원·FIFO·배정·normal 문의 감사는 같은 전체 원문을 사용한다.
- `simulation/public_offer_scenarios.py`, `public_offer_experiment.py`: 사전 고정 입력과 비교·선택·원문 저장.
- `simulation_results/public_offer_development_20261020.json` 및 `_cases/`: 모든 신규 실행과 캐시 전체 증명 결속.
- `.codex-build/public-offer-20261020/development-independent-audit.json`: 전체 원문 재감사와 사건 기반 효과·실제 문의 업무 분석.
- 같은 build의 `posthoc-first-seed.json`, `posthoc-final.json`: 첫 시드 경계와 최종 전체 원문·solver 차이를 결속한 사후 분석.
- 같은 build의 `preservation/`, `seed-audit/`, `pre-development-freeze.json`, `verification.json`: 선행 기록 보존·seed 노출 확인·사전 고정·최종 봉인.

사전 통합에서 원래 준비된 환자 뒤에 새 준비 환자가 붙는 순서를 감사기가 환자 목록 순서로 복원한 오류를 발견했다. 새 감사는 원 ready prefix와 실제 새 marker의 사건 번호를 차례로 결속하며 순서를 무시하지 않는다. 원문 51환경 102분기를 그대로 보존·재감사하고, 남은 192분기만 이어 실행했다. 규칙·엔진·환경은 바꾸지 않았다. 초기 실패와 2,451개 검사 통과 기록, 회귀 fixture 추가, 최종 검사·감사 결과를 모두 남겼으며 개발 성능 실행은 최종 사전 고정 후에만 진행했다.
